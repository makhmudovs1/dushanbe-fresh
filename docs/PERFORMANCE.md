# Аудит производительности Dushanbe Fresh

Дата: 6 октября 2026 года. Исходный коммит: `06ccbca`.
Числовые результаты отдельных проходов: [performance-results.json](performance-results.json).

## Вывод

Подтвердились три разных источника задержки:

1. **Dev-режим:** компиляция первого запроса, около 1,8–2,0 МБ передаваемого JS,
   инструменты разработки и повторные эффекты React Strict Mode. В production
   браузер передаёт около 101–111 КБ JS на проверенных маршрутах.
2. **Сетевой путь через ngrok:** установка TCP/TLS-соединения и доставка даже
   маленьких ресурсов занимают сотни миллисекунд, иногда секунды. Локальная БД
   таких задержек не показывает. Это не удалось устранить изменением приложения.
3. **Начальная загрузка каталога:** HTML -> JS -> гидратация -> fetch -> товары.
   Убрана зависимость появления данных от загрузки приложения: начальный каталог
   и товар теперь поступают с сервера в HTML-потоке под `Suspense`.

Дополнительно обнаружен и исправлен сбой запуска собранного API: CommonJS-приложение
Nest не могло загрузить ESNext-сборку `shared`. Теперь общий пакет компилируется в
CommonJS; его build дополнительно проверяет `require('./dist/index.js')` в Node.

## Методика и ограничения

- Chrome на локальном Mac, viewport 375×812, DPR 2, новый контекст браузера для
  каждого прохода. Это не измерение с физического телефона в Душанбе.
- Для каждого маршрута выполнено пять проходов. В локальных таблицах приведена
  медиана четырёх прогретых проходов; первый запрос с возможной компиляцией/JIT
  сохранён отдельно в JSON. Для ngrok учтены все успешные проходы.
- Сравнение dev/production в таблицах относится к **Next.js**: API на порту 4000
  оставался тем же, чтобы не менять две переменные одновременно. Реальный запуск
  собранного Nest с `NODE_ENV=production` и сравнение с `tsx` проверены отдельно.
- `TTFB` отсчитывается от начала навигации до первого байта HTML, включая DNS и
  соединение. В JSON отдельно сохранены установка соединения и ожидание ответа.
- `Данные` означает появление настоящего содержимого в DOM, не skeleton: карточки
  каталога, товар, позиции корзины, окна доставки либо позиции отслеживаемого заказа.
  Для корзины критерий проверяет ссылку реального товара, а не класс skeleton.
- Гидратация измерялась по появлению актуального счётчика корзины в header. Это
  проверяемый индикатор гидратации, **не полная трассировка всех React-компонентов**.
  Дополнительно сняты LCP, время выполнения JS и long tasks через браузерные API/CDP.
- В корзине три товара с минимальными количествами. Checkout проверяет окна и
  пересчёт quote после выбора слота; новые заказы при замерах не создавались.
- Публичная ссылка: `https://90e3-89-105-202-7.ngrok-free.app`. Обычное предупреждение
  Visit Site принято перед серией; специальные bypass-заголовки не применялись.
  Время этого первого ручного подтверждения в цифры не включено.
- Успешное отслеживание реального заказа измерено **только локально**. Передачу
  существующего токена через ngrok заблокировала проверка разрешений. Подтверждение
  для отдельного публичного тестового заказа не получено; результаты 404 не выдаются
  за замер работающего отслеживания. Токены, cookies и клиентские данные в JSON не сохранены.
- Это небольшой набор MVP-данных: 15 доступных товаров. Это не нагрузочный тест
  PostgreSQL или оценка производительности на тысячах заказов.

## Появление данных

Медианы, миллисекунды. В каждой ячейке: **было -> стало**.

| Страница | Localhost dev | Localhost production | Ngrok + production |
| --- | ---: | ---: | ---: |
| `/` | 331 -> 65 | 97 -> 47 | 1994 -> 749 |
| `/catalog` | 333 -> 48 | 88 -> 44 | 1469 -> 1593 |
| `/products/[slug]` | 346 -> 48 | 84 -> 40 | 1990 -> 1143 |
| `/cart` | 310 -> 301 | 60 -> 59 | 1171 -> 2970 |
| `/checkout` | 329 -> 316 | 81 -> 76 | 2088 -> 2950 |
| `/order/[trackingToken]` | 349 -> 330 | 96 -> 99 | Не измерено |

Нельзя интерпретировать колебания неизменённых cart/checkout/order как эффект
оптимизации. На публичном каталоге итоговая медиана даже хуже исходной: сеть
ухудшилась сильнее, чем сократилась клиентская цепочка загрузки.

### TTFB HTML

| Страница | Dev, мс | Production, мс | Ngrok, мс |
| --- | ---: | ---: | ---: |
| `/` | 26 -> 25 | 2 -> 16 | 788 -> 504 |
| `/catalog` | 24 -> 26 | 15 -> 16 | 677 -> 955 |
| `/products/[slug]` | 26 -> 24 | 14 -> 14 | 1083 -> 813 |
| `/cart` | 25 -> 21 | 3 -> 2 | 608 -> 1708 |
| `/checkout` | 25 -> 22 | 2 -> 3 | 1256 -> 1809 |
| `/order/[trackingToken]` | 24 -> 26 | 14 -> 14 | Не измерено |

Компромисс главной: вместо полностью статического ответа теперь динамическая
оболочка с потоковыми данными. TTFB вырос примерно на 14 мс, но реальные товары
появляются примерно вдвое раньше. Объём сжатого HTML вырос с 3,45 до 8,41 КБ;
у каталога с 3,49 до 7,34 КБ. Начальные данные не требуют дополнительного RTT клиента.

Первое открытие исходного dev: главная TTFB 1719 мс / данные 2221 мс; каталог
492 / 802 мс; товар 522 / 820 мс; корзина 167 / 442 мс; checkout 488 / 818 мс;
отслеживание 564 / 903 мс. Это отдельная стоимость компиляции, не задержка SQL.

### Контроль на одинаково медленной сети

Для `/catalog` отдельно выполнено по три прохода с CDP: latency 150 мс,
download 200 000 байт/с, upload 100 000 байт/с, CPU ×4. Это симуляция в Chrome,
не физическая мобильная сеть и не искусственная задержка в приложении.

- Данные: **1257 -> 525 мс**, примерно на **58% раньше**.
- Гидратация header: **1067 -> 1077 мс**. Она существенно не ускорилась.
- Браузерных запросов initial categories/products: **2 -> 0**.

В отдельном UI-тесте загрузка application JS удерживалась на уровне тестового
перехвата: карточки уже были видны, счётчик корзины ещё не гидратировался. После
разрешения загрузки JS повторного initial fetch не было; поиск и категории работали.

## API и PostgreSQL

HTTP-замер напрямую к локальному API: пять прогретых запросов, без Next proxy.
Prisma измерялась отдельно через query events и вызовы существующих сервисов.

| Операция | HTTP tsx, мс | HTTP собранного Nest, мс | SQL-событий | Сервис до/после, мс |
| --- | ---: | ---: | ---: | ---: |
| Категории | 2,5 | 2,5 | 1 | 2,2 / 1,0 |
| Каталог | 5,1 | 5,5 | 3 | 3,2 / 3,1 |
| Товар | 3,8 | 4,7 | 3 | 2,1 / 2,0 |
| Окна доставки | 9,1 | 7,7 | 3 | 3,4 / 4,7 |
| Checkout validate | 16,0 | 13,9 | 10 | 11,6 / 6,4 |
| Отслеживание | 10,0 | 8,3 | 10 | 6,3 / 5,9 |

SQL не менялся. Разброс сервисного времени не является результатом его оптимизации.
Десять событий включают управление транзакцией, а не десять запросов на каждую
позицию. Каталог загружает категории и quality options пакетно через `IN`, без
отдельных запросов внутри цикла по каждому товару. N+1 в проверенных путях не найден.
Query duration Prisma имеет миллисекундную точность: значение 0 не означает нулевую работу.

Через браузерный proxy исходные локальные GET занимали обычно 6–35 мс; через ngrok
те же API-запросы занимали сотни миллисекунд. В исходной серии categories/products
стартовали параллельно, но **после гидратации**. Ненужной последовательности между
категориями и товарами не было. Quote зависит от выбранного слота и корзины;
эту необходимую зависимость не заменяли спекулятивным запросом.

В checkout сохраняется одна транзакция RepeatableRead. Формальный `Promise.all`
над SQL в одной транзакции не добавляли; финансовую согласованность не меняли.

## JS, гидратация и ресурсы

Production, холодный кеш браузера. Учтены все загруженные `.js`, включая preload
webpack и автоматический Next prefetch. Размеры переданные, не распакованные.

| Страница | JS до/после, КБ | Chunks до/после | Гидратация до/после, мс | LCP до/после, мс |
| --- | ---: | ---: | ---: | ---: |
| `/` | 105,7 / 105,8 | 10 / 10 | 72 / 95 | 76 / 88 |
| `/catalog` | 106,0 / 105,8 | 11 / 10 | 72 / 87 | 70 / 60 |
| `/products/[slug]` | 111,5 / 107,1 | 12 / 10 | 68 / 72 | 130 / 74 |
| `/cart` | 105,7 / 101,2 | 10 / 8 | 60 / 59 | 112 / 106 |
| `/checkout` | 114,8 / 110,6 | 12 / 10 | 61 / 57 | 56 / 52 |
| `/order/[trackingToken]` | 112,1 / 107,9 | 11 / 9 | 69 / 70 | 124 / 134 |

Это не большой JS-рефакторинг: основной выигрыш в раннем содержимом, не в размере
бандла. Часть сокращения трафика связана с изменившимся prefetch динамической главной.
LCP главной в основном относится к hero, а не к каталогу ниже экрана. Поэтому
ускорение появления товаров нельзя подменять утверждением об ускорении всех метрик.

- Самые крупные production chunks: React/framework около 51 и 28 КБ переданного JS.
  Тяжёлых библиотек карт, редакторов или графиков на customer routes не обнаружено.
  Дополнительные dynamic imports ради нескольких маленьких компонентов не добавлены.
- В исходном dev JS занимал 1,78–2,03 МБ переданного и 7,84–8,74 МБ распакованного
  кода. В исходном production передавалось 106–115 КБ. По исходному времени появления
  данных production быстрее dev примерно в **3,4–5,2 раза**; JS меньше в **16–18 раз**.
  После серверной загрузки товаров показатель DOM почти не зависит от dev hydration;
  по гидратации финальный production всё ещё быстрее dev примерно в 3,7–5,2 раза.
- Начальные повторные запросы categories/products/product в dev были эффектом
  Strict Mode. Теперь начальные данные приходят с сервера, таких клиентских дублей нет.
  Strict Mode не выключен; отменяемый повтор tracking и эффекты checkout в dev остались.
- Tracking polling уже последовательный: следующий запрос через 20 секунд после
  предыдущего, таймаут 12 секунд, stop отменяет запрос. Наложения запросов не найдено;
  начальная загрузка не ждёт первого polling-интервала. Код и кеширование не менялись.
- Шрифты системные, отдельных font-запросов нет. CSS около 7,05 КБ переданного.
- У всех 15 доступных товаров в этой выборке нет фотографии; браузер получает одну
  общую SVG-заглушку **397 байт**, не 15 больших фотографий. `lazy` используется для
  карточек и корзины, `eager` для главного изображения товара; размеры зарезервированы.
  Не доказано, что реальные фотографии быстрые: их в измеренной выборке нет.
- Загруженные фотографии по текущему коду нормализуются API в WebP до 1600 px,
  но `ProductImage` пока `unoptimized`. Это потенциальная проблема для будущего
  заполненного каталога: нужны реальные фото, замеры и responsive thumbnails;
  причиной сегодняшних задержек её называть нельзя.

## Cache и границы компонентов

- Внешние страницы остаются Server Components; начальные данные вынесены в два
  небольших async-компонента. Client Components сохранены для фильтров, количества
  и корзины. Серверный URL API не передаётся клиентским props.
- `cache: no-store` и `force-dynamic` не создают общий серверный кеш цен/доступности.
  Обычный клиентский Router Cache Next остаётся; это не обещание мгновенного обновления
  уже открытой вкладки после правки каталога. Checkout всё равно перепроверяет данные.
- Категории и товары получают данные параллельно, без staff cookies/authorization.
  Есть таймаут 5 секунд, самостоятельные состояния ошибок и существующие кнопки повтора.
- Хешированные `_next/static` ресурсы используют долговременное immutable-кеширование.
  Для uploaded media аналогичный заголовок задан API; для отсутствующих в выборке
  реальных фото оценка кеша основана на коде, не на замере загрузки изображения.
- Public order API остаётся `Cache-Control: private, no-store`; order HTML также
  private/no-store. Персональные данные не переносились в общий кеш или Server Components.

## Что именно добавляет ngrok

В финальной серии медианная надбавка к локальному TTFB:
главная около **0,49 с**, каталог **0,94 с**, товар **0,80 с**, корзина **1,71 с**,
checkout **1,81 с**. Это сетевой путь целиком, а не отдельно измеренное время
процессинга внутри провайдера ngrok.

Доказательства нестабильности, а не только медленной отрисовки:

- В исходной серии соединение главной занимало от 281 до 5275 мс; локальный HTML
  при этом отдавался за несколько миллисекунд. Каталог один раз не достиг готовности
  за 60 секунд: в исходной публичной медиане четыре успеха из пяти, сбой сохранён.
- В промежуточной серии после исправления был `ERR_CONNECTION_CLOSED`. CSS размером
  всего 7,05 КБ доставлялся до 4,87 с; маленькие JS chunks тоже задерживались на секунды.
  HTML медленного каталога был получен примерно к 3,33 с, а CSS пришёл лишь к 8,05 с.
- В финальной серии TTFB каталога достиг 8,82 с. Неизменённые cart и checkout
  получили худшие публичные медианы при почти неизменной локальной скорости.
- Промежуточные неудачные и медленные проходы не выброшены из истории: см.
  `intermediateNgrok` в JSON. Локальные и контролируемые сетевые замеры подтверждают
  эффект изменения кода; нестабильный туннель не позволяет обещать общий коэффициент ускорения.

## Проверки и повторение

Прошли lint, typecheck, **246 тестов** (включая 81 интеграционный), build web и build API.
Собранный API дополнительно реально запускался в Node с production env на временном
порту 4300; этот процесс остановлен после проверки. Next production оставлен на 3000.

Шесть новых unit-тестов проверяют параллельный запуск запросов, фильтр/кодирование
параметров, `no-store`, отсутствие передачи staff cookies и состояния отказа API.
Браузером проверены фильтры, поиск, товар, добавление в корзину, quote и отсутствие
повторного initial fetch/ошибок гидратации. На 375/768/1440 нет горизонтального overflow.

Для самостоятельного повторения используйте команды production-запуска из README.
Не запускайте dev и build одновременно в одной `.next`. В Chrome DevTools:

1. Откройте Network, отключите кеш, выполните пять перезагрузок каждого маршрута.
2. Разделяйте Timing первого Document, API-запросов и загрузку CSS/JS; первый dev
   проход с компиляцией учитывайте отдельно. Для checkout сначала наполните корзину.
3. Через Performance запишите hydration/main thread; LCP не заменяет время данных.
4. Повторите через публичный URL и отдельно с одинаковым network/CPU throttling.
5. Не публикуйте HAR реального заказа: URL содержит приватный tracking token.

## Что осталось для Railway

Это аудит локального MVP, deployment не выполнялся. Практические следующие шаги:

- Запускать production-сборки, корректно настроить порты, `API_URL` при build и
  runtime, `DATABASE_URL`, staff secret, secure cookies и healthcheck существующего API.
- Разместить API и PostgreSQL рядом и связать сервисы приватной сетью; её адреса
  доступны в runtime, не во время build. Новый динамический каталог не требует
  доступности API для генерации статических страниц. См. [документацию приватной сети Railway](https://docs.railway.com/networking/private-networking/how-it-works).
- Подключить постоянное хранилище фотографий: существующий `PRODUCT_IMAGES_DIR`
  должен указывать на смонтированный volume либо позже заменить адаптер object storage.
  Данные volume сохраняются между deployment/restart. См. [Railway: volumes](https://docs.railway.com/guides/docker-compose).
- После запуска измерить сеть с телефона в Душанбе, подобрать регион по фактическому
  RTT, проверить cold start и настройки сна сервиса. При включённом сне первый запрос
  ждёт запуска сервиса. См. [Railway: advanced concepts](https://docs.railway.com/overview/advanced-concepts).
- Повторить SQL-профиль на реальном объёме и нагрузке, проверить лимит соединений;
  снять показатели с настоящими фотографиями и подготовить размеры для карточек.
  Удержать `private, no-store` для заказов и финансовых данных.

Railway уберёт зависимость от локального Mac и данного туннеля, но обещать конкретный
TTFB без deployment и измерений из целевого региона нельзя.
