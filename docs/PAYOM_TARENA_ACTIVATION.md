## Действия В Кабинете Payom

1. Добавить **77.95.0.94** в whitelist отправки API. Если нужен CIDR:
   `77.95.0.94/32`. Старый `91.207.75.174` больше не используется: после добавления
   нового удалить его из разрешённых адресов. Старому скомпрометированному VPS
   не нужен доступ к оплате/отправке SMS.
2. Открыть одобренный OTP-шаблон DFRESH и скопировать **полный UUID**.
   Убедиться, что выбран именно одобренный шаблон и отправитель DFRESH.
3. Найти пример API-запроса/данные переменной для конкретного шаблона. Если
   интерфейс показывает только `{code-1}`, спросить поддержку ниже. Не считать
   автоматически верным ни `code`, ни `code-1`.
4. Проверить положительный баланс, доступность отправки на нужного оператора
   +992 и цену короткого Unicode-сообщения/количество тарифицируемых сегментов.

Текст для поддержки, без JWT и номера получателя:

> Для нашего одобренного OTP-шаблона отправителя DFRESH (полный templateId
> возьмём из кабинета) редактор показывает {code-1}. Какой точный JSON-ключ
> должен быть в templateMessage.variables: code-1, code или другое имя?
> Пришлите пример templateMessage для этого конкретного шаблона и подтвердите
> совместимость DFRESH и нового whitelist IP 77.95.0.94.

Новый запрос поддержке агент не отправлял. Токен нельзя прикладывать к письму,
скриншоту, примеру запроса или сообщению в чате.

## Безопасный Ввод ENV

Из локального проекта открыть новый сервер:

```sh
ssh -t -F ops/tarena/ssh_config tarena-test
```

Уже внутри SSH выполнить:

```sh
SUDO_EDITOR='nano --ignorercfiles --restricted' sudoedit /etc/dushanbe-fresh/app.env
```

Не вводить JWT в командную строку, `export`, `echo`, curl header или чат.
Отключить запись терминала/экрана; вставлять значения только в редактор.
В существующем файле задать каждую настройку **один раз**:

```dotenv
CUSTOMER_SMS_URL=https://gateway.payom.tj/api/message
CUSTOMER_SMS_SENDER=DFRESH
CUSTOMER_SMS_API_KEY=
CUSTOMER_SMS_TEMPLATE_ID=
CUSTOMER_SMS_CODE_VARIABLE=
CUSTOMER_AUTH_ENABLED=false
CUSTOMER_REQUIRE_PHONE=false
MOBILE_CUSTOMER_API_ENABLED=false
```

Три пустых значения заполнить: raw JWT без `Bearer `, полный одобренный UUID,
подтверждённое буквальное имя переменной без `{}`. Не оставлять примерные значения.
Если подтверждён `code-1`, вписать именно `code-1`; если другой ключ, именно его.
Не менять `CUSTOMER_OTP_SECRET`, `STAFF_JWT_SECRET`, DB URL, proxy/quota настройки
и остальные строки. Новый OTP-secret уже есть и не должен заменяться токеном.
Сохранить `0640 root:adminj0n`, убрать токен из буфера обмена. Сервис не перезапускать.

Когда значения готовы, сообщить только «ENV заполнен, whitelist обновлён».
Проверку конфигурации и бесплатный GET balance агент выполнит из нового VPS,
читая private ENV без перезапуска API и без вывода токена/остатка средств.
Текущий `docker exec` runtime preflight не читает последующие изменения файла:
для нового ENV нужен существующий `payom-preflight.js --env-file ... --network`
в одноразовом trusted API image с readonly mount ENV. Это только GET health/balance.

## Одна Реальная Проверка

Только после успешной конфигурации/баланса и подтверждения параметров Payom:

1. Владелец выбирает **один свой тестовый номер +992** и явно разрешает одну
   платную отправку с согласованной стоимостью. Номер хранится в private ENV,
   не в Git/отчёте. OTP владелец вводит сам в сайт/приложение, не в чат.
2. Подготовить existing `CUSTOMER_SMS_PILOT_PHONE` и новый UUID
   `CUSTOMER_SMS_PILOT_ID`. Активировать существующий пилот после отдельного
   разрешения на изменение ENV/recreate API. `CUSTOMER_REQUIRE_PHONE=false`.
   Пилот пропускает только этот номер и резервирует одну попытку в БД до Payom.
3. Сохранить гостевую корзину/адрес, запросить код ровно один раз, проверить
   HTTP201 + UUID + положительный deliveryStatus. `SERVICE_ACCEPTED` означает
   очередь, не получение телефона. Дождаться фактической SMS/статуса доставки.
4. Ввести OTP, проверить создание профиля, привязку корзины/адресов, refresh и
   повторное открытие браузера/приложения. Проверить связанную доставку и
   списание в кабинете; агентский readiness-отчёт не печатает суммы/телефон.
5. При timeout/ошибке **не повторять отправку**, не менять pilot ID и не
   сбрасывать лимиты до проверки кабинета и нового разрешения владельца.

Один одноразовый код нельзя повторно использовать для второго независимого
входа Web/native. Сначала тестируется выбранная платформа; отдельная платная
SMS для другой платформы потребует отдельного согласия. Общий API/OTP/session
контракт покрыт unit/HTTP-тестами, но они не заменяют реальную доставку SMS.
Не отключать pilot restriction и не открывать отправки всем пользователям
автоматически после первого успешного входа: это отдельное решение владельца.

## Web И Приложение

Web и профили preview/production мобильной ветки используют один
`https://dushanbefresh.tj/api/v1`; DNS ведёт на один NestJS/одну `df_production`.
В production есть native auth/session endpoints с rotating refresh. Старый
backend мобильной ветки не деплоится поверх актуального main.
В main нет исходников нативного клиента: они в отдельной ветке/worktree.
Установленные APK/iOS и физические устройства не аттестованы этим переносом.
В EAS preview/production пока `EXPO_PUBLIC_ENABLE_ORDER_SUBMISSION=false`;
реальный клиентский release и разрешение заказов не выполнялись неявно.
