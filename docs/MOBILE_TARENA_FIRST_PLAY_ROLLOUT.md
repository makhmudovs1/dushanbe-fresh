# TARENA перед первым Android-тестом

План на утверждение владельца. Кандидат `cae0dabcf8ce65c08fc5c4316caf227912e5852d`. Меняются API мобильного геокодера и удаления, а также внешний WEB-маршрут `/account/delete`. Существующие контракты WEB и мобильного checkout, Payom и доступа сотрудников входят в регрессию.

## Доказательства и границы

- На выделенной PostgreSQL 14 повторены `pg_dump -Fc`, restore в новую БД и `prisma migrate deploy`. Хеши и количество строк `users`, `products`, `customer_carts`, `orders` совпали после миграции, включая 10 синтетических заказов. Для сравнения использована копия собственной тестовой БД. Репозиторный Compose указывает PostgreSQL 16. Точную версию, нагрузку и миграции работающего TARENA должен подтвердить оператор.
- На одной мигрированной копии последовательно подняли актуальный WEB/API `cae0dab` с выключенными функциями и предыдущий WEB/API `521b61e`. В обоих вариантах readiness, каталог с 12 позициями, auth status и HTML checkout успешны. Новый внешний маршрут доступен только у кандидата. При откате сохранились 10 заказов, 12 позиций и 2 кассовых записи. Проверка использовала локальные процессы из обоих SHA. Повторить её на фактических Linux-образах и версии PostgreSQL TARENA. [Результаты репетиции](mobile-rc-20261118/first-play-server-qa.json)
- 281 тест API по клиентским контрактам, окнам, geocoder и удалению прошёл на loopback. Отдельно проверены отозванные WEB/MOBILE сессии и OTP, очистка контактов и связанных данных, старый tracking URL, неизменные строки и суммы кассы, одно дело на конкурентные запросы и тот же результат при повторном исполнении. Для активных заказов, несведённой кассы, спорных связей и иных ограничений исполнение блокируется. [Runbook удаления](MOBILE_ACCOUNT_DELETION_RUNBOOK.md)
- Две additive миграции создают `mobile_geocoder_grants` и `customer_account_deletion_requests` с индексами. Вторая добавляет FK на `users` с `ON DELETE SET NULL`; проверить время получения блокировки на копии актуальной БД. Денежные таблицы, существующие заказы и каталог миграции не переписывают. Процессор удаления использует существующую схему и отдельный запуск `dist/scripts/process-account-deletion.js` в закрытом операторском контуре.
- HTTPS `/health` и `/products` вернули `200`, `/api/v1/mobile/geocoding/status` и `/account/delete` — `404`. SSH с проверенным host key и имеющимся ключом отклонён (`Permission denied (publickey)`). Текущие digest/SHA, реальная схема, журнал и offsite-копия остаются неподтверждёнными.

## Развёртывание после отдельного разрешения

1. **Снять состояние.** Попросить оператора TARENA предоставить read-only доступ или экспорт: SHA/digest работающих API/WEB и предыдущих образов, версию PostgreSQL, имена и состояние `_prisma_migrations`, свободные RAM/диск, количество DB connections и блокировки, статус health/ready, расписание backup и наличие off-host restore point. Проверить Caddy → WEB → API и откуда API получает доверенный IP. Для этого контура одновременно нужны loopback bind, очистка клиентских `Forwarded`/`X-Real-IP` на edge и корректный `X-Forwarded-For`. Проверить два клиента и границы IP-квот на стенде. Секреты, значения cookies и клиентские строки из БД в receipt не включать.
2. **Проверить резервную копию.** Сделать согласованную зашифрованную копию PostgreSQL и загружаемых изображений во внешнее хранилище утверждённым способом. Записать UTC, snapshot ID, checksum, disk/RAM budget, ответственного, целевые RPO/RTO и измеренное время восстановления. Проверить целостность, доступ к ключу и восстановление в новую изолированную БД той же основной версии PostgreSQL с отдельными ролями. Отключить исходящие SMS и пользовательские запросы на изменение данных. Сравнить счётчики/отпечатки заказов, позиций, сумм, кассы и профилей. Локальный synthetic restore не подтверждает состояние production-копии. [План резервного копирования TARENA](TARENA_BACKUP_MONITORING.md)
3. **Проверить совместимость на копии.** Из точного SHA построить Linux-образы API, WEB и migrator из [Production.Dockerfile](../ops/tarena/Production.Dockerfile) вне VPS. Зафиксировать digests. На копии запустить старые образы с новыми таблицами, затем кандидата с обоими флагами выключенными и WEB на том же origin. Пройти API readiness, каталог, цены, авторизацию через тестовый шлюз, корзину с ревизиями, расчёт и tracking по синтетическим данным. Проверить `/account/delete` в гостевом и авторизованном WEB и отказ при чужом Origin. Старый сборщик и курьер продолжают использовать свои scopes. Репозиторная `.dockerignore` исключает мобильный workspace и локальные env из контейнеров.
4. **Миграция и смена образов.** Во время согласованного окна применить одноразовым migrator `20261117140000_mobile_geocoder` и `20261117143000_account_deletion_requests` через `prisma migrate deploy`. До запуска проверить список pending и согласованный предел ожидания DDL на восстановленной копии. При неожиданной миграции, failed status или блокирующей транзакции остановиться и разобрать журнал Prisma. Затем заменить API и WEB на проверенные digests. `MOBILE_GEOCODER_ENABLED=false`, `CUSTOMER_ACCOUNT_DELETION_REQUESTS_ENABLED=false`, `CUSTOMER_ACCOUNT_DELETION_EXECUTION_ENABLED=false`. Mobile production checkout закрыт в AAB. Сохранить прежние auth/Payom/WEB GEOAPIFY настройки. Сравнить liveness/readiness, каталог, профили доступности, отсутствие новых 5xx и редиректов.
5. **Активация по одной функции.** Geoapify включать после успешного ограниченного теста со стендовым серверным ключом и подтверждения квот/прокси. Для старта задавать отдельно согласованный `MOBILE_GEOCODER_DAILY_LIMIT`, допустимый минимум 10. Удаление включать после утверждения версии и текста RU/TJ, очереди, поддержки, операционного порядка исполнения и правил хранения/бэкапов. Execution flag использовать в отдельном операторском процессе на одобренное дело. Публичный `/account/delete` и in-app request должны работать до закрытого теста, если сборка допускает создание аккаунта. [Настройка карт](MOBILE_MAPS.md) · [Процесс удаления](MOBILE_ACCOUNT_DELETION_RUNBOOK.md)

## Остановка и rollback

- При провале readiness, росте 5xx, проблемах WEB/доставки, OOM, неожиданной записи или всплеске расходов выключить соответствующий флаг. При проблеме с образом вернуть прежний API/WEB digest и предыдущую конфигурацию proxy. Повторить health/catalog/WEB. При откате версии сохранить новые таблицы и уже полученные запросы удаления.
- Восстановление выполнять в отдельную БД для проверки. Восстановление поверх работающей базы может потерять поступившие заказы. Стирать новые таблицы, запускать down-миграции и восстанавливать рабочие данные можно только в рамках отдельно утверждённого инцидента. Уже исполненное удаление требует применения согласованных правил к восстановленной копии.

## Первый запрос окон доставки

Первый журнал от `2026-11-18T07:51:34Z` сохранил `status: null` одновременно для `/delivery-slots`, `/health`, каталога и других путей. Его формат теряет различие между ошибкой транспорта и разбором ответа. В повторной диагностике без запроса окон DNS занял 20–78 мс, TCP установился за 21–81 мс от начала, TLS завершился за 4,47–5,62 с от начала, первый байт пришёл примерно через 0,19–0,22 с после TLS. Это согласуется с проблемой транспорта до обработки запроса, но точная историческая причина требует логов edge/API и клиентского `cause`.

Реальный локальный маршрут после удаления одного синтетического окна вернул `200` на восемь параллельных запросов за 17–21 мс. Окно создано один раз. Отключённое окно и его ёмкость сохранены. `DeliverySlotsService.list()` вызывает `ensureDeliverySlots`, включая вставку недостающих окон, а `readSlot` для конкретного окна читает таблицу. Поэтому production GET `/delivery-slots` исключён из повторных проб. Воспроизводимого дефекта кода route не найдено, семантика расписания сохранена.

Для локализации при следующем сбое сохранить фазу DNS/TCP/TLS/TTFB, статус и безопасный transport cause. Оператор сопоставляет UTC и путь с Caddy access/error logs, временем upstream, API logs, рестартами, нагрузкой PostgreSQL и lock waits. Отсутствие записи проверять с учётом ротации логов. Повторять запрос окон с измерениями только на изолированном стенде или после отдельного согласования его возможной вставки.
