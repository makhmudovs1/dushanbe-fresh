## Безопасный SSH: Команды Владельца

Сохранить текущую работающую SSH-сессию; не закрывать её до проверки нового входа.
Пароли и passphrase вводить только в защищённых prompts, никогда не в чат.

### 1. В Уже Открытой Сессии Нового VPS

```sh
whoami
passwd
```

Первый результат должен быть `adminj0n`. Использовать новый уникальный пароль.
Если был раскрыт ещё и другой системный пароль, его также нужно заменить.
Если текущая сессия закрыта, не использовать старый alias Dushanbe Fresh:
запросить у провайдера восстановление консоли или выполнить отдельный вход,
проверив предоставленный host fingerprint, и немедленно сменить пароль.

### 2. На Доверенном Mac, В Директории Проекта

```sh
cd /Users/mahmudovseravgan/Desktop/dushanbe-fresh
install -d -m 700 "$HOME/.ssh"
ssh-keygen -lf ops/tarena/known_hosts -E sha256
```

Сверить fingerprint с таблицей выше. Следующие команды выполнять только если
файлов с этими именами ещё нет; при вопросе об overwrite отвечать отказом.

```sh
test ! -e "$HOME/.ssh/df-tarena-20261029" && \
test ! -e "$HOME/.ssh/df-tarena-20261029.pub" && \
ssh-keygen -t ed25519 -a 64 -f "$HOME/.ssh/df-tarena-20261029" -C df-tarena-test
install -m 600 ops/tarena/known_hosts "$HOME/.ssh/df-tarena-known_hosts"
```

Задать passphrase на новый приватный ключ. Не принимать overwrite приватного
ключа и не использовать старый SSH-ключ. known_hosts содержит только публичный
проверенный host key, не credentials.

### 3. Установить Только Публичный Ключ

```sh
ssh-copy-id -F ops/tarena/ssh_config \
  -o PasswordAuthentication=yes \
  -o KbdInteractiveAuthentication=yes \
  -i "$HOME/.ssh/df-tarena-20261029.pub" tarena-test
```

Ввести уже НОВЫЙ пароль сервера в prompt. Парольный доступ разрешён только для
этого bootstrap-вызова. Профиль фиксирует IP/user/host key и запрещает agent
forwarding. Команда добавляет новый публичный ключ в authorized_keys, не переносит
старые ключи и не публикует приложение. При fingerprint mismatch остановиться.

### 4. Проверить Новую Независимую Сессию

```sh
ssh -F ops/tarena/ssh_config tarena-test
```

Если запрошена passphrase, это passphrase локального ключа. Профиль запрещает
password/keyboard-interactive, поэтому успешный вход доказывает key-auth.
В новой сессии выполнить `whoami` и `sudo -v` (пароль sudo не присылать).
Прежнюю сессию пока оставить открытой. После проверки на Mac можно разблокировать
ключ в локальном agent для дальнейшей автоматизации:

```sh
ssh-add "$HOME/.ssh/df-tarena-20261029"
```

Это не пересылка agent на сервер. Глобальное отключение password/root login
в sshd и firewall выполняются отдельным следующим этапом после проверки key/sudo
и плана восстановления доступа, с `sshd -t` и проверкой эффективных Match-настроек.
Без консоли особенно важно не закрыть последний рабочий канал.

## Фактическая Архитектура

- Web: Next.js 13.5.6, React 18.2, SSR/App Router, RU/TJ; админка в том же Web.
  Proxy `/api/v1` на Nest задаётся в `next.config.mjs` во время build. Next
  `dev`/watch в пилоте не использовать; для замера запускать production build.
- API: NestJS 10.3.10 / Express, один Node-процесс, Prisma 5.22, bcryptjs,
  jsonwebtoken, sharp/libvips. Один PrismaService; ограничить DB pool.
- DB: PostgreSQL 16. Корневой compose является LOCAL DEV: статический пароль и
  публикация `5432` на все интерфейсы. На новом VPS его без изменений не запускать.
- Постоянные файлы: отдельный `PRODUCT_IMAGES_DIR`; в production абсолютный путь
  обязателен. В пилоте только synthetic/repo images, не старые uploads.
- Старт API создаёт недостающие слоты доставки в своей БД. Это штатная запись,
  поэтому никакие пробные старты не должны указывать на реальную базу.
- Redis/Bull/отдельного scheduler/worker нет. Browser polling обычно 10-20 секунд;
  он учитывается при сценарии админки. Таймеры UI не являются отдельными демонами.
- Нужен также HTTPS reverse proxy для корректных Secure cookies сотрудников.
  Runtime-only процессы: Web, API, PostgreSQL, небольшой proxy/Docker/ОС.

## Предварительная Оценка 2 GB

Технически правдоподобно для небольшого MVP **без build на VPS**. Старые цифры
памяти не являются измерением TARENA или гарантией пиковой нагрузки. 2 vCPU
могут упираться в SSR, bcrypt и конкурирующие SQL/image operations; проверить
также steal time и задержки диска конкретного тарифа.

Начальные ограничения для пилота, не измеренные результаты:
- Web: ориентир cgroup MemoryMax 512 MiB; Node old-space 256 MiB.
- API: ориентир MemoryMax 384 MiB; old-space 192 MiB.
- PostgreSQL: ориентир 384 MiB, shared_buffers 128 MiB, work_mem 4 MiB,
  max_connections 20, Prisma connection_limit 5. work_mem выделяется на
  операцию/соединение; effective_cache_size не является резервированием RAM.
- Оставить запас под ОС, Docker, proxy и page cache. Heap limit не ограничивает
  весь RSS: учитывать Prisma/sharp/buffers/дочерние процессы и файловый кеш.
- Swap до 2 GiB как аварийный запас только на новом сервере после проверки
  текущего диска/разметки. Не считать swap оперативной памятью и не маскировать
  им устойчивую нехватку RAM. Не менять durability/fsync ради красивого benchmark.

## Изоляция И Сборка Вне VPS

1. После SSH bootstrap проверить Ubuntu/архитектуру/ядра/RAM/диск/время, логины,
   sudo/authorized_keys и наличие чужих служб. Получить от провайдера console/recovery.
2. Отдельные fresh runtime/deploy пользователи, новые секреты. SSH по allowlist
   на уровне provider firewall; Web/API/PostgreSQL только loopback. Docker-порт
   может обходить UFW, поэтому одной настройки UFW недостаточно.
3. Независимый тестовый каталог/DB/volume с marker, например `df_tarena_test`.
   Не копировать ни строки клиентов, ни парольные хеши, ни staff-сессии.
   Bootstrap/migration роль отдельно, API runtime без superuser/replication/DDL.
4. Собрать в чистом Linux builder/CI из reviewed локального source и lockfile.
   Текущий локальный HEAD `8bb9e75` является ориентиром, не доверять исходникам
   только из-за совпадения с compromised host. Нужен review источника и зависимостей.
5. Локальный Mac имеет ARM64: его node_modules нельзя просто скопировать на
   предполагаемый x86_64 VPS. Проверить `uname -m` TARENA и собрать под целевую
   Linux/glibc/OpenSSL архитектуру, включая Prisma/sharp. Builder не старый VPS.
6. Runtime на VPS: один Web и API под systemd, только PostgreSQL в Docker либо
   отдельно reviewed runtime images. Не добавлять ради пилота Kubernetes/Redis.
   Установку пакетов/образы брать из официальных источников, фиксировать версии
   и hashes/digests. Не переносить готовые .next/dist/images старого сервера.
7. Закрытый HTTPS endpoint на loopback, например `127.0.0.1:8443`, доступ через
   отдельный SSH local-forward. Использовать новый тестовый TLS/CA; DNS
   `dushanbefresh.tj` не менять. В SSH-профиле ClearAllForwardings=yes, поэтому
   нужный конкретный туннель разрешать явным override, не включать agent forwarding.
8. Снаружи подтвердить, что 80/443/3000/4000/5432/8443 не доступны. Изоляция по
   сети обязательна; robots/noindex или приложение-login её не заменяют.

## Синтетические Данные И Сценарии

- Создать 100-200 synthetic Product с RU/TJ и небольшими локальными изображениями,
  свежие категории, свежие staff admin/picker/courier и случайные пароли.
  Использовать `*.invalid` email и только заранее зарезервированные тестовые
  значения; ничего не отправлять на эти адреса/номера.
- Не запускать production seeds/reset. Текущий seed-staff допускается лишь
  development/test + local DB и имеет известные fallback-пароли: для пилота
  всегда передать новые случайные значения и проверить guard/целевую БД.
- Каталог/поиск/продукт/RU-TJ, добавление/изменение корзины и reload;
  guest checkout с новым synthetic заказом; отображение его в admin;
  раздельные разновидности/фактический вес/финальный расчёт; logout/session reuse.
- Авторизация сотрудников реально проверяется через fresh staff credentials.
  Customer OTP проверяется существующим loopback-only mocked Payom fixture в
  отдельном test-процессе/БД; это **не реальная SMS**. Не ослаблять production
  guards и не подключать Payom/Geoapify production keys ради пилота.
- При production-like API auth flags false, require-phone false. Customer mock
  тест отделить от runtime/performance-прогона. Внешние интеграции отключены;
  карта/ручной адрес проверяются без заимствования старого ключа.

## Измерения И Ограниченная Нагрузка

Все цели только новый staging, через loopback/SSH. Запретить redirects/произвольные
hosts в генераторе нагрузки; фиксировать IP/marker тестовой БД. Не использовать
URL рабочего сайта даже для health. Перед каждым этапом проверить цель.

1. 5 минут idle после прогрева; RAM/CPU/диск/cgroup/current/peak/OOM/restarts,
   swap-in/out, vmstat и доступная RAM с интервалом 1 секунда.
2. Functional browser smoke desktop/mobile RU/TJ с умеренной параллельностью;
   тесты не должны логировать пароли/OTP/cookies/authorization.
3. Ступени 1, 3, 5 запросов/сек по 60 секунд на каталог/API/product, максимум
   8 in-flight, ограничение до 600 запланированных запросов суммарно и cooldown.
   Рост очереди ограничен: пропуски/таймауты учитывать как проблему, не скрывать.
   Генератор запускать вне VPS, чтобы его RAM/CPU не искажали сервер.
4. Отдельная небольшая серия synthetic checkout/auth, с лимитом и сохранением
   корректности/idempotency. Не считать 60-секундный read-only тест полным
   доказательством способности обрабатывать bcrypt/изображения/заказы.
5. PostgreSQL: query timings на тестовом каталоге/joins/checkout, EXPLAIN ANALYZE
   проверенных SELECT; при pgbench только отдельная benchmark DB и ограниченные
   read-only серии. Не отключать fsync и не публиковать DB порт ради замера.
6. Фиксировать общий одновременный расход памяти, не сумму несинхронных пиков.
   Отдельно cgroup peaks Web/API/DB, p50/p95/p99, ошибки, CPU/steal/iowait,
   swap, disk growth, лимиты/размер тестового каталога, cold/warm и TLS/tunnel cost.
7. Остановить нагрузку при OOM/restart, устойчивом swap-in/out, MemAvailable
   ниже примерно 300 MiB, потерях/таймаутах или росте задержек/очереди. Сборку
   на VPS не добавлять в этот тест; build-пик измерить отдельно на builder.

Первичные цели приёмки, а не уже достигнутые цифры: ноль OOM/restarts, нет
устойчивого swap, запас RAM не меньше 300-400 MiB на согласованной нагрузке;
p95 API read около 500 мс и SSR до 1,5 сек после прогрева, ошибки <1%.
Пороговые значения пересмотреть по реальной сети/сценариям, не выдавать их за SLA.

Read-only `pnpm audit --prod --json` на доверенной машине сообщил в metadata:
5 critical, 29 high, 24 moderate, 10 low. Это вывод registry по дереву
зависимостей, а не столько же доказанно эксплуатируемых уязвимостей приложения.

его не найдено, а авторизация API отдельно проверяется Nest. Это не устраняет
другие advisories или необходимость обновлений. Нет автоматического audit fix.

## Что Требуется Для Продолжения

Владелец меняет пароль в своей текущей сессии, устанавливает новый публичный
ключ командами выше и проверяет отдельный key-only вход. Затем сообщает только
«Пароль заменён, ключ установлен» и наличие sudo, без credentials. Для полной
автоматизации ключ разблокировать в доверенном локальном agent (ForwardAgent=no).
После этого можно начинать read-only инвентаризацию нового VPS и согласованные
этапы bootstrap/staging. Старый VPS и production не трогать.

Окончательный вывод «стоит покупать» пока не сделан: не измерены TARENA CPU/RAM/
диск и не известны стоимость/SLA/backup/условия тарифа. Архитектура допускает
проверку 2 GB без on-host build; фактическая комфортность требует пилота.
