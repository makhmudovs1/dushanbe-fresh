# Архитектура

Простая архитектура MVP, рассчитанная на эксплуатацию сервиса доставки свежих продуктов
с рынков Душанбе. Цель: быстро запустить веб-продукт, не усложняя систему
раньше времени.

## Рекомендуемый стек

### Клиентская часть

- Next.js с App Router.
- TypeScript.
- React Server Components там, где нет интерактивности.
- Tailwind CSS для быстрой адаптивной верстки.
- TanStack Query для клиентских запросов в корзине, оформлении заказа и админке.
- React Hook Form + Zod для форм и валидации.

Один проект клиентской части обслуживает:

- публичный клиентский сайт;
- личный кабинет клиента;
- админ-панель по маршруту `/admin`.

### Серверная часть и API

- NestJS.
- TypeScript.
- REST API.
- Prisma ORM.
- PostgreSQL.
- Zod или class-validator для входных DTO.
- OpenAPI/Swagger для документации API.

NestJS выбран как простая и структурированная серверная основа для небольшой команды:
модули каталога, заказов, окон доставки, аутентификации и админки можно держать отдельно,
но без микросервисов.

### Аутентификация

- Электронная почта и пароль для администраторов.
- Оформление без регистрации для первого MVP: клиент может заказать без одноразового кода по SMS,
  указав имя, телефон и адрес.
- Сервер может автоматически создать или связать клиента по номеру телефона
  при первом заказе.
- Телефон + одноразовый код для клиентов - последующее улучшение авторизации,
  не блокирующее запуск MVP.
- JWT-токен доступа и токен продления в httpOnly cookie.
- Роли: `customer`, `admin`, `picker`, `courier`.

На MVP можно начать с ручного создания администраторов через скрипт начального заполнения.
Подключение SMS-провайдера должно быть скрыто за интерфейсом, чтобы в среде
разработки и предрелизном окружении использовать тестовые коды.

### Инфраструктура

- PostgreSQL как основная база.
- Redis не нужен для MVP, если нет высокой нагрузки. Временную корзину лучше
хранить на клиенте и синхронизировать при оформлении заказа.
- S3-совместимое хранилище для изображений товаров, если изображения
загружаются через админку.
- Docker Compose для локальной разработки.

### Принципы структуры

- `apps/web` содержит весь пользовательский интерфейс.
- `apps/api` содержит серверный API и бизнес-логику.
- `packages/shared` содержит общие типы, enum-значения и простые утилиты,
  которые реально нужны и клиентской, и серверной части.
- Админка живёт в том же веб-приложении, чтобы не создавать вторую клиентскую часть.
- Бизнес-правила вроде минимального заказа, стоимости доставки, наценки и
  доступных окон доставки хранятся в конфигурации и/или таблице настроек.

Это не складская система: сущность нужна только для учета закупки конкретной
волны доставки и расчёта маржи.

фиксировать в `wave_items` после рынка.

### Типы денег и количества

- Деньги нельзя хранить в `float`.
- Вес, дробные количества и цены нельзя хранить в `float`.
- Используем Prisma `Decimal` и PostgreSQL `NUMERIC` для денег, веса и
  дробных количеств.
- Денежные значения храним в TJS как `NUMERIC(12, 2)`.
- Количества и вес храним как `NUMERIC(12, 3)`.

Примеры:

- `9.90` TJS хранится без ошибок округления.
- `1.175` кг хранится точно.

Маржа считается как разница между продажной ценой и фактической закупочной
стоимостью, сохраненной в `wave_items`, с учетом финального количества товара.

## Основные маршруты API

Версионирование: все маршруты начинаются с `/api/v1`.

### Аутентификация

- `POST /auth/admin/login` - вход администратора по электронной почте и паролю.
- `POST /auth/refresh` - обновить токен доступа.
- `POST /auth/logout` - завершить сессию.
- `GET /me` - текущий пользователь.

Одноразовый код по SMS для клиента не обязателен в первом MVP. Эти маршруты можно добавить
после запуска:

- `POST /auth/request-code` - запросить одноразовый код по телефону.
- `POST /auth/verify-code` - войти или зарегистрироваться по коду.

### Каталог

- `GET /categories` - список активных категорий.
- `GET /products` - список товаров с фильтрами `category`, `search`.
- `GET /products/:slug` - карточка товара.

### Клиент

- `GET /addresses`
- `POST /addresses`
- `PATCH /addresses/:id`
- `DELETE /addresses/:id`
- `GET /orders`
- `GET /orders/:id`

### Корзина и оформление заказа

- `POST /checkout/validate` - предварительно проверить корзину, минимум заказа,
  цены, доступность товаров на сегодня и окно для интерфейса.
- `POST /checkout/orders` - создать заказ из корзины, в том числе без регистрации.

Сервер не хранит неоформленную корзину как обязательную сущность MVP.
Клиент отправляет позиции при валидации и создании заказа.

`/checkout/validate` нужен только для предварительной проверки интерфейса.
При создании заказа сервер обязан повторно проверить цены, доступность товаров
и вместимость окна доставки.

Проверка вместимости слота при `POST /checkout/orders` должна выполняться
транзакционно в PostgreSQL. Самый простой безопасный вариант для MVP:

- начать транзакцию;
- прочитать выбранную запись `delivery_slots` с блокировкой строки;
- посчитать количество активных заказов в этом слоте;
- если лимит `capacity_orders` исчерпан, вернуть корректную ошибку;
- иначе создать заказ, позиции заказа и привязку к волне доставки;
- завершить транзакцию.

### Окна доставки

- `GET /delivery-slots` - доступные окна доставки.

### Управление каталогом

- `GET /admin/products`
- `POST /admin/products`
- `PATCH /admin/products/:id`
- `POST /admin/products/:id/archive`
- `PATCH /admin/products/:id/prices`
- `PATCH /admin/products/:id/availability`
- `GET /admin/categories`
- `POST /admin/categories`
- `PATCH /admin/categories/:id`

### Управление заказами

- `GET /admin/orders?tab=active|completed|cancelled&date=YYYY-MM-DD&deliverySlotId=...&status=...`
- `GET /admin/orders/:id`
- `POST /admin/orders/:id/pack` - атомарная упаковка ещё не обработанных позиций
  как заказано, без перезаписи исключений; доступна администратору и назначенному сборщику.
  Количества и цены берутся из заказа, тело запроса не задаёт суммы.
- `PATCH /admin/orders/:id/status`
- `PATCH /admin/orders/:id/items/:itemId` - финальный вес, замена или удаление.
  Сборщику запрещено менять цену клиенту; корректировка администратором требует заметки,
  исходная зафиксированная цена не меняется.

### Управление волнами доставки

- `GET /admin/delivery-waves?date=YYYY-MM-DD&tab=upcoming|working|completed`
- `GET /admin/delivery-waves/:id`
- `POST /admin/delivery-waves` - совместимость и ручное восстановление старых данных;
  обычное оформление создаёт волну автоматически, кнопки формирования в основном интерфейсе нет.
- `PATCH /admin/delivery-waves/:id/assignments` - администратор назначает сотрудников.
- `PATCH /admin/delivery-waves/:id/status` - сборщик: picking/picked;
  назначенный курьер: out_for_delivery; администратор сохраняет контроль.
- `POST /admin/delivery-waves/:id/items` - добавить закупку для замены.
- `PATCH /admin/delivery-waves/:id/items/:itemId` - фактическая закупка.

Сборочный лист должен агрегировать товары по всем заказам волны:
товар, суммарное количество, единица измерения, заметки по качеству и список
заказов, где этот товар нужен.

`wave_items` создаются или обновляются из сборочного листа и фиксируют:
суммарно заказанное количество, реально купленное количество, фактическую цену
закупки и заметку поставщика.

`reference_purchase_price` (Decimal, допускает null для старых строк) фиксирует ориентир
каталога при создании позиции волны. Отклонение фактической закупочной цены строго выше
настраиваемого процента отмечается для проверки администратором без блокировки сборки.
Без введённой закупки, при нулевом закупленном количестве или неизвестном
историческом ориентире предупреждение об отклонении не показывается.
Курьер не получает закупочные поля ни при чтении, ни в ответе на смену статуса.

В будущем можно добавить `delivery_runs` и `delivery_stops` для маршрутизации
нескольких курьеров, но это явно не входит в MVP.

### Управление настройками

- `GET /admin/settings`
- `PATCH /admin/settings/purchase-price-deviation` - строковый Decimal-процент,
  0–100, по умолчанию 15; доступен только администратору.
- `PATCH /admin/settings/default-staff` - дежурные сборщик и курьер; только для администратора.
  Заполняет пустые назначения незавершённых волн, не заменяя уже назначенных людей.
- `GET /admin/delivery-slots`
- `POST /admin/delivery-slots`
- `PATCH /admin/delivery-slots/:id`

## Подход к развёртыванию

### Окружения

- `local` - Docker Compose: PostgreSQL, API, веб-приложение.
- `staging` - один сервер или PaaS-проект для проверки перед релизом.
- `production` - управляемый PostgreSQL и развёрнутые веб-приложение и API.

### Рекомендуемое развёртывание MVP

Самый простой вариант для боевого окружения:

- Клиентская часть: Vercel.
- API: Render, Fly.io или Railway.
- База данных: управляемый PostgreSQL у того же провайдера, что и API.
- Изображения: S3-совместимое хранилище.
- Домен: `dushanbefresh.tj` или аналогичный.
- TLS: сертификаты, управляемые провайдером.

Если важнее единая инфраструктура и предсказуемость расходов:

- один VPS;
- Docker Compose;
- Caddy или Nginx в качестве обратного прокси-сервера;
- PostgreSQL в отдельном управляемом сервисе или на VPS с ежедневным резервным копированием.

Для MVP предпочтительнее управляемый PostgreSQL, чтобы не тратить время команды
на ручное администрирование базы.

### CI/CD

- GitHub Actions.
- При запросе на слияние изменений:
  - проверка стиля кода;
  - проверка типов;
  - модульные тесты;
  - сборка веб-приложения;
  - сборка API.
- При слиянии в `main`:
  - развёртывание в предрелизном или боевом окружении согласно выбранному процессу.
- Миграции Prisma применяются автоматически при развёртывании API, но в боевом
  окружении только после успешного резервного копирования.

### Мониторинг и диагностика

- Журналы API выводятся в stdout.
- Отслеживание ошибок: Sentry.
- Базовый мониторинг доступности сервиса.
- Простые бизнес-метрики в админке:
  - заказы за день;
  - заказы по статусам;
  - сумма заказов;
  - загрузка окон доставки.

### Основы безопасности

- Пароли админов хэшируются через Argon2 или bcrypt.
- Токены продления хранятся только в виде хешей.
- Cookie продления сессии в браузере: `httpOnly`, `secure`, `sameSite=lax`.
- Административные маршруты защищены проверкой роли.
- Все цены пересчитываются на сервере при оформлении заказа.
- CORS разрешён только для доменов веб-приложения.
- Секреты хранятся в переменных окружения, не в репозитории.

## Ограничения MVP

В архитектуру намеренно не включены:

- торговая площадка для сторонних продавцов;
