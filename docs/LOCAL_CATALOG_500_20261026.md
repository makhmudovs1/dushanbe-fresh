# Локальный Каталог: HTTP 500

Это отдельная диагностика, не изменение адресного интерфейса или production.
Проводились только чтение схемы, истории миграций, количества строк и запрос Prisma.
Миграции, seed, reset, изменение товаров и заказов не выполнялись.

## Причина

Локальный API на порту 4000 использует Prisma Client текущей схемы, а локальная
БД PostgreSQL на порту 5432 отстаёт от неё. `Category.iconUrl`/`parentId` из
`apps/api/prisma/schema.prisma` ожидают `categories.icon_url`/`parent_id`.
Обе колонки отсутствуют. Прямой read-only `prisma.category.findMany()` даёт
`P2022`, колонка `categories.icon_url`. Чтение товаров также включает категорию.
Это рассинхронизация схемы, а не Geoapify, ключ, CORS или ошибка модального окна.

Последняя локальная применённая миграция: `20261018100000_category_presentation`.
Ожидают применения:

- `20261018160000_category_hierarchy`: добавляет обе колонки, индекс, FK и CHECK.
- `20261021090000_customer_accounts`.
- `20261024090000_customer_shopping`.

Контрольное количество: 14 категорий, 63 товара, 15 заказов. Остальные локальные
PostgreSQL-инстансы на других портах не являются целью и не изменялись.

## Безопасное Исправление

1. Явно проверить локальный DATABASE_URL: localhost:5432, БД dushanbe_fresh.
   Не использовать production ENV. Сохранить контрольные количества и содержимое.
2. Сделать PostgreSQL custom-format backup через `pg_dump -Fc`, проверить его
   `pg_restore --list` и тестовым восстановлением в отдельную временную БД.
3. Прочитать все три ожидающие миграции, проверить их на восстановленной копии.
   Они аддитивные, но FK/CHECK всё равно должны быть проверены на старых данных.
4. После отдельного подтверждения применить существующий `db:deploy` API
   (`prisma migrate deploy`) только с явно локальным DATABASE_URL. Затем выполнить
   `db:generate`, пересобрать и перезапустить локальный API.
5. Проверить GET categories/products (200), сравнить контрольные строки/количества
   и открытие каталога. Backup сохранить до завершения проверки.

Не использовать `migrate reset`, `db push --accept-data-loss`, seed, удаление
Docker volume или фиктивный `migrate resolve --applied`. Замена Prisma Client
старым тоже не исправляет отставшую схему.

В рамках адресного релиза этот план не выполнялся. Production проверяется
отдельно и не получает локальные миграции автоматически.
