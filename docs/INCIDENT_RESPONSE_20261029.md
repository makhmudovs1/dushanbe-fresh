# Dushanbe Fresh: аудит VPS и план восстановления

Дата: 29 октября 2026 года, пользовательское время МСК (UTC+3).
Объект: VPS `91.207.75.174`. Уровень реагирования: высокий приоритет.
Документ локальный: не отправлен на VPS или в GitHub. Значений секретов нет.

## 1. Статус И Границы Проверки

- Работы Payom и любые изменения production приостановлены по запросу владельца.
- Предыдущие инструкции ввода Payom-токена и генерации OTP на старом VPS отменены.
  Новые секреты нельзя вводить на потенциально скомпрометированную систему.
- Выполнены только просмотр кода/истории, чтение метаданных/имён ENV-параметров
  и агрегирующие SQL-запросы в явных `BEGIN READ ONLY` транзакциях.
- SSH выполнен без agent/X11 forwarding, туннелей и повторного использования
  ControlMaster. Проектный код и production-скрипты не запускались.
- Не менялись production-файлы, настройки, записи приложения, доступы и сервисы.
  Не выполнялись миграции, очистка, рестарты, ротация или запросы Payom.
- Чтение живой системы не является побитовой forensic-копией: SSH/SQL могут
  оставлять журнальные записи, чтение файлов может менять atime.
- Вывод гостевой ОС и её БД считается предварительным свидетельством, а не
  доказательством целостности: root-доступ и метаданные могли быть изменены.
- Полные root-журналы, `/root`, Caddy private storage и GitHub Security log
  не исследованы: текущего доступа для такого исследования недостаточно.

## 2. Основание И Модель Угроз

В [официальном отчёте FirstVDS](https://firstvds.ru/blog/postmortem-ataka-na-firstvds-17102026)
описан выборочный сбор файлов через гипервизор. Обычные SSH-журналы гостя не
исключают такую утечку. Точный список извлечённых файлов для конкретной ВМ
по зашифрованным архивам восстановить нельзя. Уведомление владельца связывает
этот инцидент с нашим VPS; индивидуальный scope должен подтвердить FirstVDS.

Рабочее решение для восстановления: считать раскрытыми доступные на VPS секреты
и не доверять его системе. Это консервативная оценка риска, не утверждение,
что злоумышленник доказанно прочитал всю нашу БД или вошёл в GitHub.
Ключи, добавленные после 17 октября, также перевыпустить: отсутствие дальнейшего
доступа к старой системе пока не установлено.

## 4. Риск БД, Сессий И Персональных Данных

- Localhost/`0600`/Docker не защищают от чтения диска через гипервизор.
  Возможны раскрытие пароля БД, чтение backup и offline-изучение файлов PostgreSQL.
  Точный факт выгрузки нашей БД или последующих подключений не установлен.
- В `User` хранятся имя, email/телефон, password hash и роли; в `Order`/адресах
  предусмотрены контактные сведения, координаты, домофон/ориентиры, состав и суммы.
  Финансовые операции и закупочные цены также являются конфиденциальными данными.
- Staff access JWT подписан `STAFF_JWT_SECRET`, живёт 10 минут и проверяет активный
  `sid` в БД. Refresh живёт до 7 дней, в БД только SHA-256 хеш случайного токена.
  Утечка хеша не равна готовому cookie; но JWT secret вместе с доступом к
  user/session IDs позволяет рассматривать подделку staff access как реальный риск.
  Только смены пароля или ожидания 10 минут недостаточно.
- Browser/native customer-токены opaque и хранятся хешами. Восстановление не
  должно возвращать ни старые browser/native sessions, ни refresh, ни OTP-challenges.
- Tracking-ссылки являются bearer-доступом и хранятся в `Order.publicTrackingToken`
  открыто; они могут присутствовать в access-логах. Если такие заказы найдутся
  в сохранённых данных, на новом хосте отдельно согласовать отзыв/замену ссылок.
  Заказы и позиции при этом не удалять.
- Карточный эквайринг/PAN/CVV в проверенной модели и интеграциях не обнаружен.
  Это не заключение о произвольных файлах/логах VPS и не отменяет риска PII.
- Оценить с профильным специалистом обязанности уведомления затронутых лиц и
  компетентных органов. Заявление хостера о своей billing-системе не доказывает
  отсутствие риска персональных данных Dushanbe Fresh.

## 5. GitHub И Внешние Сервисы

В `/home/deploy/.ssh` найден только `authorized_keys`: это публичные входящие
ключи, не доказательство наличия на VPS приватного ключа разработчика/GitHub.
Git remote использует HTTPS github.com без встроенных credentials; в двух
проверенных Git config не обнаружены credential helper/extraHeader.
Файлы `.git-credentials`, `.config/gh/hosts.yml`, `.npmrc`, `.netrc`,
`.docker/config.json` у deploy не найдены. В service home аналогичные GitHub
файлы не найдены. Root home недоступен, история команд не читалась.

Прямое похищение GitHub-доступа **не подтверждено**, но исключать его нельзя:
нужна проверка root, временных файлов, старых конфигураций, пересылавшихся
SSH agents и внешнего GitHub Security log. Само SSH-подключение без forwarding
не копирует приватный ключ с ноутбука на сервер.

Проверенный CI workflow содержит тестовую БД и проверки, но не настроенный
production-deploy и не ссылки на production secrets. Это не инвентаризация
всех секретов/Apps в настройках GitHub. Запись в репозиторий могла бы затронуть
исходники, workflows и будущие релизы; текущий HEAD не считается доверенным
только потому, что он совпадает на VPS и GitHub.

После разрешения проверить/отозвать обнаруженные credentials в GitHub Settings:
Security log, SSH/GPG keys, PAT, OAuth/GitHub Apps; для репозитория Deploy keys,
Webhooks, Actions/environment secrets, collaborator/ruleset/branch changes,
workflow runs и push/force-push начиная минимум с 14 октября. Сначала сохранить
журналы и идентификаторы ключей, затем отозвать затронутые, не просто создать новые.
[Экспорт Security log](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/reviewing-your-security-log).

Приоритет внешних систем:
- Geoapify: текущие server/tile ключи, ограничения, usage/billing/необычные запросы;
  одинаковые значения в локальном ENV тоже заменить, даже если ноутбук чистый.
- Payom: заморозить подключение; токен, если был на VPS, отозвать через кабинет.
  Старый IP убрать из whitelist перед реальным запуском на новом IP; пока не
  отправлять даже тестовую SMS и не включать auth.
- GitHub/npm/registry/Expo/EAS/боты/почта/S3/платёжные сервисы: менять именно те
  credentials, которые были на VPS, в его history/архивах либо использовались
  через forwarded agent. В активном ENV соответствующих интеграций не найдено;
  утверждать, что все эти аккаунты скомпрометированы, оснований нет.
- DNS/регистратор/FirstVDS: проверить внешние входы, API-ключи и изменения DNS,
  почту восстановления/MFA. Пароль, совпадающий с серверным, сменить независимо
  от того, содержался ли сам кабинет в описанном инциденте.
- TLS/ACME и SSH host authentication: новые ключи на чистом хосте, отзыв старых
  TLS-сертификатов и безопасное обновление known_hosts по согласованному плану.

## 6. Сохранение Доказательств И Ограничение Ущерба

Все действия ниже требуют отдельного разрешения. Сейчас не выполнены.

1. Открыть incident ticket у FirstVDS. Запросить немедленное сохранение текущего
   snapshot/образа всех дисков и доступных volatile/network-артефактов, retention
   гипервизорных/VMmanager/консольных/сетевых журналов. Не переустанавливать VPS.
2. Согласовать containment на стороне провайдера: изоляция старого хоста либо
   ограничение входящего/исходящего трафика до forensic-канала; сайт при
   необходимости временно заменить maintenance-страницей с чистой инфраструктуры.
   Не продолжать сбор новых пользовательских данных на недоверенном хосте.
   При продолжающейся атаке не откладывать containment ради идеального сбора.
3. Доказательства хранить отдельно от будущего production: зашифрованная копия
   с ключом на доверенной машине, ограниченные права, immutable/WORM-копия,
   SHA-256 после получения, UTC/МСК-время, источник, ответственный, журнал передач.
4. Сохранить forensic-копию дисков/тома PostgreSQL, WAL, `/etc`, homes, Caddy
   storage, SSH/sudo/auth/audit/journal, cron/systemd/timers, package и container
   metadata, `/opt/...`, `/tmp` и backup. Секреты в таком образе неизбежны:
   сохранять их только как изолированные доказательства, **не как рабочий ENV**.
5. Отдельно согласовать согласованный logical backup данных БД и upload-фото.
   Старые дампы также сохранить, включая 10 октября и перед релизом 29 октября.
   Их наличие на том же VPS не даёт независимой гарантии целостности.
6. Root-логи auth.log/auth.log.1/btmp и cron, `/root`/Caddy не читать обходом
   разрешений. Получить через уполномоченного администратора или provider image.
   Не запускать на живом хосте очистку/антивирус с удалением, upgrade, reboot,
   восстановление backup поверх БД либо новые служебные контейнеры.
7. Приобретённые образы исследовать read-only или на рабочих копиях в sandbox
   без production credentials и исходящей сети. Из гостевых логов нельзя
   доказать отсутствие гипервизорного чтения. Live-проверки не стирать.

## 7. Чистое Восстановление

1. Выбрать новый VPS в подтверждённо чистой инфраструктуре; предпочтительно
   независимый доверенный провайдер/контур. Новая VM в том же сомнительном
   control plane сама по себе не устраняет риск. У FirstVDS получить подтверждение
   для конкретного нового узла, если остаёмся у него. Не клонировать старый диск.
2. Установить свежую поддерживаемую ОС из официального образа, обновления,
   новые SSH host keys и администраторский доступ. Новый пароль/MFA провайдера,
   отдельный deploy principal, минимальные sudo, SSH только из разрешённых сетей.
   Новые клиентские SSH-ключи генерировать на доверенном устройстве, на сервер
   передавать только согласованные публичные части, не приватные ключи.
   Не копировать `/root`, `.ssh`, authorized_keys, cron, units или Caddy storage
   целиком; нужные настройки воспроизвести после ручного review.
3. Выбрать и проверить доверенный source commit на чистой машине по независимой
   истории разработчика и GitHub audit, включая изменения после 17 октября.
   Последний известный агентский runtime: `20341b0`, source/report `8bb9e75`;
   это ориентиры, не криптографическое заключение о доверии.
   Build/node_modules/.next/dist/образы со старого VPS не переносить.
4. Собрать заново из reviewed исходников и lockfile; проверить scripts,
   package/CI-конфигурацию и зависимости. Не запускать загруженные с VPS shell/SQL
   или package lifecycle scripts до проверки. Образ/container digest фиксировать.
5. На новом сервере создать новые DB bootstrap/migration/runtime роли и пароли.
   Runtime без superuser, replication, CREATEROLE/CREATEDB и владения схемой.
   PostgreSQL только localhost/private network; приложение не должно получать
   migration/bootstrap credentials. Старые роли/их хеши не восстанавливать.
6. Создать схему из доверенных миграций на пустой БД. Данные сначала обработать
   в quarantine. Не выполнять произвольный старый SQL и не делать полный
   `pg_restore` на новую production БД вслепую: источник с superuser-доступом
   способен внедрить исполняемые объекты в dump. `--data-only` не является
   гарантией безопасности. Проверить SQL/TOC, функции, extensions, triggers,
   policies, ownership, grants и метакоманды независимыми актуальными утилитами.
   [Предупреждение PostgreSQL](https://www.postgresql.org/docs/current/app-pgdump.html).
7. После review импортировать только согласованные таблицы/поля данных в
   доверенную схему. Не переносить session/refresh/OTP/auth-limit/pilot state
   как действующие доступы; историческую копию оставить в evidence. Staff users
   сверить с владельцем, перевыпустить пароль и убрать непроверенные роли.
   Не доверять перенесённым `_prisma_migrations` вместо собственной миграции.
8. Сохранить Product.id, разновидности, категории, реальные цены/настройки,
   orders/items, фактический вес, закупку, волны, финансы и аудит. Никаких seed,
   reset, автоматического восстановления удалённых товаров или стирания истории.
   Если данные пусты, подтвердить это с владельцем и независимыми копиями,
   не выводить автоматическое «ничего переносить не нужно».
9. Фото переносить только как проверенные разрешённые изображения; проверить
   сигнатуры/размеры/MIME, не исполнять файлы и не переносить симлинки/скрипты.
   Восстановить права и пути uploads заново; source assets брать из reviewed Git.
10. С нуля сформировать новый закрытый ENV, не копируя старый целиком или частично
    как готовый файл. Новые DB/JWT/SSH/TLS/Geoapify ключи; новый OTP secret только
    на чистой системе, независимо от JWT. Установить `CUSTOMER_AUTH_ENABLED=false`,
    `CUSTOMER_REQUIRE_PHONE=false`, `MOBILE_CUSTOMER_API_ENABLED=false`.
    Payom вводить только после завершения восстановления и отдельного разрешения.
11. Отозвать затронутые внешние старые ключи, проверить отказ старых доступов.
    Для Geoapify ограничить новый server key новым IP, tile key доменом/квотой;
    NEXT_PUBLIC ключ требует новой Web-сборки. В Payom заменить старый whitelist
    IP новым до первого теста, но не включать платную отправку автоматически.
12. Приостановить старые записи на согласованное окно, получить финальный
    проверенный data delta/backup и сверку. Подготовить TLS с новыми ключами,
    затем изменить DNS только по разрешению. Учитывать кеш DNS: старый VPS
    после cutover должен быть изолирован, а не оставлен вторым writable backend.
    Rollback допускается только к чистому релизу/хосту, не к старому VPS.

## 8. Приёмка До Возобновления Работы

- Восстановление БД отрепетировано отдельно, FK/количества строк/суммы/остатки,
  Product.id и раздельность разновидностей сверены. Миграции не меняют цены.
- Старые staff JWT/refresh/browser/native sessions не принимаются; новые
  staff пароли/роли согласованы. Старые ключи внешних сервисов отозваны.
- Админ/сборщик/курьер, закупка/фактический вес/финальный расчёт, guest checkout,
  сохранение корзины, RU/TJ, mobile/desktop, карта и координаты курьера проверены
  тестами в изолированном контуре. Реальные заказы не создаются для smoke.
- Снаружи недоступны PostgreSQL/API/internal Web; HTTPS/Origin/cookies/IP-limit
  корректны. Логи редактируют секреты, резервное копирование вынесено с VPS,
  тест восстановления завершён. Новые credentials не попали в Git/client output.
- Старые tracking-ссылки, если они обнаружены, пересогласованы/заменены без
  изменения исторических заказов. Не восстанавливать скомпрометированные bearer URLs.
- DNS/TLS направляют только на чистый сервер; журнал мониторинга не показывает
  неожиданных egress/login/credential changes. Provider containment подтверждён.
- Владелец принимает результаты. Payom возвращается отдельным этапом:
  бесплатный preflight, approved UUID/variable, новый IP whitelist, явное
  разрешение на одну SMS/номер. Ни одна проверка восстановления не даёт такого
  разрешения автоматически.
