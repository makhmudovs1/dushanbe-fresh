этим документом не разрешены.** Sender ID `DFRESH` активен по подтверждению

## Контракт Ответа Подтверждён Документацией

[Новая OpenAPI](https://payom.tj/payom-api.yaml) заменяет старую краткую страницу.
Локально реализована проверка **ровно HTTP 201**, UUID `id` и положительного
`deliveryStatus`. `SERVICE_ACCEPTED` означает очередь, не доставку. Также могут
быть приняты `SENT`, `ENROUTE`, `ACCEPTED`, `DELIVERED`; только последний означает
доставку. Отрицательные/неизвестные статусы, противоречивые поля ошибки, HTTP 200
и некорректный JSON отклоняются. Тело ограничено 64 КиБ, таймаут 10 секунд.
Ошибки 400/422 используют Problem Details и `violations`, 401 — `code`/`message`.
Сырой ответ может содержать OTP в `text`, поэтому не логируется и не сохраняется
в исключении. Клиент получает прежнюю обезличенную ошибку 503, без деталей Payom.

Остаётся получить у Payom реальный UUID одобренного OTP-шаблона и точный API-ключ
его OTP-переменной, совместимость с `DFRESH`, токен и whitelist. Для `{code-1}`
документация не описывает преобразование в API-имя: до ответа Payom не выбирать
автоматически ни `code`, ни `code-1`. Настройка обязательна, без значения по
умолчанию; сообщение для поддержки подготовлено в `PAYOM_SMS.md`.
Уточнить тариф Unicode,
сегменты и момент списания. `GET /api/balance` теперь документирован; он доступен
только с токеном и здесь не вызывался. Отдельного GET статуса сообщения OpenAPI
не содержит. Доставку проверять в кабинете: webhook не был реализован в этой задаче.

В текущем коде `sentAt` записывается только после успешного результата адаптера.
Отказ оставляет challenge непригодным для входа; автоматического повтора нет.

## Безопасно Записать Токен

**Это будущие действия владельца после отдельного разрешения на изменение ENV.
В рамках подготовки команды изменения не выполнялись.**

Подключиться без записи терминальной сессии, screen sharing и shell tracing.
Не передавать токен в SSH-команде, аргументах, `export`, `echo`, `curl -H`,
heredoc или чате. Встроенные снимки/логи редактора также должны быть выключены.
На сервере есть `/usr/bin/nano`. [Ограниченный режим GNU nano](https://www.nano-editor.org/dist/latest/nano.html)
не сохраняет историю и backup-файлы; чтение пользовательского nanorc
дополнительно выключено.

```sh
ssh -t dushanbe-fresh
SUDO_EDITOR='nano --ignorercfiles --restricted' sudoedit /etc/dushanbe-fresh/app.env
```

В редакторе установить без дублирующихся ключей:

```dotenv
CUSTOMER_SMS_URL=https://gateway.payom.tj/api/message
CUSTOMER_SMS_SENDER=DFRESH
# UUID одобренного Payom-шаблона, без выдуманного значения:
# CUSTOMER_SMS_TEMPLATE_ID=
# Точный API-ключ OTP-переменной после подтверждения Payom, без фигурных скобок:
# CUSTOMER_SMS_CODE_VARIABLE=
CUSTOMER_AUTH_ENABLED=false
CUSTOMER_REQUIRE_PHONE=false
```

Там же добавить подтверждённый `CUSTOMER_SMS_CODE_VARIABLE`, реальный
`CUSTOMER_SMS_TEMPLATE_ID` и `CUSTOMER_SMS_API_KEY` из
менеджера секретов непосредственно в редактор. Не использовать этот документ
как место хранения значения. Сохранить Ctrl+O, Enter; закрыть Ctrl+X и очистить
буфер обмена. Отдельный случайный `CUSTOMER_OTP_SECRET` не менее 32 байт также
потребуется перед активацией; не переиспользовать staff JWT secret.

Проверить только метаданные и флаги, не содержимое секретов:

```sh
sudo stat -c '%a %U %G %n' /etc/dushanbe-fresh/app.env
sudo /usr/bin/node --env-file=/etc/dushanbe-fresh/app.env -e 'console.log(JSON.stringify({endpointOK:process.env.CUSTOMER_SMS_URL==="https://gateway.payom.tj/api/message",senderOK:process.env.CUSTOMER_SMS_SENDER==="DFRESH",templatePresent:!!process.env.CUSTOMER_SMS_TEMPLATE_ID?.trim(),variablePresent:!!process.env.CUSTOMER_SMS_CODE_VARIABLE,tokenPresent:!!process.env.CUSTOMER_SMS_API_KEY?.trim(),otpSecretReady:(process.env.CUSTOMER_OTP_SECRET?.length??0)>=32,authOff:process.env.CUSTOMER_AUTH_ENABLED==="false",requiredOff:process.env.CUSTOMER_REQUIRE_PHONE==="false"}))'
```

Ожидаются `640 root dushanbe-fresh` и только булевы результаты проверки.
Не применять `cat`, `printenv`, общий `systemctl show Environment`, `set -x`,
`curl -v` или дампы HTTP-заголовков для проверки токена. Сохранить безопасные
права, не делать файл доступным всем. Не перезапускать сервис автоматически:
запись файла не означает разрешение активировать провайдера.

## Условия Единственной Платной Проверки

Перед запуском отдельно согласовать полный тестовый номер `+992` + 9 цифр,
согласие владельца номера, бюджет/стоимость, окружение и момент отправки.
Нужны подтверждённые whitelist, шаблон с UUID и установленный токен, а также
отдельно разрешённая установка обновлённого адаптера в согласованный контур.
Одно разрешение покрывает **одну попытку отправки**, не неограниченные retries.
При таймауте разрешение считается использованным: SMS могла быть принята.

Не включать необязательный вход глобально ради теста. Иначе любой посетитель
сможет расходовать баланс: существующие антиспам-лимиты не являются бюджетом
ровно одной SMS. Рекомендуется закрытый HTTPS-тестовый контур на этом же VPS,
чтобы сохранить исходящий IP, с отдельной БД и существующим OTP-модулем.
Его подготовка/запуск также требуют отдельного разрешения.

До реального теста необходимы ограничение единственным согласованным номером
и одноразовый запрет второй попытки отправки, сохраняющийся при перезапуске.
В production one-shot режим по-прежнему отсутствует. Теперь он подготовлен
локально (`CUSTOMER_SMS_PILOT_PHONE` + `CUSTOMER_SMS_PILOT_ID`), вместе с тестами
конкурентности, перезапуска и неопределённого таймаута. До отдельно разрешённого
релиза нельзя считать этот предохранитель установленным в production.
Тестовый транспорт не должен подменять генерацию OTP, TTL, лимиты, сессии
или реальную проверку ответа Payom. Использовать обычные code/verify endpoints.

В закрытом контуре допустим `CUSTOMER_AUTH_ENABLED=true` только после
прохождения перечисленных условий; `CUSTOMER_REQUIRE_PHONE=false` всегда.
Публичный production при этом сохраняет оба флага выключенными.
Успешная сессия в staging не выдаётся за проверку cookie на production-домене:
ограниченный пилот на настоящем домене требует отдельного согласования.

Не использовать `apps/api/test/customer-runtime.ts` для платного теста: этот
fixture специально подменяет ответы провайдера, захватывает OTP и меняет
тестовые данные. Он предназначен только для локальных mocks.

## Сценарий После Разрешения

1. Зафиксировать баланс, время, тариф и отсутствие других отправок в аккаунте
   Payom. Использовать кабинет владельца/документированный read-only API,
   без выгрузки секрета и полного журнала в чат. Сверить одноразовый бюджет.
2. В отдельном чистом браузерном профиле открыть согласованный HTTPS-контур.
   Выключить trace, HAR, видео, снимки OTP-поля и запись request/response bodies.
3. Ровно один раз нажать «Получить код». Это обычный
   `POST /api/v1/customer-auth/code` с номером в теле и корректным Origin.
   Не вызывать напрямую Payom `/api/message`, не нажимать «Отправить снова».
4. Проверить один вызов провайдера, HTTP 201 и положительное подтверждение тела.
   Не путать `SERVICE_ACCEPTED` с доставкой. Code endpoint возвращает `challengeId`, `retryAfter=60`,
   `expiresIn=300`, **не** SMS-код. Не логировать тело провайдера/OTP/токен.
5. Владелец телефона подтверждает получение SMS от `DFRESH` и сам вводит код
   в интерфейсе в пределах 5 минут. Не отправлять код или скрин SMS в чат.
   Текст должен соответствовать настроенному шаблону OTP.
6. `POST /api/v1/customer-auth/verify` подтверждает одноразовый код. При первом
   входе завершить шаг имени. Проверить `/customer-auth/me`, правильный аккаунт
   и отсутствие дубликатов; только агрегаты/булевы результаты в отчёте.
7. В HTTPS проверить cookie `__Host-df_customer`: HttpOnly, Secure,
   SameSite=Lax, Path=/, без Domain, Max-Age 30 дней. Значение не копировать.
   После перезагрузки страницы и повторного открытия браузера в том же
   постоянном профиле `/me` должен возвращать того же пользователя без SMS.
   Это не реальная проверка истечения 30 дней: expiry отдельно покрывается mocks.
8. Проверить повторное использование уже погашенного кода: отказ без новой SMS.
   Проверить выход и отзыв сессии без повторного входа (иначе потребовалась бы
   вторая платная отправка). Секрет cookie в БД хранится только как хеш.
9. В кабинете Payom найти ровно одну запись тестовой отправки по согласованным
   номеру/времени/id. Сверить «принято» и «доставлено», число сегментов, стоимость
   и транзакцию списания. Баланс до минус баланс после должен совпасть с этой
   транзакцией при отсутствии других операций. Одной разницы балансов недостаточно.
   Если списание отложено, отметить «ожидается», не объявлять проверку пройденной.
10. Снять тестовый доступ, отозвать тестовую сессию и остановить закрытый контур.
    Не удалять реальные заказы и не очищать production БД. Повторно проверить
    публичные auth-флаги и доступность гостевого checkout без оформления заказа.

Отмена шага имени у уже подтверждённого пользователя теперь покрыта исправлением
и browser-тестами локального кандидата; production пока не обновлён. Актуальные
блокеры, включая подготовку reverse proxy до включения SMS, описаны в
`PAYOM_ACTIVATION.md`. Успешный mocked OTP не заменяет проверку реального входа.
