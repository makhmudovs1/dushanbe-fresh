# Вход И Стабильное Восстановление Данных

1 ноября 2026, МСК. **Локально реализовано и проверено; production не изменён.**
Базовый реальный Payom-пилот описан в [отчёте 31 октября](PAYOM_PILOT_20261031.md).
Дополнительные платные SMS не отправлялись; лимит 2 из 3 не сбрасывался.

## Изменения

- Web: три последовательных экрана с нашим wordmark, стрелкой назад, белым
  фоном, чёрным CTA `#1F1F1F` и белым текстом. Небольшие зелёные focus-акценты
  сохранены. На телефоне форма занимает visual viewport и прокручивается при
  клавиатуре; на desktop это модальное окно. Safe area/reduced motion учтены.
- Телефон: фиксированный +992, флаг, маска 2-3-2-2, национальный ввод и вставка
  полного +992. Вставка другого международного префикса не превращается
  незаметно в таджикский номер. Автофокус и tel keyboard.
- OTP: один доступный input `autocomplete=one-time-code`, шесть ячеек,
  очистка форматирования при вставке, однократный auto-submit, ручной resend
  по абсолютному таймеру. Автоматической повторной отправки SMS нет.
- API различает истёкший код и исчерпанные попытки. Генерация, TTL 300 секунд,
  cooldown, лимиты телефона/IP/глобальные, HMAC, одноразовость и пилот не заменены.
- Новый пользователь вводит имя и фамилию после подтверждения телефона;
  прежний именованный аккаунт входит сразу. Редактор профиля имеет два поля.
  Фоновое обновление той же сессии не сбрасывает несохранённый черновик имени.
- Пока сессия неизвестна, CartProvider не гидратирует гостевую корзину.
  Явно разделены loading/loaded/error; до подтверждённой загрузки нет ложного
  «пусто» и нулевого счётчика. При известном владельце ошибка refresh сохраняет
  его данные. При повторе загрузки уже известные непустые позиции не исчезают.
- Ошибки корзины, избранного, адресов, профиля и истории отображаются как ошибки,
  не как пустые списки. Адреса и история загружаются независимо. Повреждённая
  гостевая localStorage-корзина не перезаписывается; storage-blocked guest cart
  продолжает работать в памяти и не требует входа для checkout.

## Модель И Совместимость

Additive migration: `20261031190000_customer_name_parts` добавляет только два
nullable TEXT-поля к `users`. Старые строки, имена, ID, корзины, заказы, адреса,
сессии и OTP не удаляются и не переписываются. Backfill отсутствует.

`CustomerProfile` дополнен optional `firstName`/`lastName`. Web и native PATCH
принимают либо оба поля, либо прежний `name`, но не смесь. Общий display name
продолжает использоваться прежними клиентами и checkout. Если старый клиент
сохраняет неизменённое имя, точные части сохраняются, включая многословные имена.
При реальном legacy-переименовании части сбрасываются в null во избежание
расхождения с display name. Сохранение имени и customer display name атомарно.

Сохраняются прежние правила merge/import, revision, источники импорта и явные
legacy-конфликты. Разновидности, цены, количество, min/step не менялись.
Гостевой checkout остаётся доступным; имя/фамилия не становятся новым
обязательным условием гостевого заказа.

## Проверки

- Workspace lint, typecheck и production build Web/API: прошли.
- 70 выбранных Web unit-тестов: прошли (cart reconciliation, storage errors,
  retry/hydration, форма/маска, существующие поверхности аккаунта и корзины).
- 58 выбранных API unit-тестов: прошли (профиль, OTP и checkout).
- 6 выбранных HTTP integration-тестов на отдельной локальной PostgreSQL:
  прошли. Проверены имя/фамилия в Web/native, старый PATCH name, сохранение
  частей при checkout, неверные/истёкшие/непосланные коды, одноразовость,
  cooldown и персистентный send budget. Native unchanged-name случай отдельно
  перепроверен двумя выбранными HTTP-тестами.
- 8 browser-сценариев в Chromium и те же 8 в WebKit: прошли на production-сборке,
  а не dev/HMR. Desktop 1440, mobile 375/390, RU/TJ; новый и повторный вход,
  guest merge, reload с задержанным auth/cart GET, ошибки API/storage, paste OTP,
  отсутствие дублированной проверки, resend, поворот и сохранение черновика.
- Operator test соседнего pilot-порта: прошёл, без private ENV/сетевых запросов.

Использовались отдельные локальные test DB и существующий mock-SMS runtime,
никаких клиентских production-данных, Payom token или реальных отправок.
Chromium/WebKit скриншоты просмотрены: телефон, код, имя и корзина.

## Публикация На TARENA

Нужны **подтверждение публикации Web/API и additive-миграции**, не разрешение
массовых SMS. SSH/firewall/DNS, ключи, auth flags и SMS-бюджет не менять.
Ниже процедура будущего окна, в этой задаче не выполнялась:

1. Сохранить текущие image digests/Caddy upstreams и проверить свежий encrypted
   backup с восстановлением существующим `daily-production-backup.py`.
   Известный риск отсутствия независимой offsite-копии не скрывать и не считать
   локальную копию независимым DR. Старый Алматы не является fallback.
2. Собрать immutable amd64 Web/API/migrator images вне VPS из согласованного
   Git commit/lockfile. Локальная QA-сборка использует localhost:4212 и отключённые
   Geoapify keys: **её нельзя копировать как production Web image**. Новый image
   собрать с production API URL и прежним разрешённым map-key способом, без
   включения server secrets в build context/layers. Реальные ENV не копировать.
3. Проверить память для временного соседнего API/Web. Не делать сборки на 2 ГБ
   VPS и не останавливать PostgreSQL/активный сайт ради освобождения памяти.
4. Выполнить только `prisma migrate deploy` новым trusted migrator с существующим
   закрытым migrator ENV. Не запускать seed/reset/bootstrap и не трогать сессии.
   Проверить новые колонки и отсутствие изменений business counts.
5. Прогреть кандидат API на **127.0.0.1:4013** с тем же production DB, pool и
   ограничениями. `ops/tarena/payom-ui-pilot.cjs` теперь допускает только 4012
   (default) или 4013 через process ENV `PAYOM_PILOT_API_PORT`.
   Взять скрипты в отдельный release-каталог, не перезаписывать shared файлы
   работающего контейнера. Не выполнять `activate-payom-pilot.py` повторно.
6. Сохранить ровно прежние private recipient, `ui-request.json`/pilot ID и
   `ui-provider-*.json` израсходованного слота. Не удалять/пересоздавать ledger
   и не менять OTP-secret. Wrapper и существующий OTP-flow продолжают запрещать
   другие номера и новую платную отправку. Root ENV auth/native flags остаются
   false, `CUSTOMER_REQUIRE_PHONE=false`; только процесс пилота использует
   существующее разрешение на один номер. Никакого расширения пилота.
7. Прогреть новый Web на соседнем loopback-порту с согласованным SSR API_URL
   и build-time rewrites. Проверить GET каталога/readiness, существующую сессию,
   профиль и корзину без logout/SMS или создания реального заказа.
8. Подготовить Caddy candidate: `/api/v1/*` на 4013, Web на новый порт. Validate,
   сохранить прежний несекретный файл, обновить активный bind-file с сохранением
   inode и сделать graceful SIGUSR1. Проверить HTTPS, PID proxy и существующий
   профиль/корзину. Только после drain убрать заменённые контейнеры TARENA.
9. На случай проблемы первым откатывать Web/routing. Не удалять новые колонки,
   не восстанавливать старую БД поверх новых записей, не менять cookies/secrets
   и не открывать Алматы. Предыдущий API совместим с additive-схемой, но старые
   записи `name` не поддерживают новые части: при необходимости полного API-отката
   отдельно проверить согласованность имён перед следующим roll-forward.

Повторная настоящая SMS, расширение пилота/публичный SMS-вход и проверка на
физическом телефоне требуют отдельного согласования. Текущий расходованный
слот не открывается заново автоматически при этом релизе.
