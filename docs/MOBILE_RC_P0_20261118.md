# Dushanbe Fresh Mobile 0.4.0 (5) — P0 перед закрытым тестированием

Порядок первого Android-теста и новый AAB из `cae0dab` описаны в
[плане Google Play](MOBILE_FIRST_PLAY_TEST.md). Там же находятся результаты
проверки карт, совместимости и риска `picomatch` для этого артефакта.

**Android — NO-GO для Play internal testing и публикации. iOS — NO-GO для TestFlight и публикации.** Оба build 5 прошли нативную покупку на выделенном PostgreSQL. Для магазинов нужны подписанные артефакты, работающий серверный контур карт и удаления, проверка на телефонах и утверждённые формы.

Версия Android и iOS `0.4.0 (5)`, SHA исходников `806abe322e5684bcd7d56a5894f6c36691f13644`. Preview, unsigned production AAB и архив `iphoneos` перечислены в [манифесте](mobile-rc-20261118/artifacts.json). Для локальной покупки собраны Release-варианты тех же исходников с отдельным тестовым API. Android использовал `tj.dushanbefresh.app.integration5` и разрешение HTTP только для `127.0.0.1`. iOS использовал preview ID и loopback API. Оба варианта проверили идентификатор изолированного API перед отправкой заказа. Store-кандидаты сохраняют выключенную отправку заказов.

HTTP-проверки дополнительно покрывают повтор запроса с тем же ключом, изменение цены/доступности, смену ревизии и конкуренцию.

## Production и серверные блокеры

Повторный HTTPS GET-аудит достиг production. WEB, health и каталог работают. Получены 46 товаров и 5 категорий. У всех товаров цена передана строкой, у 39 шаг 0,5. Публичный каталог сервера включает активные доступные товары. И WEB, и MOBILE auth status сообщают об обязательном входе. Анонимные профиль, корзина, избранное, адреса и заказы вернули `401` с `private, no-store`. Мобильный geocoder status, два deletion status и внешний URL `/account/delete` вернули `404`. Серверный SHA, применённые миграции и авторизованный сценарий живого Payom остаются неподтверждёнными.

Из повторного маршрута аудита исключены окна доставки: их GET на существующем backend может создавать расписание. В первом запуске все результаты остались без HTTP-статуса, включая запрос окон; серверный эффект этого таймаута не подтверждён. Аудит не отправлял SMS, заявки на удаление и заказы. [Снимок публичного контракта](mobile-rc-20261118/p0-production-read-only.json)

## Перед закрытым тестом

1. Подтвердить `tj.dushanbefresh.app` в Play Console и Apple Developer. Для Android нужен Play upload key и SHA-1 сертификата Play App Signing. Для iOS нужны Apple Team, действующие signing credentials и профили для зарегистрированного iPhone и TestFlight. Если после согласования используются EAS production profiles, сперва сверить удалённые счётчики Android/iOS — оба профиля используют `autoIncrement`.
2. Настроить отдельное тестовое окружение с серверным Geoapify и Android Maps key для точного package/сертификата. Утвердить ограниченный прогон и проверить карты на физических устройствах. [Android](MOBILE_QA_ANDROID_DEVICE.md) · [iPhone](MOBILE_QA_IPHONE_DEVICE.md)
3. Утвердить двуязычную политику, обязательное хранение, поддержку/оператора удаления и сроки, review access без общих обходных кодов. Затем отдельно согласовать backend rollout, подпись, включение checkout и загрузку в Play internal testing / TestFlight.

Для Android после согласования подпишите production AAB подтверждённым Play
upload key и сверьте его сертификат с Play Console. Установочный APK из Play
будет иметь сертификат Play App Signing. Для iOS выберите подтверждённую команду
в Signing & Capabilities, соберите `iphoneos` archive и проверьте его через Xcode
Organizer. Экспорт выбирается по назначению: development/ad hoc для указанных
устройств, App Store Connect для TestFlight. Signing flags, пути к ключам и пароли
задаются окружением владельца. [Apple — распространение](https://developer.apple.com/documentation/xcode/distributing-your-app-for-beta-testing-and-releases) · [Play App Signing](https://support.google.com/googleplay/android-developer/answer/9842756)

В этой сессии не запускались EAS jobs, production deployment, реальные SMS, production-заказы, API удаления на production и загрузки в магазины. Исходный WEB worktree остался на `main` и чист.
