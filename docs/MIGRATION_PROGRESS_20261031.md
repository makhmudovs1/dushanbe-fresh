### Автоматическое Продление

Ручные TXT нужны только для первичного сертификата до DNS cutover. Подготовлена
и установлена native Caddy конфигурация `ManagedStandbyCaddyfile`, проверена
через настоящий `caddy adapt`. `activate-managed-https.py --check` проверяет
оба домена через Google/Cloudflare и **не** включает HTTP-01, пока A/AAAA не
указывают только на TARENA. Сейчас guard корректно отказывает: A всё ещё Алматы.

После согласованного DNS cutover выполнить на TARENA:

```sh
python3 /srv/dushanbe-fresh/ops/activate-managed-https.py --activate-after-dns
```

Публичный вход останется503. Native Caddy получит managed certificates через
HTTP-01/TLS-ALPN-01, используя уже открытые80/443; DNS API/token и новые ручные TXT
не нужны. Первичный SAN certificate остаётся валидным fallback на период получения
managed certificates. Затем проверить managed storage для обоих имён, peer TLS
снаружи, сохранность managed leaf после restart и только после этого включать
`PublicCaddyfile`/публичные заказы. Он использует то же постоянное ACME storage.
При последующих обновлениях Caddy сам продляет сертификаты и загружает их в память.

Это подготовленная и проверенная конфигурация, **не утверждение, что HTTP-01
renewal уже активирован/проверен при старом DNS**. Текущий pre-DNS standby продолжает
использовать `disable_certs`; нельзя оставлять его окончательной production-конфигурацией.
Чтобы не создавать замкнутый gate, проверенный bootstrap TLS обязателен до DNS,
а native renewal + новая DNS/единая БД обязательны после DNS до открытия записей
(`production-gates.cjs`: отдельная фаза `activation`).

[Caddy Automatic HTTPS](https://caddyserver.com/docs/automatic-https),
[ignore_loaded_certs](https://caddyserver.com/docs/caddyfile/options#auto-https).
