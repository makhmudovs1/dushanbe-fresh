# Принятые решения

## 2026-10-24: Компактный хедер и разрешённая выкладка аккаунтов за флагами

- На desktop вход/профиль в хедере остаётся одной иконкой с tooltip/aria-label.
  У адреса скрыта только desktop-подпись города; сам адрес и выбор не меняются.
- На mobile профиль доступен из нижней панели, его дубль в хедере скрыт.
- Владелец разрешил push и production rollout подготовленных изменений.
  SMS и обязательный вход остаются выключенными до реальной настройки Payom.
  Миграции только additive, после backup и репетиции на восстановленной копии.
  Сгенерированные screenshots/traces/ZIP не входят в Git и релиз.

## 2026-10-24: Профиль, избранное и корзина аккаунта, только локально

- Переиспользуем клиентские OTP/сессии и `User`/`Customer`. Имя запрашиваем
  после подтверждения телефона, только если его нет: до SMS не раскрываем,
  существует ли аккаунт. Без настроенного провайдера вход честно недоступен,
  гостевой checkout сохраняется; обязательный вход не включаем.
- Избранное и корзина принадлежат аккаунту на сервере. Импорт гостевой корзины
  идемпотентен; одинаковый обычный товар объединяется по большему количеству,
  а не суммой. Конкурентные изменения требуют явного повторного сохранения.
  Исторические предпочтения не объединяются автоматически и не выбираются заново.
- Первый add без адреса открывает приглашение один раз за сессию. Адрес вводится
  по шагам, с отдельными необязательными деталями/домофоном. Геокодер не подключён;
  ручной ввод и существующая карта доступны без фиктивных подсказок.
- В мобильную icon-only навигацию после корзины добавлен профиль. В кабинете
  только работающие разделы; основные действия чёрные. Desktop использует
  компактные модальные окна, mobile адаптивные плашки в visual viewport.
- Новая additive migration `20261024090000_customer_shopping` дополняет прежнюю
  миграцию аккаунтов. Production, цены и реальные товары не менялись.
  Подробности и ограничения: `docs/CUSTOMER_EXPERIENCE.md`.

## 2026-10-21: Клиентский аккаунт и SMS, без production deployment

- По явному запросу владельца расширяем прежний гостевой MVP. Переиспользуем
  `User`, `Customer`, `CustomerAddress`; staff-авторизация остаётся отдельной.
- Провайдер не выбран. HTTP SMS-адаптер выключен по умолчанию; до реальной
  настройки и проверки гостевой checkout сохраняется. В production нельзя
  имитировать отправку, выдавать фиксированные коды или включать тестовый шлюз.
- Новый заказ принадлежит аккаунту через явный nullable `accountUserId`.
  Старые гостевые заказы не раскрываются по совпадению телефона: нужны приватная
  ссылка и подтверждённый совпадающий номер. Риск/COD/финансы не переписываются.
- Сессии клиента opaque/httpOnly, отдельны от staff JWT. OTP одноразовые,
  HMAC-хешированные, ограничены по времени, телефону, IP и попыткам.
- Адреса квартиры/дома и необязательная точка используют прежние адреса и
  snapshot заказа. Карта загружается по нажатию, GPS только по разрешению.
- Повтор заказа дополняет корзину актуальными публичными товарами, ценами и
  min/step; недоступные товары/варианты пропускаются с сообщением. Checkout
  повторно проверяет сумму и наличие, не меняя существующие расчёты.
- Нужна только additive migration `20261021090000_customer_accounts`.
  Настройки запуска, ограничения и тестовое окружение: `docs/CUSTOMER_ACCOUNTS.md`.

## 2026-10-20: Только мобильная витрина, без production deployment

- Новая компоновка ограничена `max-width: 1023px`, включая планшет 768px.
  Существующий desktop от 1024px сохраняется. Стили вынесены в последний
  override `apps/web/src/app/mobile-storefront.css`.
- Нижняя навигация содержит только главную, категории и корзину. `/categories`
  использует существующее дерево и независимые иконки из админки. Выбранный
  slug передаётся в URL; реальные дочерние категории доступны горизонтально
  на странице товаров. Данные и иерархия не создаются и не изменяются.
- Мобильная главная показывает существующие три баннера в native scroll-snap
  без autoplay, затем непустые опубликованные корневые категории. Тематические
  блоки содержат только реальные непустые дочерние категории: одна категория
  не повторяется в нескольких плитках. Desktop сохраняет прежние блоки.
- Адресного picker в текущем customer UI нет: показываем «Душанбе», не добавляя
  неработающий выбор города или GPS. Активный заказ остаётся доступен в хедере.
- Сердца скрыты только на мобильных grid-карточках. Избранное не удаляется;
  сохранённые данные и существующая страница/detail остаются совместимыми.
- Корзина использует прежний subtotal и те же quantity handlers. Закреплённый
  CTA находится над нижней навигацией; сумма остаётся предварительной, доставка
  не объявляется бесплатной. На checkout и в admin нижней панели нет.
- Учитываем safe areas и reduced motion. При фокусе поиска нижняя навигация
  скрывается, чтобы не занимать пространство у экранной клавиатуры.
- Миграций, seed, изменения API/pricing/checkout/Telegram нет. Production
  deployment допускается только после отдельного подтверждения владельца.

## 2026-10-12: Пилотный каталог и RU/TJ

- Источник импорта: `apps/api/prisma/data/pilot_catalog.json` из handoff v2,
  53 товара и 5 категорий. XLSX не используется для расчётов.
- Upsert по slug, без удаления товаров вне файла и без изменения ID, фотографий,

- Закупочная цена строго из `referencePurchasePrice`; продажная = закупочная × 1.15,

- `qualityOptions` в предоставленном JSON отсутствует: существующие варианты
  сохраняются, новым товарам варианты не выдумываются.
- По уточнению владельца от 12 октября фото больше не обязательно для включённого
  товара. Все 53 позиции активны; отсутствующие фото заменяются фирменным placeholder.
  Это отменяет требование обязательного фото от 3 октября. Ограничения загрузки файлов сохраняются.
- Customer UI: RU по умолчанию, TJ в переключателе, ISO-код `tg` в HTML/cookie.
  Cookie читается на сервере до рендера; localStorage и скриптов определения языка нет.
  Admin/staff остаются на русском. Приватные страницы по-прежнему noindex.
- Additive nullable поля: названия категорий/товаров, описание товара, подпись качества,
  таджикское название-снимок новой позиции заказа. Старые строки заказов не обновляются.
  Русские поля совместимы; для старых названий и описаний используется словарь перевода.

  без записей в БД. Эти проверки не заменяют интеграционные тесты бизнес-процессов.

## 2026-10-08: Удаление из каталога

- Товары и категории удаляются мягко через `deletedAt` и отдельные admin-only
  DELETE endpoints. Это не временное выключение: удалённые записи скрыты также
  в админке, обычное редактирование не может их восстановить.
- Категория удаляется только без неудалённых товаров, включая выключенные.
  Автоматического массового удаления нет; администратор сначала переносит или
  удаляет товары. Блокировка строки категории сериализует удаление с созданием
  и переносом товаров; блокировка товара защищает удаление от конкурентного PATCH.
- Исторические связи заказов, замен и волн, ценовые снимки и фотографии сохраняются.
  Ограничения БД требуют выключать удалённые записи; прежняя checkout validation
  отклоняет их. Расчёты заказов не меняются.
- Slug остаётся зарезервированным, восстановления в UI пока нет. Seed пропускает
  удалённые записи, чтобы не возвращать их незаметно. Перед удалением в UI есть
  подтверждение с названием; ошибка сервера остаётся в диалоге.

## 2026-10-07: Компактный каталог и быстрый выбор

- Карточки, корзина и страница товара переиспользуют один визуальный счётчик
  количества и прежний `CartProvider`. Reducer, формат `localStorage`, расчёты
  и контракты API не меняются. В каталоге минус на минимуме удаляет позицию;
  в корзине сохраняются минимум и отдельное удаление.
- Первый выбор весового товара использует `minQuantity`; невесового - одну
  единицу с нормализацией по существующим минимуму и шагу. Настройки товара
  важнее универсального правила «1 шт.»; обходить quantity validation нельзя.
- В API нет отдельного признака обязательности предпочтения. Поэтому любой
  товар с вариантами качества требует явного выбора в карточке. Разные варианты
  показываются отдельно; выбранные предпочтения никогда не заменяются молча.
- До гидратации корзины показываем компактную заглушку управления. Начальные
  данные каталога по-прежнему приходят из Server Component без повторного fetch.
- Админский список компактный, формы открываются нативным `dialog` с фокусом,
  Escape и возвратом фокуса. Все поля, загрузка фото, enabled/today и серверные
  проверки сохранены. Операционные страницы и checkout не перерабатываются.
- Браузерные тесты, изменяющие БД, требуют `RUN_MUTATING_UI_TESTS=1`. Созданный
  тестовый товар выключается, тестовый заказ отменяется; массовой очистки нет.

## 2026-10-06: Начальная загрузка публичного каталога

- Измерения обнаружили клиентскую последовательность HTML -> JS -> гидратация ->
  запрос каталога. Начальные категории/товары и карточку товара загружаем в Server
  Components под `Suspense`, не задерживая оболочку страницы. Независимые категории
  и товары запрашиваются одновременно. Гидратация использует эти данные без повторного fetch.
- Поиск, смена категории, повтор после ошибки и управление корзиной остаются
  клиентскими. Серверный fetch использует только публичные DTO, не передаёт staff
  cookies, ограничен таймаутом 5 секунд; ошибка показывает действие повтора.
- Для свежести цен и доступности сохраняем `no-store` и явно динамические страницы.
  Главная больше не является полностью статическим HTML: измеренный компромисс
  указан в `docs/PERFORMANCE.md`. Это не кеш персональных заказов.
- На текущем объёме данных SQL не оказался узким местом. Prisma/schema, checkout,
  снимки цен, auth и polling не менялись. Нестабильность сетевого пути ngrok
  отделяем от скорости приложения; подробные измерения в отчёте аудита.
- Реальный запуск собранного Nest выявил несовместимость: `shared` выдавал ESNext,
  а API загружает CommonJS. Общий пакет теперь собирается в CommonJS и в dev/watch,
  и в build; build проверяет загрузку результата в Node. Next продолжает использовать
  этот небольшой пакет через существующий `transpilePackages`.

## 2026-10-05: Исправление отслеживания через обычный браузер в ngrok

- Подтверждён HTTP 200 с HTML-предупреждением `ERR_NGROK_6024` вместо JSON:
  `credentials: omit` исключал cookie посещения туннеля. Токены checkout/URL/БД
  совпадали, запрос шёл по относительному proxy, ошибок guard или mapper не было.
- Используем стандартный `credentials: same-origin` и `Accept: application/json`.
  Без специальных ngrok-заголовков, хардкода домена или ослабления авторизации.
  Публичность API означает отсутствие требования staff-сессии, а не запрет
  технических cookies транспорта. Refresh cookie ограничена маршрутом `/api/v1/auth`.
- Skeleton показывается только до первого результата. Initial error имеет отдельный
  компактный экран; polling error сохраняет уже загруженный заказ. Последовательный
  опрос и таймауты сохранены, повторная попытка не запускает параллельный запрос.
- Проверка публичного UI должна проходить без `ngrok-skip-browser-warning`:
  этот тестовый заголовок маскировал ошибку предыдущей проверки.

## 2026-10-05: Публичное отслеживание гостевого заказа

- Добавлен только слой чтения `/order/[trackingToken]` и `GET /api/v1/public/orders/:trackingToken`.
  Внутренний цикл, авторизация сотрудников, checkout-суммы и снимки не меняются.
- `Order.publicTrackingToken` уникален и независим от id. Checkout использует
  `crypto.randomBytes(32)` (64 hex-символа). Миграция и создание вне checkout используют
  две независимые `gen_random_uuid()` PostgreSQL (244 случайных бита), без расширений.
  Добавление столбца с криптографическим DEFAULT заполняет старые строки без сброса данных.
- Публичный DTO собирается по явному списку, не из admin DTO. Телефон не выдаётся,
  адрес только в теле ответа. Сотрудники, заметки, цены закупки, ответственность,
  риск/политика клиента, кассовые расхождения и аудит недоступны.
- Статус определяется централизованно: отмена приоритетнее всего; незакрытое обращение
  или pending_review дают нейтральное уточнение; незавершённая замена даёт запланированную
  замену; иначе показывается текущий этап заказа. Ожидание внутренней проверки уже
  закрытого обращения само по себе не является проблемой клиента.
- `balance()` остаётся источником денежных итогов, возвратов и остатка к оплате.
  Позиции показывают текущий оплачиваемый состав после применённых отказов; оплаченная
  замена не вычитает уже оплаченную позицию исходного заказа. Корректировки имеют только
  фиксированные нейтральные подписи, не произвольные примечания администратора.
  У отменённого заказа сохранённая сумма подписана как сумма отменённого заказа,
  без призыва оплатить; исторические финансовые данные не переписываются.
- Повторная доставка берёт окно, статус и деньги из существующего технического заказа,
  не создаёт новых сущностей и не начисляет повторные сборы.
- Опрос каждые 20 секунд после ответа, таймаут 12 секунд, без параллельных опросов.
  Сетевые ошибки сохраняют последние данные. 404 прекращает опрос и удаляет только
  совпадающий последний токен устройства. Сохранение последнего заказа не является
  историей или авторизацией; чужая открытая ссылка не перезаписывает его.
- Bearer-ссылка открывает адрес её обладателю. Используем noindex/nofollow, no-store,
  no-referrer, ограниченный process-local rate limit по транспортному IP. За прокси
  лимит может быть общим; распределённый лимит, политика хранения/отзыва токенов
  и очистка внешних access-логов относятся к подготовке production.

## 2026-10-04: Проблемы доставки и контроль наличных

- Гость остаётся без регистрации. `Customer` идентифицируется только нормализованным
  телефоном; локальный формат +992/9 цифр является параметризуемым значением по умолчанию.
  Имя/адрес/телефон каждого заказа остаются снимками. Старая связь с `User` сохранена
  как `legacyCustomerId`, новые заказы используют `Customer`. Невалидные старые телефоны
  не ломают миграцию: связь остаётся пустой, SQL выдаёт количество таких заказов.
- Политики `manual_review`, `blocked`, неактивный профиль и `restricted` направляют
  заказ в `pending_review`, без волны. Он занимает место в окне, как любой неотменённый
  заказ. Подтверждение оператора повторно проверяет окно; закрытое окно нужно перенести.
  Клиент получает нейтральное сообщение, а не обвинение или фиктивную предоплату.
- Фиксированный `service_fee` остаётся исходным режимом. Необязательный
  `service_fee_percent` со значением по умолчанию 0 включает процентный режим только
  для новых заказов. Сумма сбора и процент фиксируются в заказе; старые суммы не меняются.
- После передачи курьеру обычная отмена недоступна. `DeliveryIssue` и позиции обращения
  описывают проблему отдельно от lifecycle, `fulfillmentOutcome` и оплаты.
  `OrderFinancialAdjustment` хранит подписанные Decimal-проводки, исходные
  checkout/packed суммы и позиции не перезаписываются. Все актуальные суммы считает API.
- Для частичного сервисного отказа снимаем товары и соответствующий процент сбора;
  фиксированный сбор и доставку сохраняем. При полном сервисном отказе снимаем всё.
  Если клиент передумал, по умолчанию сохраняем исходные сборы; настройка
  `customer_refusal_keep_fees` централизует эту гипотезу. До production нужна юридическая проверка.
- Однозначные товарные проблемы предварительно считаются сервисными. Ответственность
  клиента требует подтверждения администратора. Счётчики считают уникальные заказы,
  а не число повторных обращений. Два подтверждённых случая дают `watch`, но никогда
  автоматически не меняют `codPolicy` на blocked. Ограничение `restricted` снимает администратор.
- Наличная оплата, возврат и исправление хранятся отдельными append-only записями API.
  Старая отметка paid переносится в `legacyPaidAmount`, а не в фиктивную текущую кассу.
  В схеме сохраняются уникальность одного collection на заказ и одной открытой смены курьера.
  «Ноль получено» при ненулевом ожидании создаёт PaymentIssue даже при закрытии доставки.
- Кассовая смена открывается при первой денежной записи. Сверка смены независима от
  проверки заявлений о неоплате. Клиентское оспаривание повышает приоритет разбора,
  не доказывая вину клиента или сотрудника. Программа не доказывает передачу физических денег.
- Возврат курьером ограничен рассчитанным излишком, исходным курьером, открытой
  передачей и открытой сменой. После закрытия нужна отдельная административная
  корректировка начисления/кассы с причиной. Существующие записи не редактируются.
- Замена: `ReplacementDelivery` связывает исходное обращение с помеченным
  техническим Order `service_recovery` и номером `-R1`. Позиции/слот/статус находятся
  в этой связанной доставке, чтобы не дублировать закупку, упаковку и назначение волн.
  До оплаты товар переносится к оплате на замену; после полной оплаты замена бесплатна.
  Частичная оплата сначала требует финансового разбора администратора.
- Перенос уже упакованного заказа сохраняет тот же заказ с `requiresPicking=false`:
  новая волна доставляет его, но не включает в спрос/распределение новой закупки.
  Смешанные волны по-прежнему проходят обычные этапы сборщика и курьера.
- Запись денег/обращений выполняется в Serializable-транзакции с блокировкой заказа,
  версией `financialVersion`, идемпотентным `requestId` и хешем запроса в аудите.
  Повтор того же запроса не дублирует действие; разные действия со старой версией получают 409.
  Роль, активность, назначение и этап проверяются на сервере, административная причина обязательна.
- UI и ручные проверки описаны в [DELIVERY_FINANCE.md](DELIVERY_FINANCE.md).
  Не добавляем бухгалтерию, онлайн-платежи, сообщения клиентам, склад возвратов или ML.

## 2026-10-04: Несколько ролей и управление сотрудниками

- Источник прав сотрудников: `User.roles StaffRole[]`, тип PostgreSQL enum
  ограничен `admin`, `picker`, `courier`. Не вводим произвольные права, смены или HR.
  Старый `User.role` сохраняется для клиентов и совместимости схемы, но не RBAC.
- Аддитивная миграция переносит одиночные роли в массив, не меняя ID, пароли,
  назначения и refresh-сессии. Клиенты получают пустой массив. Перед обновлением
  останавливаем старые процессы записи и обновляем API/web совместно.
- Роль, назначение и этап проверяются независимо. Читать волну может сотрудник,
  назначенный хотя бы на одну свою роль; изменять может только свой текущий этап.
  Внутри транзакции роли/активность читаются повторно; сохраняем блокировки строк,
  Serializable и повтор транзакции при конфликте. Администратор сохраняет вмешательство.
- Один человек может быть сборщиком и курьером одной волны и обоими дежурными.
  Автоматическое создание/назначение волн не меняется. Недействительный дежурный
  пропускается при создании и явно отмечается в настройках. Историю не переписываем.
- Единая страница волны показывает сотрудников и прогресс, обновляется каждые 10 секунд.
  После `picked` открывается доставка без повторного входа. Курьер без назначения
  сборщиком не получает закупочные цены, поставщиков и маржу, даже имея обе роли.
- Администратор управляет аккаунтами в «Настройки → Сотрудники». Пароли bcrypt,
  роль администратора требует отдельного подтверждения. Собственное отключение/
  снятие административной роли и отключение последнего администратора запрещены.
- Отключение или снятие роли блокируется, пока есть незавершённое назначение.
  Сначала администратор переназначает работу. Для доставленной, но неоплаченной
  волны удерживается только назначение курьера; завершившего работу сборщика
  можно отключить. Разрешена замена курьера; оставлять её без курьера нельзя.
  Завершённые и оплаченные назначения остаются историческими, удаления аккаунтов нет.
- Изменение ролей, отключение и сброс пароля отзывают прежние сессии. Изменение
  имени само по себе не разлогинивает. Seed не возвращает изменённые роли/пароли.
- Минимальный `OperationalAudit`: `userId + createdAt + action + entityId`.
  Пишем закупку, упаковку, переходы этапов, доставку/оплату, назначения и действия
  управления сотрудниками в их транзакциях. UI аудита и политика архивирования
  остаются отдельными задачами. Не создаём event sourcing.

## 2026-10-03: Единицы измерения и фотографии каталога

- Значения API/БД не переводим: `kg`, `g`, `piece`, `pack`, `bunch`.
  Общий форматтер интерфейса `apps/web/src/lib/format.ts` даёт русские подписи,
  склонение пучков и десятичную запятую без преобразования Decimal в float.
- Фото обязательно при создании/редактировании товара с `isActive=true`,
  даже если он временно недоступен сегодня. Выключенный товар можно сохранить без фото.
  Старые seed-записи автоматически не отключаем: до первого редактирования они
  используют нейтральную общую картинку. Это временная совместимость, а не фото товара.
  Фиктивные старые seed-пути `/img/products/*.jpg` считаются отсутствующим фото;
  seed больше не создаёт такие пути и не перезаписывает фотографии при повторном запуске.
- Схема Prisma и публичное поле `image` не меняются: оно отображает `Product.imageUrl`.
  Новый маршрут загрузки `POST /api/v1/admin/product-images` доступен только администратору.
  JPEG/PNG/WebP до 5 МБ и 25 Мп проверяются декодированием через sharp,
  преобразуются в WebP до 1600 px, с учётом ориентации и без исходных метаданных.
- S3 пока не настроен. Вводим небольшой интерфейс `ImageStorage` с локальным
  адаптером; при обычном запуске файлы лежат в `apps/api/var/product-images`.
  В БД относительные `/api/v1/media/<uuid>.webp`, доступные через существующий
  proxy и HTTPS-туннель. Локальные адреса и base64 в БД не сохраняем.
- На production нужен явно заданный абсолютный `PRODUCT_IMAGES_DIR` на постоянном
  томе с резервными копиями (один API-инстанс). Для PaaS с временным диском или
  нескольких инстансов перед деплоем нужен S3-адаптер `ImageStorage`; он пока не реализован.
  Это не готовая инфраструктура S3 и не повод использовать временный диск в production.
- Фото отправляется при сохранении формы, не при выборе. Замена создаёт новый ключ,
  старые файлы не удаляются автоматически, чтобы не ломать прежние ссылки в корзинах.
  Очистка неиспользуемых загрузок остаётся отдельной эксплуатационной задачей.


## 2026-10-03: Автоматическое ежедневное расписание доставки

- Окна больше не зависят от разового seed на неделю. API при запуске и чтении
  публичного или административного списка добавляет недостающие окна на сегодня
  и следующие шесть дней по времени Душанбе (UTC+05:00).
- Сохраняем прежнее ежедневное расписание: 10:00–12:00, 14:00–16:00,
  18:00–20:00; вместимость нового окна 10 заказов. Параметры вынесены в единый
  `deliverySchedule`. Seed использует тот же механизм. Cron и фоновые очереди
  не нужны: после смены даты расписание пополняется при первом запросе.
- Автоматическое создание использует прежние детерминированные ID и
  `createMany(skipDuplicates)`. Существующее окно на ту же дату и время учитывается
  также с произвольным ID, в том числе отключённое. Его данные, волны и заказы
  не перезаписываются; старые окна не удаляются. Схема БД не меняется.
- Прошедшие, заполненные и закрытые сборкой окна не открываются заново.
  На пустой БД по-прежнему нужно один раз подготовить настройки оформления.

## 2026-09-25: Временный HTTPS-доступ к локальному MVP

- Для демонстрации используем ngrok только перед Next.js. API остаётся локальным,
  браузер обращается к нему через существующий `/api/v1` proxy. После сетевых сбоев
  Cloudflare Quick Tunnel не тратим время на повторную настройку QUIC/HTTP2.
- `dev:share` запускает только туннель; приложение отдельно запускается с точным
  `WEB_ORIGIN` полученного HTTPS-адреса. Адрес не фиксируется в исходниках.

- `STAFF_COOKIE_SECURE=true` позволяет включить Secure-cookie для HTTPS-демо
  без смены NODE_ENV. В production Secure обязателен независимо от переменной.
  HttpOnly, SameSite=Lax, область cookie и ротация сессии сохраняются.
- Это временный доступ к тестовой локальной БД, не production-развёртывание.
  Инспектор ngrok отключён; ссылку передаём только участникам тестирования.

## 2026-09-23: Упаковка заказов без повторного ввода количества

- «Разложить по заказам» заменено на «Упаковать заказы». Обычные позиции показаны
  компактно, формы открываются только через «Изменить». До подтверждения показываем
  «К упаковке», а не галочку сохранения. После физической упаковки сотрудник нажимает
  «Всё упаковано как заказано» один раз на заказ.
- `POST /admin/orders/:id/pack` заполняет только позиции в requested без finalQuantity:
  finalQuantity = requestedQuantity, status = picked, finalUnitPrice = saleUnitPriceSnapshot,
  finalTotal = количество × зафиксированная цена с прежним округлением Decimal HALF_UP.
  Все уже обработанные позиции, в том числе частичные/removed/unavailable/replaced, сохраняются.
- Операция атомарна под существующей блокировкой окна с повтором транзакции Serializable.
  Суммирует необработанные позиции одного товара, включая разные предпочтения по качеству, и проверяет
  всю закупку с учётом уже упакованных заказов. Нехватка откатывает всю операцию;
  повторный запрос безопасен, конкурентные заказы не расходуют один остаток дважды.
- Упакованность определяется существующими разрешёнными позициями и totalFinal,
  отдельный статус или флаг в БД не добавляется. Заказ остаётся в picking до завершения волны;
  существующий переход в picked и процесс работы курьера не меняются.
- Остаток = purchasedQuantity минус фактически упакованное в неотменённые заказы.
  Замена расходует закупку товара замены. До окончания упаковки остаток включает
  ещё не упакованное; после окончания это излишек компании, не добавляемый клиентам.
  Пока закупка не введена, остаток null. Складского движения/учёта нет.
- Ручная частичная упаковка по-прежнему пересчитывает итог через зафиксированную цену заказа.
  В форме упаковки не редактируется цена для клиента. Существующий отдельный
  механизм корректировки через API администратора с обязательной заметкой не менялся.
  Оформление заказа, зафиксированные данные, проверка закупочных цен, окна доставки,
  аутентификация и схема БД в этой задаче не изменены.

## 2026-09-23: Причины закрытия слотов и единицы закупочной цены

- Публичный список окон и проверка оформления заказа возвращают все применимые
  `unavailableReasons`: capacity_full, cutoff_passed, wave_closed,
  wave_cancelled, inactive. Интерфейс показывает соответствующие причины вместо
  универсального «Недоступно». Крайний срок заказа в текущем MVP равен началу окна в Душанбе
  (UTC+05:00); отдельной настройки этого срока пока нет. Завершённая/отменённая
  волна не открывает слот повторно. Проверка под блокировкой слота сохранена.
- `purchaseUnitPrice` всегда цена одной единицы, `purchaseTotal` всегда
  `purchasedQuantity × purchaseUnitPrice`, вычисленная сервером через Decimal.
  Отклонение сравнивает только цену за единицу с ориентиром, никогда не итог закупки.
  Порог по-прежнему применяется к абсолютному отклонению в обе стороны.
- В сохранённой локальной закупке бананов найдено: количество 16, цена за единицу 160,
  ориентир 10, итог 2560. Поэтому 1500% соответствовало сохранённой цене 160,
  а не подстановке итога в формулу. Текущая форма, API и преобразователь данных
  передают цену за единицу отдельно от итога. Источник ошибочного значения без журнала запросов неизвестен.
  Аналогично сохранены картофель 10 × 32 и кинза 50 × 75. Автоматически делить
  такие цены на количество нельзя: это догадка, которая изменит историю закупок.
  Завершённые записи оставлены без изменения; новые проверки используют отдельный заказ.
- Каталог администратора: «Цена для клиента» и «Ориентир закупки». Сборщик видит
  «Ориентир рынка» только для чтения и ввод цены закупки за 1 единицу, без поля продажи клиенту.
  Сохранённая строка явно показывает количество × цену за единицу = итог. Список закупки
  одноколоночный при любой ширине, раскрытие строки не удерживает соседние карточки.
  Формулы оформления, зафиксированные данные заказов и схема Prisma в этой правке не менялись.

## 2026-09-23: Автоматические волны и дежурные сотрудники

Уточняет решение 22 сентября: ручное формирование/назначение больше не является
частью обычного успешного сценария. Старые записи ниже описывают историю решений.

- Первый `confirmed`-заказ создаёт одну `open`-волну на окно доставки; следующие
  confirmed-заказы автоматически включаются в неё. Это одна Serializable-транзакция
  оформления под блокировкой окна; уникальный индекс delivery_slot_id и повторные попытки
  защищают от дублей. Оформление по-прежнему закрыто после начала сборки.
- `default_picker_id` и `default_courier_id` в app_settings задают дежурных.
  Используем только активных пользователей нужной роли. Пустое назначение
  автоматически заполняется, ручное назначение не заменяется. Настройки меняются
  через интерфейс администратора; сохранение также заполняет пустые назначения open/picking/picked-волн.
- Если дежурный отсутствует или деактивирован, заказ не теряется: волна создаётся
  без этого назначения, администратор видит «Не назначен» и устраняет проблему. Никакого
  выбора случайного сотрудника или планировщика нет. Скрипт заполнения сотрудников задаёт тестовых дежурных
  только при отсутствии ключей настроек, не меняет существующие пароли/назначения.
- Сборщик по умолчанию видит «Предстоящие» (open), отдельно «В работе» (picking)
  и «Завершённые» (picked/out_for_delivery/delivered/cancelled). Эти вкладки
  фильтруются сервером вместе с назначением и датой доставки. История остаётся доступной.
- Предупреждение требует введённой фактической закупочной цены, положительного закупленного
  количества и известного ориентира. Пустые закупки и старые строки без
  ориентира не получают ложного предупреждения. Процент считает сервер через Decimal;
  сообщение называет направление и величину отклонения. Цена клиенту не меняется.
- Начальное заполнение разделено на каталог, сотрудников, настройки оформления
  и окна доставки, а также необязательные демонстрационные операции. Демонстрация
  создаёт заказы через CheckoutService, не заполняя фактические количества и цены.
  Она не нужна для обычного запуска.
- `db:reset:operations --confirm` удаляет ВСЕ orders/order_items/waves/wave_items
  выбранной локальной БД разработки в транзакции, не только начальные тестовые строки
  (у старых данных нет надёжного признака происхождения). Каталог, сотрудники,
  клиенты, настройки и окна сохраняются. Запрещены боевое и предрелизное окружения,
  удалённая БД и запуск без подтверждения.
- Фильтр admin/orders применяется по deliverySlot.date, не createdAt. Интерфейс не
  показывает таблицу предыдущего запроса во время загрузки новых фильтров; смена
  даты сбрасывает выбранный слот и ограничивает список слотов этой датой.
- Проверка старой локальной БД: 3 confirmed-заказа без волны, одна старая назначенная
  волна в out_for_delivery. Закупки содержали, например, 43 кг огурцов по 232 сом/кг
  и 132 кг картофеля по 134 сом/кг. Старый seed-operations создавал только сотрудников;
  точный автор этих сохранённых тестовых значений неизвестен, журнал аудита отсутствует.

## 2026-09-22: Самостоятельная работа сборщика и курьера

Эта запись заменяет ручные подтверждения и передачу курьеру из решения 17 сентября.

- Успешное оформление создаёт `confirmed`. Цены, формулы и зафиксированные при оформлении данные не
  меняются. Если у слота уже есть `open`-волна, заказ сразу включается в неё и
  пересчитывается запрос закупки в той же Serializable-транзакции под блокировкой
  слота. После начала сборки новые заказы на слот по-прежнему запрещены.
- Администратор формирует волну и назначает сборщика/курьера. Сборщик сам начинает сборку,
  закупает товары, выполняет «Разложить по заказам» и завершает сборку. Переход
  волны в `picked` одновременно переводит её активные заказы в `picked`.
- Курьер видит назначенную волну заранее как «Готовится». После `picked` сам
  нажимает «Забрал заказы»: волна и заказы становятся `out_for_delivery`.
  Последняя доставка автоматически завершает волну; получение наличных отмечается
  отдельно для каждого доставленного заказа. Обязательных действий администратора между
  этапами больше нет. Списки и страницы волн обновляются каждые 10 секунд.
  Если все заказы волны в пути отменены, она завершается как `cancelled`.
- Сборщику запрещено передавать `finalUnitPrice`, в том числе через прямой API.
  Цена клиенту берётся из зафиксированных данных заказа. Существующая исключительная
  корректировка финальной цены с обязательной заметкой остаётся только у администратора
  и не меняет исходные данные.
- В `wave_items.reference_purchase_price` сохраняется Decimal-ориентир каталога
  при первом включении товара в волну. Для старых закупок неизвестный ориентир
  остаётся `null`, а не заменяется сегодняшней ценой. Такая сохранённая закупка
  помечается для проверки. Никаких новых сущностей нет.
- `purchase_price_deviation_percent` хранится строкой в `app_settings`, по умолчанию
  `15.00`; администратор меняет его через «Настройки» (0–100%, до двух десятичных знаков).
  Проверяется абсолютное отклонение в обе стороны, строго больше порога, через
  Decimal без округления процента. При нулевом ориентире любая ненулевая цена
  требует проверки. Флаг информационный: сборка и доставка не блокируются.
  Изменение порога обновляет флаг существующих закупок; журнал согласований не добавлен.
- Администратор может переназначить сотрудников до завершения волны, в том числе курьера
  в пути (но нельзя убрать последнего курьера без замены). Неоплаченный заказ
  можно отменить до доставки. Возвраты оплаченных заказов не добавляются.
- Вкладки заказов: «Активные» (confirmed/picking/picked/out_for_delivery),
  «Завершённые» (delivered), «Отменённые» (cancelled). Старые draft/placed
  не переводятся автоматически и не входят в эти вкладки; при миграции таких
  заказов администратор должен отдельно проверить их через API или сохранённый адрес страницы заказа.

## 2026-09-17: Управление заказами, волны доставки и сборка

- Одна волна на окно доставки закреплена уникальным ограничением БД. Администратор
  подтверждает placed-заказы, затем вручную формирует волну. Повторное формирование
  открытой волны добавляет новые confirmed-заказы, не перенося заказы из других волн.
  Для начатой/завершённой волны действие возвращает существующую волну без изменений.
- Перед началом сборки нужно подтвердить и включить либо отменить все оставшиеся
  placed/confirmed-заказы окна. После начала сборки оформление закрывается для этого
  окна. Проверка оформления и операции волны используют одну блокировку строки окна.
- Запросы собираются в wave_items по productId через Decimal. В каждой позиции
  сохраняются копии названия и единицы; предпочтения по качеству вычисляются из
  зафиксированных меток order_items с отдельными суммами и числом уникальных заказов.
  Несовместимые единицы одного товара в разных заказах блокируют формирование.
- Закупленные количество, цена и примечание вводятся вручную. purchase_total считает
  сервер. Ноль означает явно зафиксированную несостоявшуюся закупку; null означает,
  что закупка ещё не введена. Отмена заказа уменьшает запросы, но не удаляет закупку.
- Распределять можно только в статусе picking. Сумма распределения активным заказам
  не может превышать закупку. Уменьшить закупку ниже уже распределённого количества
  нельзя. Автоматического распределения веса и складских остатков нет.
- Клиентская final_unit_price по умолчанию берётся из saleUnitPriceSnapshot и не
  зависит от закупочной цены. Ручная корректировка цены требует примечания. Итог
  позиции округляется HALF_UP; total_final = сумма финальных позиций + зафиксированная
  стоимость доставки + сервисный сбор - скидка, минимум 0. До обработки всех позиций итог null.
- removed/unavailable дают нулевую сумму позиции. Пустой по факту заказ следует
  отменить, а не передавать курьеру. Сборы автоматически не меняются при исключении
  отдельных товаров; минимальная сумма не перепроверяется после сборки.
- Замена допустима только на другой товар в той же единице измерения. Закупка товара
  замены сначала добавляется в волну и записывается. remove_item запрещает замену;
  contact_me требует заметки о согласовании. Цена по умолчанию остаётся исходной
  ценой на момент оформления, явное изменение фиксируется с примечанием.
- Поток заказа: placed → confirmed → picking → picked → out_for_delivery → delivered.
  Для волны: open → picking → picked → out_for_delivery → delivered. До отправки
  возможна отмена; возвраты после доставки и отмена оплаченных заказов не реализованы.
  Переходы волны обновляют активные заказы в той же транзакции. Перед picked нужны
  закупки и все фактические данные; перед отправкой нужен курьер. Завершённые закупки
  и распределения неизменяемы. После delivered можно отметить наличные как paid.
- В выручку по товарам входят только позиции активных заказов, без доставки и сборов.
  Закупочная стоимость включает всю фактическую закупку волны, в том числе излишек.
  «Валовая маржа по товарам» = финальная товарная выручка - фактическая закупка.
  Незавершённые показатели имеют null, а не вводящий в заблуждение ноль.
- Аутентификация сотрудников: только активные сотрудники с ролями `admin`, `picker`
  или `courier` могут войти по электронной почте и паролю, проверяемому по хешу bcrypt.
  JWT-токен доступа короткоживущий (10 минут), а токен продления обновляется при
  использовании, передаётся только в httpOnly cookie с `SameSite=Lax` и хранится
  в PostgreSQL только как хеш SHA-256. Каждая проверка токена доступа дополнительно
  читает сессию и актуальные роль/статус, поэтому выход, отзыв сессии и деактивация
  сотрудника действуют сразу.
- Разграничение доступа по ролям (RBAC) намеренно простое. `admin` получает полный
  административный API. `picker` видит
  только назначенные волны/заказы и может выполнять закупку, распределение и
  переходы сборки. `courier` видит только назначенные доставки, не получает
  поля закупки/маржи и может отметить только доставку (delivered) и оплату (paid).
  Проверка назначения выполняется сервером, а не только интерфейсом.
- Для боевого окружения обязательно задать случайный `STAFF_JWT_SECRET` не короче
  32 байтов. Скрипт тестовых данных с известными паролями запрещён при `NODE_ENV=production`;
  он сохраняет существующие хеши и не является способом управления персоналом.
- Миграция не объединяет и не удаляет старые волны автоматически. Если в существующей
  БД уже есть дубликаты на слот, их нужно разобрать до применения уникального индекса.

## 2026-09-17: Оформление без регистрации и создание заказа

- Одна страница `/checkout`, без регистрации и OTP. Телефон нормализуется;
  девять цифр считаются местным номером +992. Совпадение телефона не является
  авторизацией: история заказов и сохранённые адреса гостю не выдаются.
- Существующий клиент связывается по телефону, новый создаётся при необходимости.
  Профиль существующего пользователя не перезаписывается неподтверждёнными
  гостевыми данными. Имя и телефон заказа сохраняются вместе с копией адреса.
- Сервер повторно читает продукты и настройки. `observedPrice` нужен только
  для уведомлений об изменении цены; все доверенные суммы считает Prisma Decimal.
  Каждая позиция округляется до двух знаков HALF_UP, затем суммы складываются.
- `minimum_order_amount`, `delivery_fee`, `service_fee` хранятся в app_settings
  строками с десятичными значениями. Если настройки отсутствуют или некорректны,
  оформление недоступно. Минимум применяется к товарам, без стоимости доставки.
- Предварительная проверка не резервирует окно. Создание заказа повторяет проверки в Serializable-транзакции,
  блокирует строку delivery_slots через FOR UPDATE и повторяет транзакцию при
  конфликте сериализации. Все заказы кроме cancelled занимают место.
- Слоты трактуются во времени Душанбе (UTC+05:00). Начиная с момента старта окно
  недоступно. API выдаёт активные окна ближайших семи дней, включая заполненные
  и уже начавшиеся с признаком available=false.
- reviewToken является отпечатком проверенных сервером данных. При изменении цены,
  суммы, предпочтения или времени окна создание заказа возвращает 409 и свежую проверку;
  пользователь подтверждает её заново. Токен не заменяет повторную валидацию.
- Для повторной отправки одного запроса используются уникальный checkoutRequestId
  и checkoutRequestHash в orders. Это предотвращает двойной заказ при повторном
  запросе после сетевого сбоя. Изменённое содержимое с прежним ключом отклоняется.
- Сохраняем копии адреса, контактов, названия, единицы, цены и предпочтения на момент заказа.
  finalQuantity/finalTotal остаются null до сборки. Оплата cash_on_delivery,
  статус pending. Предварительные суммы весовых товаров не являются финальными.
- Страница успешного оформления использует ответ создания заказа в памяти/sessionStorage текущей вкладки.
  Публичный поиск заказов по номеру/телефону не добавляется. Корзина очищается
  только после успешного ответа. Для просмотра в другом браузере позже нужна аутентификация.
- Отдельный скрипт заполнения данных оформления добавляет настройки и окна, не изменяя существующий
  каталог. API управления заказами пока отсутствует; его реализация с авторизацией является
  следующим этапом. Волны доставки и сборка в этот этап не входят.
