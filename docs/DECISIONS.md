# Decisions

## 2026-09-23: Упаковка заказов без повторного ввода количества

- «Разложить по заказам» заменено на «Упаковать заказы». Обычные позиции показаны
  компактно, формы открываются только через «Изменить». До подтверждения показываем
  «К упаковке», а не галочку сохранения. После физической упаковки сотрудник нажимает
  «Всё упаковано как заказано» один раз на заказ.
- `POST /admin/orders/:id/pack` заполняет только requested-позиции без finalQuantity:
  finalQuantity = requestedQuantity, status = picked, finalUnitPrice = saleUnitPriceSnapshot,
  finalTotal = quantity × snapshot price с прежним Decimal HALF_UP. Все уже
  обработанные позиции, в том числе частичные/removed/unavailable/replaced, сохраняются.
- Операция атомарна под существующей блокировкой слота и Serializable retry.
  Суммирует pending-позиции одного товара, включая разные quality options, и проверяет
  всю закупку с учётом уже упакованных заказов. Нехватка откатывает всю операцию;
  повторный запрос безопасен, конкурентные заказы не расходуют один остаток дважды.
- Упакованность определяется существующими разрешёнными позициями и totalFinal,
  отдельный DB-статус/флаг не добавляется. Заказ остаётся picking до завершения волны;
  существующий переход picked и courier flow не меняются.
- Остаток = purchasedQuantity минус фактически упакованное в неотменённые заказы.
  Замена расходует закупку товара замены. До окончания упаковки остаток включает
  ещё не упакованное; после окончания это излишек компании, не добавляемый клиентам.
  Пока закупка не введена, остаток null. Складского движения/учёта нет.
- Ручная частичная упаковка по-прежнему пересчитывает итог через snapshot-цену.
  В форме упаковки не редактируется цена для клиента. Существующий отдельный
  admin API override с обязательной заметкой не менялся. Checkout, snapshots,
  purchase review, slots, auth и схема БД в этой задаче не изменены.

## 2026-09-23: Причины закрытия слотов и единицы закупочной цены

- Публичные слоты и checkout validation возвращают все применимые
  `unavailableReasons`: capacity_full, cutoff_passed, wave_closed,
  wave_cancelled, inactive. UI показывает соответствующие причины вместо
  универсального «Недоступно». Cutoff в текущем MVP равен началу окна в Душанбе
  (UTC+05:00); отдельного настраиваемого cutoff пока нет. Завершённая/отменённая
  волна не открывает слот повторно. Проверка под блокировкой слота сохранена.
- `purchaseUnitPrice` всегда цена одной единицы, `purchaseTotal` всегда
  `purchasedQuantity × purchaseUnitPrice`, вычисленная backend через Decimal.
  Отклонение сравнивает только unit price с reference price, никогда не total.
  Порог по-прежнему применяется к абсолютному отклонению в обе стороны.
- В сохранённой локальной закупке бананов найдено quantity=16, unitPrice=160,
  reference=10, total=2560. Поэтому 1500% соответствовало сохранённой цене 160,
  а не подстановке total в формулу. Текущая форма, API и mapper передают unit price
  отдельно от total. Источник ошибочного значения без журнала запросов неизвестен.
  Аналогично сохранены картофель 10 × 32 и кинза 50 × 75. Автоматически делить
  такие цены на количество нельзя: это догадка, которая изменит историю закупок.
  Завершённые записи оставлены без изменения; новые проверки используют отдельный заказ.
- Admin catalog: «Цена для клиента» и «Ориентир закупки». Picker: read-only
  «Ориентир рынка» и ввод цены закупки за 1 единицу, без поля продажи клиенту.
  Сохранённая строка явно показывает quantity × unit price = total. Список закупки
  одноколоночный при любой ширине, раскрытие строки не удерживает соседние карточки.
  Формулы checkout, snapshots заказов и Prisma schema в этой правке не менялись.

## 2026-09-23: Автоматические волны и дежурные сотрудники

Уточняет решение 22 сентября: ручное формирование/назначение больше не является
частью happy path. Старые записи ниже описывают историю решений.

- Первый `confirmed`-заказ создаёт одну `open`-волну на delivery slot; следующие
  confirmed-заказы автоматически включаются в неё. Это одна Serializable-транзакция
  checkout под блокировкой слота; уникальный индекс delivery_slot_id и retries
  защищают от дублей. Checkout по-прежнему закрыт после начала сборки.
- `default_picker_id` и `default_courier_id` в app_settings задают дежурных.
  Используем только активных пользователей нужной роли. Пустое назначение
  автоматически заполняется, ручное назначение не заменяется. Настройки меняются
  через admin UI; сохранение также заполняет пустые назначения open/picking/picked-волн.
- Если дежурный отсутствует или деактивирован, заказ не теряется: волна создаётся
  без этого назначения, admin видит «Не назначен» и устраняет проблему. Никакого
  выбора случайного сотрудника или scheduler нет. Staff seed задаёт dev-дежурных
  только при отсутствии ключей настроек, не меняет существующие пароли/назначения.
- Picker по умолчанию видит «Предстоящие» (open), отдельно «В работе» (picking)
  и «Завершённые» (picked/out_for_delivery/delivered/cancelled). Эти вкладки
  фильтруются backend вместе с назначением и delivery date. История остаётся доступной.
- Warning требует реального actual purchase price, положительного закупленного
  количества и известного reference price. Пустые закупки и старые строки без
  ориентира не получают ложного warning. Процент считает backend через Decimal;
  сообщение называет направление и величину отклонения. Цена клиенту не меняется.
- Seed разделён на catalog, staff, checkout settings/slots и необязательный demo
  operations. Demo создаёт заказы через CheckoutService, не заполняя actual quantities
  и actual prices. Он не нужен для обычного запуска.
- `db:reset:operations --confirm` удаляет ВСЕ orders/order_items/waves/wave_items
  выбранной локальной dev-БД в транзакции, не только seed-строки (у старых данных нет
  надёжного признака происхождения). Каталог, staff, customers, settings и slots
  сохраняются. Запрещены production/staging, удалённая БД и запуск без подтверждения.
- Фильтр admin/orders применяется по deliverySlot.date, не createdAt. UI не
  показывает таблицу предыдущего запроса во время загрузки новых фильтров; смена
  даты сбрасывает выбранный слот и ограничивает список слотов этой датой.
- Проверка старой локальной БД: 3 confirmed-заказа без wave, одна старая назначенная
  wave в out_for_delivery. Закупки содержали, например, 43 кг огурцов по 232 сом/кг
  и 132 кг картофеля по 134 сом/кг. Старый seed-operations создавал только staff;
  точный автор этих сохранённых тестовых значений неизвестен, audit log отсутствует.

## 2026-09-22: Самостоятельная работа сборщика и курьера

Эта запись заменяет ручные подтверждения и передачу курьеру из решения 17 сентября.

- Успешный checkout создаёт `confirmed`. Цены, формулы и snapshots checkout не
  меняются. Если у слота уже есть `open`-волна, заказ сразу включается в неё и
  пересчитывается запрос закупки в той же Serializable-транзакции под блокировкой
  слота. После начала сборки новые заказы на слот по-прежнему запрещены.
- Admin формирует волну и назначает сборщика/курьера. Сборщик сам начинает сборку,
  закупает товары, выполняет «Разложить по заказам» и завершает сборку. Переход
  волны в `picked` одновременно переводит её активные заказы в `picked`.
- Курьер видит назначенную волну заранее как «Готовится». После `picked` сам
  нажимает «Забрал заказы»: волна и заказы становятся `out_for_delivery`.
  Последняя доставка автоматически завершает волну; получение наличных отмечается
  отдельно для каждого доставленного заказа. Обязательных admin-действий между
  этапами больше нет. Списки и страницы волн обновляются каждые 10 секунд.
  Если все заказы волны в пути отменены, она завершается как `cancelled`.
- Сборщику запрещено передавать `finalUnitPrice`, в том числе через прямой API.
  Цена клиенту берётся из snapshot заказа. Существующая исключительная корректировка
  финальной цены с обязательной заметкой остаётся только у admin, snapshot не меняет.
- В `wave_items.reference_purchase_price` сохраняется Decimal-ориентир каталога
  при первом включении товара в волну. Для старых закупок неизвестный ориентир
  остаётся `null`, а не заменяется сегодняшней ценой. Такая сохранённая закупка
  помечается для проверки. Никаких новых сущностей нет.
- `purchase_price_deviation_percent` хранится строкой в `app_settings`, по умолчанию
  `15.00`; admin меняет его через «Настройки» (0–100%, до двух десятичных знаков).
  Проверяется абсолютное отклонение в обе стороны, строго больше порога, через
  Decimal без округления процента. При нулевом ориентире любая ненулевая цена
  требует проверки. Флаг информационный: сборка и доставка не блокируются.
  Изменение порога обновляет флаг существующих закупок; журнал согласований не добавлен.
- Admin может переназначить сотрудников до завершения волны, в том числе курьера
  в пути (но нельзя убрать последнего курьера без замены). Неоплаченный заказ
  можно отменить до доставки. Возвраты оплаченных заказов не добавляются.
- Вкладки заказов: «Активные» (confirmed/picking/picked/out_for_delivery),
  «Завершённые» (delivered), «Отменённые» (cancelled). Старые draft/placed
  не переводятся автоматически и не входят в эти вкладки; при миграции таких
  заказов admin должен отдельно проверить их через API или сохранённый URL заказа.

## 2026-09-17: Admin orders, delivery waves и picking

- Одна волна на delivery slot закреплена уникальным ограничением БД. Администратор
  подтверждает placed-заказы, затем вручную формирует волну. Повторное формирование
  открытой волны добавляет новые confirmed-заказы, не перенося заказы из других волн.
  Для начатой/завершённой волны действие возвращает существующую волну без изменений.
- Перед началом сборки нужно подтвердить и включить либо отменить все оставшиеся
  placed/confirmed-заказы слота. После начала сборки checkout закрывается для этого
  слота. Проверка checkout и операции волны используют одну блокировку строки слота.
- Запросы собираются в wave_items по productId через Decimal. В каждой позиции
  сохраняются snapshots названия и единицы; предпочтения по качеству вычисляются из
  snapshot-меток order_items с отдельными суммами и числом уникальных заказов.
  Несовместимые единицы одного товара в разных заказах блокируют формирование.
- Закупленные количество, цена и примечание вводятся вручную. purchase_total считает
  backend. Ноль означает явно зафиксированную несостоявшуюся закупку; null означает,
  что закупка ещё не введена. Отмена заказа уменьшает запросы, но не удаляет закупку.
- Распределять можно только в статусе picking. Сумма распределения активным заказам
  не может превышать закупку. Уменьшить закупку ниже уже распределённого количества
  нельзя. Автоматического распределения веса и складских остатков нет.
- Клиентская final_unit_price по умолчанию берётся из saleUnitPriceSnapshot и не
  зависит от закупочной цены. Ручная корректировка цены требует примечания. Итог
  позиции округляется HALF_UP; total_final = сумма финальных позиций + snapshot
  доставки + сервисный сбор - скидка, минимум 0. До разрешения всех позиций итог null.
- removed/unavailable дают нулевую сумму позиции. Пустой по факту заказ следует
  отменить, а не передавать курьеру. Сборы автоматически не меняются при исключении
  отдельных товаров; минимальная сумма не перепроверяется после сборки.
- Замена допустима только на другой товар в той же единице измерения. Закупка товара
  замены сначала добавляется в волну и записывается. remove_item запрещает замену;
  contact_me требует заметки о согласовании. Цена по умолчанию остаётся исходной
  snapshot-ценой, явное изменение фиксируется с примечанием.
- Поток заказа: placed → confirmed → picking → picked → out_for_delivery → delivered.
  Для волны: open → picking → picked → out_for_delivery → delivered. До отправки
  возможна отмена; возвраты после доставки и отмена оплаченных заказов не реализованы.
  Переходы волны обновляют активные заказы в той же транзакции. Перед picked нужны
  закупки и все фактические данные; перед отправкой нужен курьер. Завершённые закупки
  и распределения неизменяемы. После delivered можно отметить наличные как paid.
- В выручку по товарам входят только позиции активных заказов, без доставки и сборов.
  Закупочная стоимость включает всю фактическую закупку волны, в том числе излишек.
  «Валовая маржа по товарам» = финальная товарная выручка - фактическая закупка.
  Незавершённые показатели имеют null, а не вводящий в заблуждение ноль.
- Staff auth: только сотрудники с активными `admin`, `picker` или `courier`
  могут войти по email и bcrypt hash пароля. JWT access token короткоживущий
  (10 минут), а refresh token ротируется, передаётся только в httpOnly
  `SameSite=Lax` cookie и хранится в PostgreSQL только как SHA-256 hash. Каждая
  проверка access token дополнительно читает сессию и актуальные роль/статус,
  поэтому logout, отзыв сессии и деактивация сотрудника действуют сразу.
- RBAC — намеренно простой. `admin` получает полный admin API. `picker` видит
  только назначенные волны/заказы и может выполнять закупку, распределение и
  переходы сборки. `courier` видит только назначенные доставки, не получает
  поля закупки/маржи и может отметить только delivered и payment paid. Проверка
  назначения выполняется backend, а не только интерфейсом.
- Для production обязательно задать случайный `STAFF_JWT_SECRET` не короче
  32 байтов. Dev seed с известными паролями запрещён при `NODE_ENV=production`;
  он сохраняет существующие hashes и не является способом управления персоналом.
- Миграция не объединяет и не удаляет старые волны автоматически. Если в существующей
  БД уже есть дубликаты на слот, их нужно разобрать до применения уникального индекса.

## 2026-09-17: Guest checkout и создание заказа

- Одна страница `/checkout`, без регистрации и OTP. Телефон нормализуется;
  девять цифр считаются местным номером +992. Совпадение телефона не является
  авторизацией: история заказов и сохранённые адреса гостю не выдаются.
- Существующий customer связывается по телефону, новый создаётся при необходимости.
  Профиль существующего пользователя не перезаписывается неподтверждёнными
  гостевыми данными. Имя и телефон заказа сохраняются в address snapshot.
- Backend повторно читает продукты и настройки. `observedPrice` нужен только
  для уведомлений об изменении цены; все доверенные суммы считает Prisma Decimal.
  Каждая позиция округляется до двух знаков HALF_UP, затем суммы складываются.
- `minimum_order_amount`, `delivery_fee`, `service_fee` хранятся в app_settings
  строками с десятичными значениями. Если настройки отсутствуют или некорректны,
  checkout недоступен. Минимум применяется к товарам, без стоимости доставки.
- Validate не резервирует слот. Create повторяет проверки в Serializable-транзакции,
  блокирует строку delivery_slots через FOR UPDATE и повторяет транзакцию при
  конфликте сериализации. Все заказы кроме cancelled занимают место.
- Слоты трактуются во времени Душанбе (UTC+05:00). Начиная с момента старта окно
  недоступно. API выдаёт активные окна ближайших семи дней, включая заполненные
  и уже начавшиеся с признаком available=false.
- reviewToken является отпечатком проверенных сервером данных. При изменении цены,
  суммы, предпочтения или времени окна create возвращает 409 и свежую проверку;
  пользователь подтверждает её заново. Токен не заменяет повторную валидацию.
- Для повторной отправки одного запроса используются уникальный checkoutRequestId
  и checkoutRequestHash в orders. Это предотвращает двойной заказ при повторном
  запросе после сетевого сбоя. Изменённое содержимое с прежним ключом отклоняется.
- Сохраняем snapshots адреса, контактов, названия, единицы, цены и предпочтения.
  finalQuantity/finalTotal остаются null до сборки. Оплата cash_on_delivery,
  статус pending. Предварительные суммы весовых товаров не являются финальными.
- Success-страница использует ответ create в памяти/sessionStorage текущей вкладки.
  Публичный поиск заказов по номеру/телефону не добавляется. Корзина очищается
  только после успешного ответа. Для просмотра в другом браузере позже нужна auth.
- Отдельный seed checkout добавляет настройки и окна, не изменяя существующий
  каталог. Admin orders API пока отсутствует; его реализация с авторизацией является
  следующим этапом. Волны доставки и сборка в этот этап не входят.

## 2026-09-17: Запросы frontend к API

- Браузер обращается к `/api/v1` на домене сайта. Next.js перенаправляет запросы
  к NestJS через rewrite; адрес backend задаётся серверной переменной `API_URL`
  с префиксом `/api/v1`, по умолчанию используется localhost и `API_PORT`.
- Это устраняет зависимость клиентской сборки от localhost и CORS при смене
  порта frontend. Контракты API и его правила доступа не меняются.
- Ошибки категорий и товаров отображаются отдельно с повторной загрузкой;
  вместо ответа API не подставляются тестовые данные.

## 2026-09-14: Стартовая архитектура MVP

- Используем монорепозиторий с `apps/web`, `apps/api` и `packages/shared`,
  потому что проект рассчитан на небольшую команду и общий TypeScript-контекст.
- Клиентскую корзину на MVP храним в браузере и отправляем на backend при
  checkout, чтобы не усложнять состояние до появления реальной потребности.
- Админка находится в том же Next.js-приложении по маршруту `/admin`, чтобы не
  поддерживать два frontend-проекта.
- Backend строится как один NestJS REST API, без микросервисов.
- Основная база данных - PostgreSQL.
- Delivery waves моделируются явно, потому что группировка заказов по окнам
  доставки является ключевым продуктовым решением.
- На момент первого архитектурного документа `docs/MVP.md` отсутствовал, поэтому
  стартовая архитектура опиралась на `docs/PRODUCT.md` и требования задачи.

## 2026-09-14: Уточнение архитектуры перед кодингом

- Для учета фактической закупки на рынке добавляем `wave_items`: агрегированную
  сущность товара внутри delivery wave с суммарно заказанным количеством,
  реально купленным количеством, фактической закупочной ценой и заметкой
  поставщика.
- Разделяем закупочную и продажную цену: у товара храним текущие
  `current_purchase_price` и `current_sale_price`, а в заказах сохраняем
  snapshot-цены на момент checkout.
- Для первого MVP разрешаем guest checkout: клиент оформляет заказ по имени,
  телефону и адресу без обязательного SMS OTP.
- Заказ хранит snapshot адреса доставки в JSONB, потому что сохраненный адрес
  клиента может измениться или быть удален после checkout.
- `is_active` и доступность на сегодня разделены: `is_active` означает наличие
  товара в каталоге, `is_available_today` означает возможность заказать товар
  сегодня.
- Для денег, веса и дробных количеств используем Prisma `Decimal` и PostgreSQL
  `NUMERIC`, без `float`.

## 2026-09-15: Клиентская корзина до checkout

- Корзина первого MVP хранится только на клиенте: React state синхронизируется
  с `localStorage`, backend cart entity не создается.
- `localStorage` используется только до появления checkout. При checkout backend
  обязан заново проверить `is_active`, `is_available_today`, `sellingPrice`,
  `minQuantity` и `quantityStep`.
- Цены и суммы во frontend-корзине являются предварительными UI-значениями и не
  считаются доверенными для backend.
- Для изменения количества во frontend используем scaled integer helpers, чтобы
  не опираться на небезопасную float-арифметику для `minQuantity` и
  `quantityStep`.
