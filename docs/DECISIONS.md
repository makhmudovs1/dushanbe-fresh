# Decisions

## 2026-09-14: Стартовая архитектура MVP

- Используем монорепозиторий с `apps/web`, `apps/api` и `packages/shared`,
  потому что проект рассчитан на небольшую команду и общий TypeScript-контекст.
- Клиентскую корзину на MVP храним в браузере и отправляем на backend при
  checkout, чтобы не усложнять состояние до появления реальной потребности.
- Админка находится в том же Next.js-приложении по маршруту `/admin`, чтобы не
  поддерживать два frontend-проекта.
- Backend строится как один NestJS REST API, без микросервисов.
- Основная база данных - PostgreSQL.
- Delivery waves моделируются явно, потому что группировка заказов по окнам
  доставки является ключевым продуктовым решением.
- На момент первого архитектурного документа `docs/MVP.md` отсутствовал, поэтому
  стартовая архитектура опиралась на `docs/PRODUCT.md` и требования задачи.

## 2026-09-14: Уточнение архитектуры перед кодингом

- Для учета фактической закупки на рынке добавляем `wave_items`: агрегированную
  сущность товара внутри delivery wave с суммарно заказанным количеством,
  реально купленным количеством, фактической закупочной ценой и заметкой
  поставщика.
- Разделяем закупочную и продажную цену: у товара храним текущие
  `current_purchase_price` и `current_sale_price`, а в заказах сохраняем
  snapshot-цены на момент checkout.
- Для первого MVP разрешаем guest checkout: клиент оформляет заказ по имени,
  телефону и адресу без обязательного SMS OTP.
- Заказ хранит snapshot адреса доставки в JSONB, потому что сохраненный адрес
  клиента может измениться или быть удален после checkout.
- `is_active` и доступность на сегодня разделены: `is_active` означает наличие
  товара в каталоге, `is_available_today` означает возможность заказать товар
  сегодня.
- Для денег, веса и дробных количеств используем Prisma `Decimal` и PostgreSQL
  `NUMERIC`, без `float`.
