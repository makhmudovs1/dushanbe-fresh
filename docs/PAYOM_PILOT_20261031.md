# Payom: Результат Реального Пилота

31 октября 2026, время ниже МСК. Production: TARENA, 77.95.0.94.
Это актуальное дополнение к прежним заметкам о подготовке SMS.

## Подтверждено

- Владелец разрешил максимум **3 платных запроса**, без автоматических повторов,
  исключительно на свой тестовый номер. Выполнено **2**, третий не использован.
- Endpoint: `https://gateway.payom.tj/api/message`, sender: `DFRESH`.
- Для одобренного шаблона редакторский `{code-1}` соответствует буквальному
  JSON-ключу **`code-1`** в `templateMessage.variables`. Владелец сохранил
  `CUSTOMER_SMS_CODE_VARIABLE=code-1` в закрытом production ENV.
- Первая отправка в 18:02:24: HTTP 201, корректный receipt,
  `SERVICE_ACCEPTED`, подстановка шестизначного OTP в ответе провайдера;
  владелец подтвердил получение настоящего кода на телефоне.
- Вторая отправка в 18:13:13 выполнена самим владельцем через обычный экран
  входа сайта. HTTP 201, корректная подстановка кода, sender совпадает с DFRESH.
  Владелец самостоятельно ввёл код на сайте, сохранил имя и увидел профиль.
- После добавления товаров и обновления страницы владелец подтвердил сохранение
  профиля и корзины. Обезличенная проверка БД в 18:21:05: одна действующая
  browser session, привязанный customer, три позиции корзины, одно избранное.
- Проверка баланса до отправок: HTTP 200, положительный документированный
  баланс. Точные суммы, телефон, template UUID, OTP и токен в отчёт не включены.

Финальный GET health/balance после теста также успешен, баланс положительный.
Встроенный preflight по-прежнему выводит `requires_provider_confirmation`
для approval/mapping: он намеренно не умеет читать шаблоны и не сохраняет
ручное подтверждение. Это ограничение этого read-only инструмента, не новый
блокер после фактической успешной подстановки и входа. Флаги в его отчёте
относятся к root ENV, а не к отдельным процессным настройкам пилота.

`SERVICE_ACCEPTED` подтверждает очередь, **не доставку**. Получение двух SMS и
успешный ввод второго кода подтверждены владельцем отдельно. Точный sender
дополнительно проверен по ответам API; отдельного подтверждения названия
отправителя на экране телефона пока нет. Списание и число оплаченных сегментов
нужно сверить в кабинете Payom: баланс до отправки не доказывает сумму списания.

потребовалось. UUID шаблона и токен известны только закрытому ENV.

## Что Сейчас Работает В Production

Основной `/etc/dushanbe-fresh/app.env` оставлен с:

```dotenv
CUSTOMER_SMS_URL=https://gateway.payom.tj/api/message
CUSTOMER_SMS_SENDER=DFRESH
CUSTOMER_SMS_CODE_VARIABLE=code-1
CUSTOMER_AUTH_ENABLED=false
MOBILE_CUSTOMER_API_ENABLED=false
CUSTOMER_REQUIRE_PHONE=false
```

Токен, одобренный UUID и новый OTP-secret находятся там же, без раскрытия.
Запущен временный `df-payom-ui-pilot-api` на **127.0.0.1:4012**, тот же проверенный
API image, тот же PostgreSQL `df_production`, без миграций и отдельной копии БД.
Только в процессе пилота разрешены Web/native auth endpoints, один согласованный
номер и одна заранее зарезервированная отправка для проверки через UI.
Все остальные номера блокируются существующим OTP-flow до вызова провайдера.
Этот слот уже израсходован: повторное нажатие не должно вызвать платную отправку.

Caddy направляет `/api/v1/*` в этот API; Web на 3000 и прежний API на 4000 не
останавливались. Reload через SIGUSR1 выполнен без изменения PID/StartedAt proxy.
SSR-каталог использует прежний API, но оба API работают с одной production БД.
TLS, Web, DB и гостевой checkout не переключались на старый VPS.

Операторские файлы: `ops/tarena/PayomPilotCaddyfile`, `activate-payom-pilot.py`,
`payom-ui-pilot.cjs`, `payom-template-probe.cjs`, `payom-probe.py`,
`payom-ui-audit.cjs`. Они не заменяют авторизацию: используют существующие
OTP/Payom/session services и добавляют только ограниченный операторский пилот.
Private recipient, ledger, receipt и расходованный слот находятся исключительно
в `/srv/dushanbe-fresh/state/payom-format-pilot-20261031` с закрытыми правами.
Не переносить этот каталог в Git и не выводить его содержимое в терминал.

## Проверки И Границы Результата

Реальный Web-flow: отправка, получение, ввод OTP, профиль, имя, обновление
страницы и сохранение корзины подтверждены. Native session через настоящий
Android/iOS в этом пилоте **не проверялась**; browser OTP нельзя повторно
использовать для независимого native-входа. Общие API и DB не означают, что
физические устройства уже прошли реальный вход.

Защиты проверяются локально с mock-SMS на отдельной синтетической PostgreSQL:
одноразовость при конкурентной проверке, exact origin, cooldown, 5 неверных
попыток, истечение OTP, запрет непосланных кодов и персистентный send budget.
Они не проверяются дополнительными платными SMS или изменением реальных OTP.
Результаты текущего запуска:

- 3 выбранных HTTP-теста существующего customer-account suite прошли на новой
  локальной `df_payom_test`; provider полностью замокан, 15 миграций применены
  только к этой изолированной БД. Проверены перечисленные выше защиты.
- 19 выбранных adapter-тестов прошли: точное имя переменной, отсутствие
  обязательных настроек, отказ от небезопасного/неподтверждённого ключа.
- 3 operator Node-теста прошли: обезличивание receipt, нераскрытый placeholder,
  безопасное извлечение validation fields.
- 2 operator Python-теста прошли: запрет четвёртой попытки и автоматического
  повтора при непроверенном/неизвестном исходе.
- Workspace lint, typecheck и сборка прошли; приложение не переписывалось.
- Финальные публичные GET сайта, API readiness и Web/native auth status:
  HTTP 200, PostgreSQL `ok`, `requiredForCheckout=false`. Pilot API работает
  без перезапусков; native status не заменяет реальный native-вход.

## Следующее Включение

1. Сверить отправителя на телефоне и списание/сегменты в кабинете Payom.
2. При необходимости согласовать использование оставшейся третьей SMS для
   реального native-входа. Не отправлять её автоматически и не сбрасывать slots.
3. Для общедоступного SMS-входа получить отдельное подтверждение владельца:
   это открывает платные запросы других покупателей. Сохранить глобальные,
   телефонные/IP-лимиты и `CUSTOMER_REQUIRE_PHONE=false`.
4. Выполнить контролируемую замену временного pilot API на обычный production
   API с новой конфигурацией и graceful routing. Не просто менять root ENV:
   текущий контейнер не перечитывает его, а pilot entrypoint специально требует
   выключенного массового auth. Текущие профили/сессии/корзины не удалять.
5. Не менять OTP-secret во время пилота: он участвует в ключах лимитов.
   Отдельный [план безопасной ротации](PRODUCTION_SECRET_ROTATION.md) подготовлен,
   но ротация секретов в рамках этой проверки не выполнялась.
