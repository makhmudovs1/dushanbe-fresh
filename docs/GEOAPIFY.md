# Geoapify: адреса Душанбе

## Подключение локально

Серверный ключ задаётся в `apps/web/.env.local` как `GEOAPIFY_API_KEY`.
Файл исключён из Git; реальное значение не добавляется в примеры, документацию
или отчёты. Next читает ENV из директории `apps/web`, а не автоматически из
корневого `.env`. Альтернатива: переменная окружения процесса Web.

Локальный Web: `corepack pnpm --filter @dushanbe-fresh/web dev`, обычно
`http://localhost:3000`. После изменения ключа перезапустите Web, если Next
не перечитал ENV автоматически. API/Prisma и перезапуск базы не требуются.

`GET /api/address-search` показывает только доступность, провайдера и рамку
поиска. Самого ключа и URL с ключом в JSON нет. Запросы браузера идут на
локальные POST `/api/address-search` и `/api/address-reverse`; вызовы Geoapify
выполняет сервер. Тексты поиска и координаты не помещаются в URL этих маршрутов.

## Ключи И Ограничения

- **`GEOAPIFY_API_KEY`**: только сервер, Autocomplete/Reverse Geocoding. Не
  переименовывать в `NEXT_PUBLIC_*` и не использовать для тайлов. Для будущего
  production ограничить исходящим публичным IP сервера. Для разработки лучше
  отдельный ключ с подходящим IP-ограничением: домашний динамический IP может
  меняться. Ограничения по referrer/origin не подходят серверным запросам,
  которые не отправляют браузерный Origin.
- **`NEXT_PUBLIC_GEOAPIFY_MAP_API_KEY`**: необязательный отдельный браузерный
  ключ тайлов. Он заведомо виден
  браузеру, поэтому разрешить только нужные HTTP referrers/origins. Примеры
  шаблонов Allowed HTTP referrers: `^https://dushanbefresh[.]tj(/.*)?$`;
  для отдельного dev-ключа `^http://(localhost|127[.]0[.]0[.]1):3000(/.*)?$`.
  Проверить шаблоны в кабинете; `www` и другие порты добавлять только если они
  реально используются. Если включать Allowed origins, указывать точные origins,
  например `https://dushanbefresh.tj` или `http://localhost:3000`.
- CORS-настройка сама по себе не защищает ключ от чужих запросов. Разные ключи
  одного проекта используют общую квоту. Контролировать расход в кабинете.

Рекомендации по ограничениям подтверждены в [Geoapify API keys help](https://myprojects.geoapify.com/help/api-keys/).
Ни один ключ не создаётся и ограничения не меняются автоматически в кабинете.
Для подробного выбора дома выбран светлый `osm-bright` с начальным масштабом 17.
Прежний спокойный стиль доступен через `NEXT_PUBLIC_GEOAPIFY_MAP_STYLE=positron`
и пересборку Web. Публичный ключ
также встраивается при сборке, одного runtime-рестарта для его замены недостаточно.
Пока браузерный ключ не задан, сохраняется существующая OSM-подложка Leaflet;
поиск и reverse Geoapify при этом работают. Существующие `NEXT_PUBLIC_MAP_TILE_URL`
и `NEXT_PUBLIC_MAP_ATTRIBUTION` остаются fallback-конфигурацией.

Для будущего production также нужен правильный `WEB_ORIGIN` с HTTPS. Проверка
origin защищает оба серверных маршрута. Первоначальный запрет production отменён
последующим явным разрешением владельца; результат релиза фиксируется отдельно.

## Логика

- Если задан серверный Geoapify-ключ, он приоритетнее старого
  `ADDRESS_SEARCH_URL`-адаптера. Без Geoapify-ключа старый адаптер и ручной ввод
  сохраняются. SKU, аккаунты или сессии не меняются.
- Автоподсказки: debounce 350 мс, 3–150 символов, до 6 результатов, язык `ru`
  или `tg`. Фильтр `countrycode:tj|rect:...` объединяет страну и рамку поиска;
  дополнительно проверяются страна, название Душанбе и числовые координаты.
  Улица без номера дома допустима; номер не выдумывается. В autocomplete принимаются
  адресные результаты street/building: парк или магазин, совпавший по названию,
  не маскируется под адрес другой улицы.
  Если таджикское написание не даёт адресов, выполняется один дополнительный
  запрос с нормализацией букв (например Рӯдакӣ → Рудаки), сохраняя `lang=tg`.
  Запросы без номера ищут `type=street`; запросы с номером сначала ищут полный
  адрес и при отсутствии дома могут вернуть реальную улицу для ручного уточнения.
  Это настоящие результаты провайдера, а не выдуманные подсказки; такой fallback
  может расходовать два запроса Geoapify на один поиск.
- `ADDRESS_SEARCH_BOUNDS` сохраняет прежнюю конфигурацию `[west,south,east,north]`.
  По умолчанию `[68.65,38.45,68.90,38.68]`. Это приблизительная рамка, **не точный
  административный или тарифный полигон доставки**. Рамка ограничивает только
  поиск подсказок, не перемещение карты, GPS или reverse. Пространственное
  ограничение теперь настраивается отдельно: [DELIVERY_ZONE.md](DELIVERY_ZONE.md).
- Один экран поиска и карты: dropdown поверх карты, переход к компактным деталям
  единственной нижней кнопкой. Нет отдельных экранов выбора центра и применения
  reverse. На mobile поиск не получает автоматический фокус.
- Метка закреплена в центре, перемещается карта. Клик также переносит центр.
  GPS вызывается только кнопкой. Ошибка/отказ GPS не блокирует ручной ввод.
  Поздний ответ GPS не заменяет новый поиск, ручную точку или закрытый экран.
- Reverse: debounce 400 мс после остановки карты; улица/дом заполняются автоматически.
  Выбранная точка/вход не заменяется координатами ближайшего здания. Ручное
  уточнение улицы/дома теперь сохраняет точку по явному требованию владельца.
  Начало нового поиска отменяет ожидающий reverse и старые подсказки.
- Leaflet отслеживает размер контейнера при изменении viewport. Подложка при
  отсутствии публичного ключа не заменяется фиктивной картой. Ошибка тайлов или
  отсутствие улицы у провайдера оставляет доступным ручной адрес.
- Гостевой адрес/координаты сохраняются существующим sessionStorage-механизмом
  и draft checkout. Гостевой список с метками Дом/Работа/Другое также хранится в
  sessionStorage (до 20 адресов, 24 часа), не отправляется в БД. Аккаунт использует
  существующие POST/PATCH/DELETE адресов; редактирование сохраняет id. В заказ
  попадает прежний снимок адреса с координатами. Старые заказы не переписываются.
- Курьер видит координаты и ссылку Google Maps с `destination=latitude,longitude`,
  без отдельного платного routing API. Старый адрес без координат читается как
  раньше, но ссылки на выдуманную точку не получает. Интерфейс сотрудников,
  как и прежде, русскоязычный; клиентский адресный flow поддерживает RU/TJ.

Документация протокола: [Autocomplete](https://apidocs.geoapify.com/docs/geocoding/address-autocomplete/),
[Reverse](https://apidocs.geoapify.com/docs/geocoding/reverse-geocoding/),
[Map tiles](https://apidocs.geoapify.com/docs/maps/map-tiles/).

## Ошибки И Безопасность

- Таймаут провайдера 4 секунды, abort при отмене, запрет redirect, ограниченный
  размер JSON, проверка схемы ответа. 401/403/429/5xx, повреждённый JSON и сетевые
  ошибки дают обезличенный `unavailable` без текста провайдера, URL или ключа.
- Общий per-process лимит двух маршрутов: 60 запросов/минуту, до 4 одновременно.
  Клиентские IP и адреса для лимитера не сохраняются. Для нескольких процессов
  и защиты публичного сервиса при production-настройке нужен общий/edge limiter;
  локальный лимит не обещает соблюдения дневной квоты проекта.
- Не включать upstream URL в APM/fetch-логи без удаления параметра `apiKey`:
  Geoapify передаёт ключ в query string своего серверного запроса.
- Browser-тесты используют фиктивные адреса/служебную сессию и моки API, не
  создают реальных заказов, не вызывают SMS и не изменяют production-данные.
