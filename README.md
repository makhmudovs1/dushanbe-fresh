# Dushanbe Fresh

Основа MVP сервиса доставки свежих продуктов с местных рынков Душанбе.

## Технологии

- Монорепозиторий на pnpm
- Next.js + TypeScript в `apps/web`
- NestJS + TypeScript в `apps/api`
- Общий пакет TypeScript в `packages/shared`
- PostgreSQL
- Prisma
- Docker Compose для локального PostgreSQL

Реализованы просмотр и управление каталогом, корзина в браузере, оформление
заказа без регистрации, вход сотрудников, разграничение доступа по ролям,
волны доставки, закупка и упаковка заказов. Вход клиентов по SMS, онлайн-оплата
и автоматическое построение маршрутов пока не реализованы.

## Требования

- Node.js версии 18.17 или новее (для обработки изображений sharp)
- Docker Desktop или служба Docker
- Corepack

Версия pnpm закреплена в `packageManager`, поэтому устанавливать pnpm глобально
не требуется.

## Локальный запуск

Установите зависимости:

```bash
corepack pnpm install
```

Сгенерируйте Prisma Client:

```bash
corepack pnpm db:generate
```

Запустите проект локально:

```bash
corepack pnpm dev
```

Эта команда запускает PostgreSQL через Docker Compose, а также:

- веб-приложение по адресу `http://localhost:3000`;
- API по адресу `http://localhost:4000`.

Браузер отправляет запросы на `/api/v1` по тому же адресу, с которого открыт сайт.
Next.js перенаправляет их на `http://localhost:4000/api/v1` (или порт из `API_PORT`).
Это позволяет избежать ошибок междоменных запросов при открытии сайта на другом
порту или с телефона. Если API размещён отдельно, задайте серверную переменную
`API_URL`, включая `/api/v1`, при запуске или сборке Next.js.
`NEXT_PUBLIC_API_URL` больше не используется. После изменения настроек
проксирования перезапустите Next.js.

Пример запуска на других портах:

```bash
WEB_PORT=3001 API_PORT=4001 corepack pnpm dev
```

В одной рабочей копии репозитория запускайте только один процесс Next.js:
одновременные экземпляры используют общую папку `.next` и могут перезаписывать
результаты сборки друг друга. Перед `build:web` остановите сервер разработки,
а после сборки запустите его снова. Задавайте переменные в оболочке или сохраняйте
настройки Next.js в `apps/web/.env.local`. Корневой `.env.example` служит образцом,
а не автоматически загружаемой конфигурацией для всех пакетов монорепозитория.

Проверка работоспособности API:

```bash
curl http://localhost:4000/api/v1/health
```

Админ-панель:

```text
http://localhost:3000/admin
```

Каталог:

```text
http://localhost:3000/catalog
```

Пример страницы товара:

```text
http://localhost:3000/products/tomatoes
```

Корзина:

```text
http://localhost:3000/cart
```

Корзина хранится в `localStorage` браузера. При оформлении заказа сервер заново
читает из PostgreSQL доступность товаров, цены и правила количества. Цены в
корзине предварительные и используются только для отображения. После успешного
создания заказа корзина очищается.

Оформление заказа: `http://localhost:3000/checkout`.

## Как дать доступ к локальному MVP

Для временной демонстрации используем **ngrok**: один публичный HTTPS-адрес
ведёт на Next.js, а `/api/v1` проксируется к локальному API. Порт 4000 и
PostgreSQL отдельно не публикуются. Это не развёртывание в production.

### Подготовка один раз

Установите ngrok на Mac и добавьте токен из своего аккаунта
[ngrok](https://dashboard.ngrok.com/get-started/your-authtoken):

```bash
brew install ngrok
ngrok config add-authtoken ВАШ_ТОКЕН
ngrok config check
```

Токен хранится в локальной конфигурации ngrok, не в репозитории. Не присылайте
его в чат и не добавляйте в `.env.example`. Если сервис сообщает `ERR_NGROK_121`
об устаревшем клиенте, выполните `ngrok update`.
Зависимости, миграции и тестовые данные приложения должны быть подготовлены
по разделам выше; повторно заполнять каталог перед каждым показом не нужно.

### Каждый запуск

1. Запустите Docker Desktop. Если `pnpm dev` уже работает, остановите его
   через `Ctrl+C`: API нужно перезапустить с публичным Origin.
2. В первом терминале из корня проекта запустите:

```bash
corepack pnpm dev:share
```

Эта команда запускает **только туннель**, не приложение. Оставьте терминал открытым.
В строке `Forwarding` появится адрес вида `https://ваш-домен.ngrok-free.app`.
До запуска приложения ngrok может показывать ошибку соединения с локальным сервером.
Инспекция содержимого запросов отключена флагом `--inspect=false`.

3. Во втором терминале запустите приложение, подставив полученный адрес
   **без завершающего `/` и без пути**:

```bash
WEB_ORIGIN="https://ваш-домен.ngrok-free.app" STAFF_COOKIE_SECURE=true corepack pnpm dev
```

Корневой `.env` автоматически не читается: в этой команде переменные передаются
непосредственно процессам. Не меняйте `NODE_ENV` на `production` ради туннеля.
`API_URL` остаётся локальным: по умолчанию `http://localhost:4000/api/v1`.
Для другого порта веб-приложения задайте одинаковый `WEB_PORT` в обоих терминалах.
Если публичный адрес изменился, перезапустите приложение с новым `WEB_ORIGIN`.

4. Отправьте другу только публичную HTTPS-ссылку. По ней доступны `/`, `/catalog`,
   `/cart`, `/checkout` и `/admin/login`. Вход всех сотрудников находится на
   `/admin/login`; тестовые учётные данные перечислены в разделе ручной проверки.
   На бесплатном тарифе ngrok перед сайтом может появиться страница с кнопкой
   `Visit Site`. Предупредите друга об этом.

### Проверка с телефона

- Откройте ссылку через мобильный интернет, загрузите каталог, добавьте товары
  в корзину и оформите тестовый заказ на доступное окно.
- Войдите администратором, перезагрузите страницу: сессия должна восстановиться.
  Выйдите и убедитесь, что закрытые разделы снова требуют входа. Повторите
  для сборщика и курьера, используя отдельные профили либо выход между ролями.
- При `403 Недопустимый Origin` проверьте точное совпадение `WEB_ORIGIN` с адресом
  в браузере и перезапустите API. Не отключайте проверку Origin и не ставьте `*`.
- Проверяйте вход именно через HTTPS-ссылку, не через localhost: при такой
  конфигурации авторизация с локальным Origin намеренно отклоняется.

Cookie продления остаётся `HttpOnly`, `SameSite=Lax`, без `Domain`, с путём
`/api/v1/auth`. `STAFF_COOKIE_SECURE=true` включает `Secure` и имя
`__Secure-df_refresh` также в режиме разработки. При выходе удаляется эта же
cookie; ротация токена сохраняется. В production `Secure` нельзя отключить
этой переменной. Браузер обращается к API на том же домене, поэтому междоменный
доступ ему не нужен; разрешённый CORS Origin API также берётся из `WEB_ORIGIN`.
Прокси не переписывает Origin, а переходы сотрудников остаются относительными.

### Остановка и ограничения

- `Ctrl+C` в терминале `dev:share` закрывает публичный доступ. `Ctrl+C` во втором
  терминале останавливает приложение. Для обычной локальной работы снова
  запустите `corepack pnpm dev` без переменных демо.
- Mac, сеть, Docker, приложение и туннель должны оставаться включёнными.
  Сон Mac или разрыв сети прервут доступ. Стабильность бесплатного туннеля
  не гарантируется; это не круглосуточный сервер.
- Не распространяйте ссылку широко. Она сама по себе не является паролем.
  Используйте только тестовые данные: заказы друга сохраняются в вашей локальной БД,
  а ngrok является внешним посредником HTTPS-трафика.
- Известные dev-пароли и секрет по умолчанию **нельзя использовать в публичном
  production**. Для этого короткого демо остаются существующие проверки ролей,
  назначения сотрудников и Origin; полноценная защита production сюда не входит.
- На бесплатном тарифе есть ограничения трафика и запросов; актуальные значения
  приведены в [документации ngrok](https://ngrok.com/docs/pricing-limits/free-plan-limits).
  Опросы страниц сотрудников также расходуют лимит.
- Не запускайте сборку web одновременно с сервером разработки: они используют
  общую `.next`. Перед сборкой остановите приложение, затем запустите заново.

## База данных

Адрес локальной БД по умолчанию:

```text
postgresql://dushanbe_fresh:dushanbe_fresh@localhost:5432/dushanbe_fresh?schema=public
```

Примените миграции в среде разработки:

```bash
corepack pnpm db:migrate
```

Заполните локальный каталог тестовыми данными:

```bash
corepack pnpm db:seed
```

После применения миграций подготовьте настройки оформления заказа и окна доставки:

```bash
corepack pnpm db:deploy
corepack pnpm db:seed:checkout
```

Скрипт начального заполнения добавляет отсутствующие настройки
(`minimum_order_amount = "120.00"`, `delivery_fee = "20.00"`, `service_fee = "0.00"`)
и окна на 10:00, 14:00 и 18:00 на семь дней, каждое вместимостью 10 заказов.
Время местное, по Душанбе (UTC+05). Существующие настройки, вместимость и
доступность окон, а также заказы сохраняются. Повторный ручной запуск для новых
дат больше не нужен: API пополняет расписание автоматически. В отличие от заполнения каталога, скрипт не сбрасывает товары
и предпочтения по качеству. Денежные настройки хранятся строками JSON, не числами.

Каждый день действуют одинаковые окна **10:00–12:00, 14:00–16:00, 18:00–20:00**
по Душанбе. При запуске API и при запросе списка окон (checkout или админка)
добавляются только недостающие окна на сегодня и следующие шесть дней.
После смены даты они пополнятся при следующем запросе, без перезапуска или cron.
Расписание, горизонт и вместимость новых окон заданы в
`apps/api/src/delivery-slots/delivery-schedule.ts` (`deliverySchedule`).
Существующие окна, их вместимость, отключения и связанные волны/заказы не меняются;
история не удаляется. Параллельные автопополнения не создают дублей.
Правила закрытия по времени, вместимости и начатой сборке остаются прежними.

В новой рабочей копии репозитория перед первым `dev` выполните `db:generate`,
`db:deploy`, `db:seed`, `db:seed:checkout` и `db:seed:staff`.
Не используйте `prisma db push` при обычной разработке: источником истины являются
миграции. Если старая локальная БД была создана через `db push`, сначала сравните
её схему с начальной миграцией и только затем отметьте миграцию применённой через
`prisma migrate resolve --applied 20260914000000_init`.
Не очищайте заполненную БД только ради инициализации истории миграций.

Применение миграций в развёрнутых окружениях:

```bash
corepack pnpm db:deploy
```

При необходимости переопределите `DATABASE_URL`:

```bash
DATABASE_URL="postgresql://user:password@host:5432/database?schema=public" corepack pnpm db:deploy
```

## Маршруты API

Публичный каталог:

```text
GET /api/v1/categories
GET /api/v1/products
GET /api/v1/products?category=vegetables
GET /api/v1/products?search=помидоры
GET /api/v1/products/:slug
```

Оформление заказа без регистрации:

```text
GET  /api/v1/delivery-slots
POST /api/v1/checkout/validate
POST /api/v1/checkout/orders
```

`validate` принимает `{ items, deliverySlotId }`. Каждая позиция содержит
`productId`, `quantity` (десятичная строка), `qualityOptionId` (допускает null)
и необязательный `observedPrice` (только для уведомления об изменении цены).
Переданные клиентской частью названия, цены, суммы и поля оплаты не определяют
значения, сохраняемые сервером.

Ответ содержит актуальные позиции, ошибки и предупреждения по каждой из них,
`itemsSubtotal`, `deliveryFee`, `serviceFee`, `totalEstimated`, `minimumOrderAmount`,
`minimumOrderShortfall`, `valid` и `reviewToken`. Деньги передаются десятичными
строками. Итог каждой позиции округляется до двух знаков через Decimal HALF_UP.

`orders` дополнительно требует `name`, `phone`, `address` (street/building
обязательны, apartment/entrance/floor/instructions необязательны),
`substitutionPolicy`, подтверждённый `reviewToken` и `requestId` в формате UUID v4.
Правила замены: `replace_similar`, `contact_me`, `remove_item`.
К местным девятизначным номерам телефона добавляется префикс +992.

Предварительная проверка не резервирует место в окне и не гарантирует создание
заказа. При создании все проверки повторяются в транзакции Serializable с
блокировкой окна. Отменённые заказы не занимают места; все остальные занимают.
Изменение цен, сборов, данных товаров или времени доставки возвращает HTTP 409
с новым `quote`: клиент должен проверить и подтвердить данные заново.
Некорректные поля запроса возвращают 400; отсутствующие или некорректные ценовые
настройки возвращают 503. Одинаковые повторные запросы с тем же `requestId`
возвращают исходный заказ; повторное использование ключа с другими данными отклоняется.

Для заказов используются `cash_on_delivery` / `pending`. Имя и телефон контакта
сохраняются вместе с адресом в `deliveryAddressSnapshot`; название товара, единица,
количество, продажная цена и предпочтение по качеству копируются в позиции заказа.
Финальные количества и суммы остаются null до сборки. Предварительная стоимость
весовых товаров не является окончательным счётом.

Страница успешного оформления `/orders/[orderNumber]/success` использует только
ответ создания заказа, сохранённый в памяти и `sessionStorage` текущей вкладки.
Публичного поиска заказа по номеру, телефону или идентификатору клиента нет.
Совпадение телефона гостя не является аутентификацией и не открывает доступ
к предыдущим заказам или сохранённым адресам.

### Отслеживание заказа без регистрации

После оформления нажмите **«Отслеживать заказ»**. Ссылка имеет вид
`/order/<publicTrackingToken>` на том же сайте, в том числе через публичный HTTPS-туннель.
Она открывается в другом браузере без входа. В шапке **«Мой заказ»** ведёт к последнему
заказу, оформленному на этом устройстве: в `localStorage` хранится только его случайный
токен, не история заказов. Неизвестная ссылка показывает «Заказ не найден»;
очищается только соответствующий сохранённый токен, не более новый заказ.

- API: `GET /api/v1/public/orders/:trackingToken`, только чтение, без авторизации сотрудников.
  Браузер обращается по относительному пути с `credentials: same-origin`: это сохраняет
  техническую cookie подтверждения посещения ngrok, но не требует staff-сессии.
- Статус, окно и адрес без телефона, состав, текущая стоимость, корректировки и
  повторная доставка обновляются каждые 20 секунд без перезагрузки страницы.
- При сбое сети последние данные остаются на экране; доступна кнопка «Попробовать снова».
  При ошибке самой первой загрузки вместо skeleton появляется «Не удалось загрузить заказ».
- Все деньги рассчитывает API тем же финансовым калькулятором, что и внутренние операции.
  Корректировки показываются отдельно от исходных товаров/сборов, поэтому не вычитаются дважды.
  Оплаченная замена бесплатна; неоплаченные товары замены показаны отдельной суммой без повторных сборов.
- Закупочные цены, телефоны, заметки сотрудников, внутренние идентификаторы, ответственность,
  риск клиента, касса и журнал не входят в публичный DTO.
- Ссылка приватная: любой её обладатель видит заказ и адрес. Не публикуйте её в чатах
  общего доступа. Страница закрыта от индексации, ответы не кешируются, Referer не передаётся.

На существующей БД выполните `corepack pnpm db:deploy`, затем `corepack pnpm db:generate`
и перезапустите API/web. Миграция автоматически заполнит токены старых заказов;
сбрасывать БД и повторять seed не нужно. Старый чек в `sessionStorage` не получит
ссылку задним числом; для старых заказов автоматическая рассылка ссылок не реализована.

Ручная проверка:
1. Оформите заказ, откройте отслеживание и ту же ссылку в приватном окне браузера.
2. Проведите заказ через интерфейс сотрудника: начать сборку → упаковать → завершить
   сборку → забрать → доставить. На клиентской странице дождитесь следующего опроса.
3. Для другого заказа оформите частичный отказ через «Проблема при доставке».
   Проверьте текущую сумму и корректировки без внутренних примечаний.
4. Создайте замену с новым окном: появится отдельный блок «Повторная доставка».
5. Отключите сеть: данные не должны исчезнуть. Включите сеть и нажмите повторную попытку.

Ограничения: токен пока бессрочный, отзыва/перевыпуска ссылки в UI нет. Ограничитель API
локальный для процесса (300 запросов/минуту на транспортный IP); за frontend proxy
клиенты могут делить этот лимит. Для нескольких инстансов нужен лимит на доверенном
reverse proxy. В боевом окружении исключите токены и полные URL отслеживания из
access-логов/аналитики; не подключайте к странице сторонние трекеры.

Проверено 5 октября 2026: 233 теста (174 API, 58 web, 1 shared), lint, typecheck,
сборки web/API и Prisma validate. Через публичный HTTPS в Chrome пройдены оформление
и все этапы до доставки без перезагрузки tracking page, частичный отказ, повторная
доставка, вход по ссылке без cookies, ошибка сети с повторной попыткой и медленный
ответ API со skeleton. Проверены 375/768/1440 px и длинный адрес. Изолированные данные
проверки удалены; существующие заказы сохранены.

### Проверка загрузки на медленной сети

На `/`, `/catalog`, `/products/[slug]`, `/cart` и `/checkout` начальная разметка
содержит шапку, доступную статическую часть и skeletons без ожидания клиентских
запросов. Категории и товары загружаются независимо. Корзина не показывается
пустой до чтения localStorage. В оформлении отдельно загружаются окна доставки
и проверка суммы; поля контактов остаются доступны во время запросов.

Для ручной проверки в DevTools включите Network → Disable cache и Slow 4G,
затем перезагрузите каждую страницу по публичной HTTPS-ссылке. Сначала добавьте
товар в корзину, чтобы проверить восстановление непустого состояния. При выборе
окна должен появиться skeleton суммы, а подтверждение заказа оставаться
недоступным до ответа сервера. Проверьте также повторную загрузку после ошибки
API и быстрое переключение категорий: запоздалый ответ не должен заменять
товары последней выбранной категории.

Изображения в списках и корзине загружаются lazy с асинхронным декодированием;
основное фото товара загружается сразу, но не блокирует остальную карточку.
Размер места под фото фиксирован. При отсутствии или ошибке изображения показывается
единая нейтральная картинка. Старые фиктивные пути `/img/products/*.jpg` считаются
отсутствующим фото; новый seed не создаёт их и не перезаписывает реальные фотографии.
Искусственных задержек в приложении нет. Skeleton не может появиться раньше
первого HTML-ответа: DNS/TLS, страница `Visit Site` ngrok и холодная компиляция
Next.js в режиме разработки находятся до этой границы.

## Работа сотрудников

После применения миграций создайте сотрудников для локальной разработки:

```bash
corepack pnpm db:generate
corepack pnpm db:deploy
corepack pnpm db:seed:staff
```

Скрипт создаёт по одному активному администратору, сборщику и курьеру, сохраняя
только хеши паролей; запуск в боевом окружении запрещён. Существующие хеши паролей
не меняются. Учётные данные для разработки приведены ниже. При первом создании
пароли можно переопределить через `DEV_ADMIN_PASSWORD`, `DEV_PICKER_PASSWORD`
и `DEV_COURIER_PASSWORD`; длина должна составлять 12–72 байта в UTF-8.

Также создаются отсутствующие настройки `default_picker_id` / `default_courier_id`.
Существующие значения сохраняются. Администратор меняет дежурных в `/admin/settings`.
При оформлении заказа на свободные назначения волны автоматически ставятся активные
сотрудники соответствующих ролей. Если дежурный не задан или некорректен, заказ
и волна всё равно создаются, а администратор должен назначить сотрудника.
Существующие ручные назначения не заменяются.

Страницы:

```text
/admin/orders
/admin/orders/:id
/admin/delivery-waves
/admin/delivery-waves/:id
/admin/login
/admin/settings/staff
```

Список заказов фильтруется по дате доставки, окну и статусу. Карточка заказа
использует сохранённые при оформлении контакты и адрес, показывает предварительные
и финальные суммы, позволяет упаковать заказ одной кнопкой и вручную внести
исключения. В карточке волны есть вкладки закупки, упаковки и доставки.
Формы закупки адаптированы для телефона; количества и цены вводятся десятичными строками.

Маршруты (префикс `/api/v1/admin`):

```text
GET   /orders?tab=active|completed|cancelled&date=YYYY-MM-DD&deliverySlotId=...&status=...
GET   /orders/:id
PATCH /orders/:id/status                     { status }
PATCH /orders/:id/items/:itemId               { status, finalQuantity, finalUnitPrice?, replacementProductId?, pickerNote? }
POST  /orders/:id/paid
GET   /delivery-slots?date=YYYY-MM-DD
GET   /staff
POST  /staff                                { name, email, password, roles, confirmAdmin? }
PATCH /staff/:id                            { name?, roles?, status?, confirmAdmin? }
POST  /staff/:id/password                   { password }
GET   /delivery-waves?date=YYYY-MM-DD&tab=upcoming|working|completed
POST  /delivery-waves                        { deliverySlotId }
GET   /delivery-waves/:id
PATCH /delivery-waves/:id/assignments         { pickerUserId?, courierUserId? }
PATCH /delivery-waves/:id/status             { status }
POST  /delivery-waves/:id/items              { productId }
PATCH /delivery-waves/:id/items/:itemId       { purchasedQuantity, purchaseUnitPrice, supplierNote? }
GET   /settings
PATCH /settings/purchase-price-deviation     { value: "15.00" }
PATCH /settings/default-staff                { pickerUserId?, courierUserId? }
```

Полный процесс: оформление автоматически подтверждает прошедшие проверку заказы,
при необходимости создаёт волну окна и назначает дежурных сборщика и курьера.
Сборщик начинает сборку, фиксирует закупку, упаковывает заказы как заказано
(вручную меняя только исключения) и завершает волну (`picked`). Назначенный курьер
сначала видит «Готовится», затем готовые заказы, нажимает «Забрал заказы»
(`out_for_delivery`), отмечает доставку и получение наличных.
Волна завершается автоматически после доставки последнего активного заказа.
Передача через администратора не требуется. Все старые заказы в placed/confirmed
для этого окна должны быть включены или отменены до начала сборки. После начала
сборки окно закрывается для новых заказов, в том числе при финальной проверке
оформления в транзакции.

Новые заказы создают волну окна или присоединяются к открытой под той же
блокировкой окна. PostgreSQL гарантирует одну волну на окно. Повторное формирование
открытой волны добавляет только непривязанные подтверждённые заказы и обновляет
потребность в товарах; существующие данные закупки сохраняются. Для начатой или
завершённой волны возвращаются неизменённые данные. Изменения выполняются
в транзакциях Serializable с блокировкой окна и повторными попытками при конфликтах.

Суммы закупки и клиентских позиций рассчитывает сервер через Decimal с округлением
HALF_UP. Передача `purchaseTotal` или `finalTotal` не влияет на расчёт.
Упаковать больше закупленного количества нельзя. Цена клиенту по умолчанию берётся
из зафиксированной в заказе продажной цены. Запросы сборщика с `finalUnitPrice`
отклоняются; исключительная корректировка администратором требует примечания
и не меняет исходные данные заказа. `totalFinal` остаётся null до обработки всех
позиций, затем включает исходные стоимость доставки, сервисный сбор и скидку.
Удалённые и недоступные позиции имеют нулевой итог. Полностью невыполненный заказ
следует отменить, а не отправлять клиенту.

Замена должна использовать ту же единицу измерения, соответствовать выбранному
клиентом правилу и иметь сохранённую закупку в волне. При `contact_me` согласование
с клиентом фиксируется в примечании сборщика; `remove_item` запрещает замену.
Пересчёт единиц веса и автоматическое распределение излишка не реализованы.

Показатели волны учитывают выручку только от товаров. Валовая маржа равна финальной
выручке по товарам за вычетом всей фактической закупки, включая излишек. Доставка,
сервисные сборы, зарплаты, расходы на курьера и прочие операционные расходы
не учитываются. Незавершённые показатели закупки, выручки и маржи имеют значение
null. В интерфейсе используется название «Валовая маржа по товарам».

Доставленные заказы нельзя вернуть в сборку сменой статуса. После сборки данные
закупки и упаковки неизменяемы; завершённые волны сохраняют историю закупок.
Обычная доставка завершается действием «Доставлен и получено X сомони» с записью
наличных. Исключения оформляются отдельно, без изменения исходных сумм заказа.

Каждая новая позиция волны фиксирует `referencePurchasePrice` из каталога.
Сервер отмечает абсолютное отклонение закупочной цены, строго превышающее
`purchase_price_deviation_percent` (по умолчанию "15.00", администратор меняет
порог в настройках). Предупреждения не блокируют сборку и отправку. Пустые закупки,
нулевые количества и старые строки с неизвестным ориентиром предупреждений не дают.
Сообщение содержит фактическое отклонение, например: «Цена закупки выше ориентира
на 18%. Нужна проверка администратора». Отдельный процесс согласования закупки
пока не реализован; операционные и финансовые действия журналируются.
Администратор может переназначать сотрудников, включая курьера в пути.
После передачи курьеру вместо обычной отмены используется «Проблема при доставке».
Страницы сотрудников опрашивают сервер каждые 10 секунд.

Операционные маршруты и управление каталогом требуют действительный токен доступа
сотрудника. JWT-токен доступа живёт 10 минут; обновляемый при использовании токен
продления хранится в PostgreSQL только как хеш SHA-256 и передаётся в httpOnly
cookie с `SameSite=Lax` (`Secure` в боевом окружении). В боевом окружении задайте
случайный `STAFF_JWT_SECRET` длиной не менее 32 байтов.
Клиентский каталог и оформление заказа остаются публичными.

Миграция операционного модуля добавляет уникальный индекс связи волны с окном,
индекс связи заказа с волной и копии названия и единицы товара в позиции волны.
Для существующих позиций эти данные заполняются из товаров. Дубликаты волн нужно
разобрать вручную до миграции; история закупок при миграции не удаляется.

Интеграционные тесты охватывают три клиентских заказа, конкурентное формирование
волны, агрегацию предпочтений, расчёты закупки и упаковки, защиту от превышения
закупленного количества, замены, отмену, доставку, оплату и неизменяемость
завершённой закупки. Файлы тестов с БД выполняются последовательно из-за общих
настроек; конкурентные запросы проверяются явно внутри отдельных наборов тестов.

Не реализованы: построение маршрутов, работа с несколькими рынками, складской учёт,
отслеживание курьеров, онлайн-оплата и отдельное приложение сборщика.

## Как проверить MVP вручную

### Проблемы доставки, клиенты и наличные

Полные правила, API и ограничения: [Расчёты при доставке](docs/DELIVERY_FINANCE.md).
Перед первым запуском обновления выполните `corepack pnpm db:generate` и
`corepack pnpm db:deploy`; старые заказы сохраняются. Обычные seed-команды
не создают проблемных заказов или фиктивных кассовых операций.

1. Для числового примера в тестовой БД нужен заказ с товарами на 300 сомони,
   доставкой 20 и сервисным сбором 10%: администратор задаёт процент в
   `/admin/settings` с обязательным обоснованием. Верните прежнее значение после проверки.
   Существующие заказы при изменении настроек не пересчитываются.
2. Пройдите обычные checkout, закупку и упаковку. Назначенный курьер открывает
   волну, нажимает «Забрал заказы» и «Доставлен и получено 350 сомони».
   Деньги попадают в «Моя касса» (`/admin/cash`), доставка закрывается.
3. На другом заказе откройте «Проблема при доставке»: причина «Качество товара»,
   позиция и количество на 60 сомони, решение «Принять остальное, убрать позиции».
   Перед подтверждением сервер покажет 350 - 60 - 6 = 284 сомони.
   Подтвердите согласованный результат, получите 284. Исходные суммы видны в «Расчёт и история».
4. Для полного отказа без ошибки сервиса выберите «Клиент передумал», всё количество
   и «Полный отказ». При включённом сохранении сборов останется 50 сомони.
   Курьер может получить 50 либо открыть «Клиент не оплатил / оплатил частично»,
   записать причину и завершить передачу. Для 0 и 20 сохранятся расхождения -50 и -30.
5. Для замены выберите проблемный товар, «Замена в другое окно» и доступное окно.
   В исходном заказе появится ссылка «Замена …-R1». До оплаты товар убирается
   из текущего счёта; при замене оплачивается только товар, без повторных сборов.
   После полной оплаты исходного заказа замена бесплатна. Сборщик видит её в обычной волне.
6. Администратор открывает `/admin/problems`, «Разобрать обращение», фиксирует
   результат звонка, ответственность и результат проверки. «Клиент оспаривает»
   выводит обращение наверх, но никого автоматически не обвиняет.
   Ссылка на клиента ведёт в `/admin/customers/:id`: история, телефоны, имена,
   счётчики, политика наличных и примечание. `manual_review`, `blocked` и отключённый
   профиль дают нейтральное сообщение и заказ «Ожидает оператора», без волны.
   Администратор подтверждает/отклоняет заказ; закрытое окно сначала нужно перенести.
7. Для возврата на месте сначала в «Расчёт и история» нажмите «Получить 350 сомони,
   не закрывая передачу». Оформите отказ от товара на 100: система рассчитает возврат 110.
   Нажмите «Вернул 110 сомони», затем «Завершить передачу заказа».
   После закрытия доставки/кассы курьер возвращать деньги не может: нужен администратор.
8. Курьер открывает `/admin/cash`, указывает «Фактически сдаю» и завершает смену.
   При расхождении обязательна причина. Администратор там же сверяет кассу с заметкой.
   Сверка НЕ закрывает заявления о неоплате заказов: они остаются в «Проблемы».
9. Поздняя жалоба: администратор открывает заказ, «Новое обращение после доставки».
   В «Расчёт и история → Корректировка администратора» можно отменить сбор,
   начислить компенсацию или отдельной записью исправить наличные. Причина обязательна.
   При неудачной попытке курьер выбирает повтор в этой волне, предлагает новое окно
   или передаёт вопрос администратору. Перенос упакованного заказа не создаёт повторную закупку.

Это тестирование учёта заявленных наличных, не доказательство физического получения денег.
Не используйте реальные денежные операции для тестов. Удержание сборов при отказе
без ошибки сервиса до production требует отдельной юридической проверки.

Перед проверкой подготовьте локальную БД и запустите приложение:

```bash
corepack pnpm db:generate
corepack pnpm db:deploy
corepack pnpm db:seed:catalog
corepack pnpm db:seed:checkout
corepack pnpm db:seed:staff
corepack pnpm dev
```

Вход для всех сотрудников находится по одному URL:
`http://localhost:3000/admin/login`. После входа приложение само открывает
подходящий раздел для роли.

| Роль | Электронная почта | Пароль | Открываемый раздел |
| --- | --- | --- | --- |
| Администратор | `admin@dushanbefresh.local` | `Dev-admin-only-2026!` | `/admin/orders` |
| Сборщик | `picker@dushanbefresh.local` | `Dev-picker-only-2026!` | `/admin/delivery-waves` |
| Курьер | `courier@dushanbefresh.local` | `Dev-courier-only-2026!` | `/admin/delivery-waves` |

Эти пароли предназначены только для локальной разработки. Передавать их в
боевое окружение нельзя. Если скрипт заполнения сотрудников уже был выполнен с переменными
`DEV_*_PASSWORD`, используйте заданные тогда значения: скрипт намеренно не меняет
существующий пароль.

### Сотрудники и несколько ролей

Один аккаунт может иметь роли `picker` и `courier` одновременно. Вход для всех
по-прежнему `/admin/login`; на публичной ссылке замените только домен.
Управление доступно администратору в «Настройки → Сотрудники»
(`/admin/settings/staff`). Сотрудник не может создавать аккаунты самостоятельно.

1. Нажмите «Новый сотрудник», заполните имя, email и пароль (минимум 12 символов,
не больше 72 байт), отметьте «Сборщик» и/или «Курьер», нажмите «Создать сотрудника».
2. Для изменения выберите сотрудника в списке. Можно менять имя, роли и флаг
«Сотрудник активен». Email существующего аккаунта не редактируется.
3. В блоке «Сброс пароля» задайте новый пароль. Смена пароля, набора ролей или
отключение завершает прежние сессии. Повторный seed пароль и роли не восстанавливает.
4. Роль администратора находится в отдельном раскрывающемся блоке и требует
явного подтверждения полного доступа. Нельзя снять собственный административный
доступ или отключить последнего администратора.
5. При незавершённых назначениях отключение/снятие нужной роли блокируется.
Откройте волну по ссылке из формы, выберите другого сотрудника и повторите изменение.
Доставленная волна с неоплаченным заказом также требует действующего курьера:
его можно заменить до отметки оплаты. Исторические назначения не удаляются.
Завершившего работу сборщика неоплаченный доставленный заказ не блокирует.
6. В «Настройки → Дежурные сотрудники» можно выбрать одного человека в обоих полях.
Недоступный прежний дежурный явно помечается и не назначается на новые волны.
Замена дежурного не перезаписывает уже сделанные назначения: их меняют в самой волне.

**Проверка: Али выполняет обе роли**

1. Создайте «Али» с новым email, собственным тестовым паролем и обеими ролями.
В настройках выберите Али дежурным сборщиком и курьером, сохраните.
2. Через клиентский сайт добавьте товары, откройте `/checkout` и оформите заказ
на окно без существующей волны. Если волна уже есть, проверьте её назначения:
они сохраняются; при необходимости администратор выбирает Али в обоих полях.
3. В карточке новой волны должны быть «Сборщик: Али» и «Курьер: Али».
4. В отдельном браузере/профиле войдите под Али. Откройте «Мои волны», нужную волну,
нажмите «Начать сборку», введите количество и цену закупки, «Отметить купленным».
5. На вкладке «Упаковать заказы» нажмите «Всё упаковано как заказано» для каждого
заказа, затем «Завершить сборку». Закупка и упаковка становятся недоступны для изменения.
6. На этой же странице автоматически открывается «Доставка» и появляется
«Забрал заказы». Нажмите её, затем «Доставлен и получено X сомони» для каждого заказа.
Повторный вход и ручная передача администратором не нужны.

**Проверка: Али собирает, Фарид доставляет**

1. Создайте Фарида только с ролью «Курьер». Дежурный сборщик: Али, курьер: Фарид.
Оформите заказ на другое свободное окно и проверьте назначения новой волны.
2. Откройте её одновременно под Али и Фаридом в разных браузерных профилях
(вкладки одного профиля используют одну cookie-сессию).
3. Али выполняет закупку/упаковку. Фарид видит «Готовится», сотрудников и счётчики
прогресса, но не закупочные цены, поставщиков и маржу; редактирование упаковки
недоступно, кнопки начала доставки нет.
4. После завершения сборки Фарид видит «Забрал заказы». Экран обновляется
автоматически каждые 10 секунд; также есть «Обновить». Али не получает действий
доставки этой волны, даже если его аккаунт глобально имеет роль курьера.
5. Фарид забирает заказы, отмечает доставку и оплату. Али видит состояние,
но не может изменить завершённую сборку или отметить деньги за Фарида.

### Обновление модели ролей

Миграция `20261004000000_staff_roles` добавляет типизированный `User.roles`
(`StaffRole[]`) и таблицу `operational_audit`. Старые `admin/picker/courier`
получают массив из одной роли; у клиентов массив пустой. ID, хеши паролей,
назначения и refresh-сессии сохраняются. Старое поле `role` оставлено для
совместимости клиентов, но **не является источником прав сотрудников**.
API `/me` и вход возвращают `roles`, а не одиночную `role`.

Обновляйте API и web совместно: остановите старые процессы записи, выполните
`corepack pnpm db:generate` и `corepack pnpm db:deploy`, затем запустите новую
версию. Перед применением на ценной БД сделайте резервную копию. Обратный запуск
старой версии после назначения нескольких ролей не поддерживается.

Критичные действия сотрудников сохраняют `userId`, время, действие и ID сущности:
закупка, упаковка, этапы волны/заказа, оплата, переназначение, смена дежурных,
создание/изменение сотрудника и сброс пароля. Пароли в журнал не попадают.
Отдельного UI просмотра журнала пока нет; доставка уведомлений также не добавлена.

### Каталог от администратора

1. Войдите как администратор и в верхнем меню откройте «Каталог».
2. Чтобы добавить категорию, в блоке «Категории» заполните «Новая категория»:
название, уникальный латинский `slug` (например, `berries`) и порядок. Нажмите
«Создать категорию».
3. Чтобы добавить товар, нажмите «Новый товар», выберите категорию, заполните
название, `slug`, единицу, продажную и закупочную цены, минимальное количество
и шаг. В поле «Фотография товара» выберите JPEG/PNG/WebP до 5 МБ.
Для весового товара оставьте включённым «Весовой товар»; затем нажмите
«Сохранить».
4. Чтобы изменить продажную либо ориентировочную закупочную цену, нажмите на
нужный товар в списке. В форме измените «Цена для клиента» или «Ориентир закупки»
и нажмите «Сохранить». Ориентир закупки также виден сборщику в назначенной волне,
но клиенту и курьеру закупочные цены не выдаются.
5. Чтобы выключить товар на сегодня, в строке товара нажмите «Сегодня: да».
Кнопка изменится на «Сегодня: нет»; товар перестанет появляться клиентам.
6. Чтобы включить товар снова, нажмите у него «Сегодня: нет». Полное отключение
товара выполняется соседней кнопкой «Включен» / «Выключен».

### Фотографии товаров

В `/admin` при создании или редактировании товара выберите файл в поле
«Фотография товара». Предпросмотр появляется до сохранения. Для замены выберите
другой файл; «Убрать фотографию» очищает выбор формы, но не изменяет сохранённый
товар до нажатия «Сохранить». Загрузка отправляется только при сохранении.

- Поддерживаются JPEG/JPG, PNG, WebP до 5 МБ, до 25 мегапикселей, без анимации.
- Включённый товар (`isActive=true`) требует фото, в том числе при изменении цены
  или переключении доступности. Для черновика без фото снимите «Включен».
- Старые товары без фото временно показывают общую нейтральную картинку;
  при первом редактировании включённого товара потребуется настоящее фото.
  Старые фиктивные seed-пути `/img/products/*.jpg` не считаются фотографиями.
  Повторный seed сохраняет загруженные фото (прочие тестовые поля по-прежнему обновляет).
- Фото показывается в каталоге, карточке, корзине и списке администратора.
  Файлы нормализуются сервером в WebP до 1600 px, EXIF удаляется.
- Единицы в интерфейсе: кг, г, шт., уп., пучок/пучка/пучков. Цены и количества
  отображаются с запятой, технические значения API остаются прежними.

**Хранение:** при `corepack pnpm dev` каталог `apps/api/var/product-images`
создаётся автоматически и исключён из Git. PostgreSQL хранит только относительный
путь в существующем `Product.imageUrl`; public API возвращает его как `image`.
Загрузка: `POST /api/v1/admin/product-images` (multipart, поле `file`, только admin).
Чтение: `GET /api/v1/media/:key` (публично, только обработанные WebP).
Работает через тот же `/api/v1` proxy, в том числе по публичной HTTPS-ссылке.

Другой каталог задаётся переменной окружения API `PRODUCT_IMAGES_DIR`.
Для production она обязательна и должна содержать абсолютный путь к **постоянному
тому**, доступному на запись API. Например, `PRODUCT_IMAGES_DIR=/data/product-images`.
Нужны резервные копии и контроль свободного места; лимит тела запроса reverse proxy
должен пропускать 5 МБ плюс multipart-обвязку (например, 6 МБ).
Без этой переменной production API не стартует, чтобы случайно не терять фото при деплое.

S3-совместимое хранилище предусмотрено архитектурой, но пока не подключено.
Для нескольких API-инстансов или хостинга с временным диском **до деплоя** нужно
реализовать адаптер `ImageStorage` для S3 и настроить bucket, credentials, резервирование.
Локальный адаптер пригоден для dev и одного сервера с persistent volume.
Автоматической очистки заменённых/непривязанных фото пока нет: не удаляйте файлы
вслепую, старые ссылки могут ещё храниться в корзинах.

### Заказ, сборка и доставка

1. Для тестового заказа откройте клиентский сайт `http://localhost:3000/catalog`
в отдельном окне или после выхода из админки. Добавьте товаров минимум на
120 сомони, откройте корзину, перейдите к оформлению, заполните контакты и адрес,
выберите свободное окно, подтвердите условия и создайте заказ.
2. Войдите как администратор. На «Заказы» по умолчанию открыты «Активные».
Новый заказ уже имеет статус «Подтверждён»: отдельная кнопка не требуется.
Вкладки «Завершённые» и «Отменённые» отделены; дата/слот/статус фильтруют
заказы внутри выбранной вкладки.
3. Волна уже создана автоматически, дежурные уже назначены. В «Волны доставки»
администратор может просто проверить это: формировать волну вручную больше не нужно.
4. Создайте ещё один заказ на тот же слот и третий на другой слот (для проверки
даты удобно выбрать следующий день). В админке должны быть 3 заказа и 2 волны:
в первой 2 заказа, во второй 1. Выберите дату доставки и нажмите «Показать»:
в таблице должны остаться только заказы с этой датой доставки, независимо от даты создания.
5. Войдите как сборщик. В «Мои волны» → «Предстоящие» сразу видны обе волны.
Откройте первую и нажмите
«Начать сборку». Во вкладке «Закупить товары» укажите «Куплено», «Цена закупки за 1 кг, сом»
и при необходимости примечание, затем «Отметить купленным». Карточка свернётся;
нажатие «Изменить» откроет её снова. Для других единиц подпись цены меняется
соответственно. «Ориентир рынка» доступен только для чтения.
Начатая волна находится во вкладке «В работе», после сборки переходит в «Завершённые».
6. Во вкладке «Упаковать заказы» видны компактные строки товаров каждого заказа.
После физической упаковки нажмите «Всё упаковано как заказано»: сервер сохранит
requestedQuantity как finalQuantity для ещё не обработанных позиций. Появится
«Заказ упакован». Открывать каждый заказ и повторять ввод количества больше не нужно.
Если товара меньше, он отсутствует или заменён, нажмите «Изменить» у нужной строки,
задайте фактическое количество/статус/примечание и сохраните изменение. После этого
общая кнопка заполнит только остальные позиции, не перезаписывая исключение.
Цена клиенту берётся из сохранённой копии данных заказа, итог позиции равен finalQuantity × зафиксированная цена,
а не закупочной цене. Нажмите «Завершить сборку»: волна и заказы станут «Собран».
7. Курьер в отдельном браузере/профиле заранее видит волну как «Готовится».
После завершения сборки состояние обновится в течение 10 секунд (или нажмите
«Обновить»). Когда партия физически получена, нажмите «Забрал заказы».
Волна и заказы перейдут в «У курьера» без подтверждения администратора.
8. В каждом заказе нажмите «Доставлен и получено X сомони». После последней
доставки волна завершится автоматически. Курьер не видит закупочные цены,
поставщика и маржу. Администратор видит доставленные заказы во вкладке «Завершённые».

### Проверка отклонения закупки и вмешательства администратора

**Цена за единицу и сумма закупки не взаимозаменяемы.** Для бананов с ориентиром
`10.00 сом/кг` введите количество `16`, цену за 1 кг `10`, нажмите «Отметить купленным».
Сохранённая карточка должна показать `16 кг × 10.00 сом/кг = 160.00 сом`, без предупреждения.
`purchaseTotal` считает только сервер через Decimal; отклонение считается как
`(purchaseUnitPrice - referencePurchasePrice) / referencePurchasePrice × 100`.
При цене `12` отклонение составляет 20%, а сумма при 16 кг равна `192.00`.
В поле цены не нужно вводить итог `160`: это означало бы 160 сом **за килограмм**.
После сохранения следующий товар поднимается вверх: список одноколоночный
на телефоне и компьютере. Для повторного ввода нажмите «Изменить».

Для кинзы в тестовом каталоге «Цена для клиента» = `2.50 сом/пучок`,
«Ориентир закупки» = `1.50 сом/пучок`. Это разные цены, не ошибка:
клиент видит первую, сборщик видит вторую как «Ориентир рынка».

1. До создания новой волны задайте товару ориентир закупки `8.00` в каталоге.
В «Настройки» задайте «Порог отклонения закупочной цены, %» = `15` и сохраните.
2. Сборщик вводит `8.30`: флага нет. При `9.20` (ровно 15%) флага также нет.
При `9.44` появится «Цена закупки выше ориентира на 18%. Нужна проверка администратора.», но завершение
сборки не блокируется. Администратор видит предупреждение в той же волне.
3. Администратор может поменять назначенного сборщика/курьера в полях волны, в том числе
заменить курьера в пути. Старый сотрудник потеряет доступ, новый увидит волну.
4. Для проблемного неоплаченного заказа до доставки откройте его и нажмите
«Отменить заказ». Он появится в «Отменённые». Закупочная история сохраняется.

### Проверка быстрой упаковки

1. Создайте заказ с 15 кг бананов, запишите закупку 16 кг. После упаковки одной
   кнопкой клиенту сохраняются ровно 15 кг, не 16. Его цена за кг не меняется.
2. В списке закупки проверьте «Куплено: 16 кг», «Нужно клиентам: 15 кг»,
   «Упаковано: 15 кг», «Остаток: 1 кг». До упаковки остаток включает всё ещё
   не упакованное; после упаковки всех заказов это излишек компании.
3. Для исключения через «Изменить» уменьшите количество отдельной позиции,
   сохраните, затем упакуйте остальные одной кнопкой. Исключение должно сохраниться,
   итог клиента уменьшиться, а остаток увеличиться. Удалённая/недоступная позиция
   имеет нулевой итог; замены по-прежнему требуют соблюдения политики клиента.
4. При нехватке закупки упаковка отклоняется целиком с указанием товара. Исправьте
   закупку или сохраните исключение и повторите. Списывать чужую закупку и
   упаковывать чужие волны нельзя. Повторное нажатие не меняет сохранённые позиции.

API: `POST /api/v1/admin/orders/:id/pack`, без тела, только для администратора или назначенного сборщика.
`remainingQuantity` в списке закупки считает сервер через Decimal:
`purchasedQuantity - сумма finalQuantity` по активным позициям picked/replaced,
с учётом фактического товара замены. До ввода закупки значение null.
Массовая упаковка работает только в статусе picking; статусы доставки не меняются до
«Завершить сборку». Складской учёт не добавлен.

### Почему окно доставки закрыто

`GET /api/v1/delivery-slots` и проверка оформления заказа возвращают `unavailableReasons`:

- `capacity_full`: «Мест больше нет»; все неотменённые заказы занимают места в окне.
- `cutoff_passed`: «Время заказа прошло»; в MVP крайний срок заказа совпадает с началом окна
  по времени Душанбе (UTC+05:00), включая точную границу времени.
- `wave_closed`: «Приём заказов закрыт — сборка уже началась»; волна в picking,
  picked, out_for_delivery или delivered. Завершение доставки не открывает слот заново.
- `wave_cancelled`: «Приём заказов закрыт — доставка отменена».
- `inactive`: «Приём заказов на это окно закрыт»; неактивные окна не включаются
  в публичный список, но причина возвращается при проверке ранее выбранного окна.

Если действуют несколько причин, интерфейс показывает все. У доступного окна массив
пустой. Сервер повторно проверяет доступность при создании заказа под блокировкой
слота, даже если клиент выбрал его до начала сборки.

Диагностика локальной БД 23 сентября 2026 в 08:32 по Душанбе: окно 23.09
10:00–12:00 закрыто из-за delivered-волны (2 из 10 мест), окно 24.09 10:00–12:00
из-за picking-волны (1 из 10). На момент проверки время начала ещё не наступило.
Эти конкретные состояния относятся только к локальной тестовой БД.

Все перечисленные действия доступны через интерфейс. Управление сотрудниками и паролями
находится в «Настройки → Сотрудники». Фиксированные стоимость доставки, сервисный сбор
и минимум заказа пока доступны только для просмотра; процентный сбор и политика
отказов редактируются в «Настройки → Расчёты при доставке».
Дежурные сотрудники и порог отклонения закупочной цены также редактируются. Прикрепление подтверждения закупки
и журнал согласований отклонений пока отсутствуют. Старые draft/placed-заказы
не попадают в новые вкладки и не подтверждаются миграцией: их нужно отдельно
разобрать через существующий API или сохранённую ссылку на заказ до запуска сборки.

### Тестовые данные и очистка для локальной проверки

- `corepack pnpm db:seed:catalog`: каталог (`db:seed` остаётся совместимым псевдонимом команды).
- `corepack pnpm db:seed:staff`: тестовые сотрудники и дежурные, без заказов/закупок.
- `corepack pnpm db:seed:checkout`: настройки оформления и будущие окна доставки.
- `corepack pnpm db:seed:operations`: необязательная демонстрация, 3 заказа через серверное
  оформление в двух окнах; фактические количества и цены остаются пустыми. Не запускайте
  эту команду перед ручной проверкой трёх собственных заказов.

Для чистой проверки остановите работу с локальными заказами и выполните:

```bash
corepack pnpm db:reset:operations --confirm
corepack pnpm db:seed:staff
corepack pnpm db:seed:checkout
```

Команда очистки удаляет **все заказы и волны выбранной локальной БД разработки**, включая созданные
вручную тестовые заказы, а не только строки из скриптов заполнения. Она сохраняет товары,
категории, сотрудников, клиентов, настройки приложения и окна доставки. Боевое и предрелизное окружения,
удалённый хост и запуск без `--confirm` запрещены. Не направляйте команды для разработки
на БД с реальными заказами. Очистка не является обычным шагом ежедневного запуска.
Также удаляются обращения, корректировки, попытки доставки, замены, кассовые записи,
смены и журнал удаляемых операций. Счётчики инцидентов клиентов обнуляются;
их политики, административные заметки и ограничения сохраняются.
